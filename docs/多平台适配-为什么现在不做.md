# 多平台适配：为什么现在不做

> 状态：**暂缓（不是否决）** · 记录日期 2026-10-28 · 相关：`docs/world-db.md`、动作队列设计（待写）

## 0. 一句话结论

**不是"不做多平台"，是"这件事被放错了层"。**

她那一侧（记忆 / 白名单 / 视界）早就平台无关了；真正卡住的是**发送通道**这一层——而它现在还在漏水。
先把它做对（队列 + 面板可见 + 回执真实），比先让它变宽更值。

---

## 1. 队列存在的唯一理由：抢一台机器的键鼠

| 通道类型 | 代表 | 发送方式 | 需要排队吗 |
|---|---|---|---|
| GUI 类 | 微信 PC 客户端 | 点按 + 打字 + 截图识别，抢**键鼠 / 焦点 / 剪贴板** | **必须** |
| API 类 | QQ(NapCat)、Telegram、Discord | WebSocket / HTTP，同步返回消息 id | **不需要** |

**只有"靠界面操作别人家软件"的通道才需要队列。**
把 API 通道塞进同一个队列，等于给一个已经有明确回执的通道再加一层减速带——那是退步。

**已做的预留**（不改逻辑，只留口子）：

- 队列表带 `platform` 字段
- `claim_next()` 按 `platform` 过滤
- `desk` 独占锁只包 GUI 动作

将来加 GUI 类软件（钉钉 / 飞书客户端）→ 只写 driver，队列不用改；
加 API 类软件 → 干脆不进队列。

---

## 2. 每加一个软件，要重做的是四件事，不是"写个 driver"

| 要做的事 | 微信的代价（2026-10-28 实测） | 新平台要不要重付 |
|---|---|---|
| **定位**（窗口 / 元素） | `detect_layout` + OCR + 图标外形排序；微信 4.x 改版一次全废 | 要 |
| **回执**（真的发出去了吗） | 靠解密库 `messages`；还要 per-DB keyring、假 key 识别、`file` 类不在 `message_media` 里 | 要 |
| **归属**（"我"还是"这个号"） | `is_self` 与发送账本对账、`_mark_own_files`、`_mark_aliens_world`——为一件事折腾一整天 | 要 |
| **登录态 / 风控** | 扫码、Hook 注入、封号风险 | 要 |

这不是"多功能"，这是四份新的脏活。

---

## 3. 更硬的理由：她现在不是被"平台太少"卡住

2026-10-28 当天真实数字：

- 微信库 **17 个**，其中 **1 个降级**（`MSG_0.db` 是 0 字节残壳）
- 回执 **271 条**，其中 **14 条 unconfirmed**
- 话丢过至少 **6 次**：「冒了」、「耶什么」、3 条被去重闸拦、1 条被 OCR 误判清框
- 同步曾经卡 **11 分钟**（`_db_signature` 的 10 分钟 mtime 桶）
- 单条发送 **9–73 秒**（最快 9s，最慢 73s 是多气泡 + 抢锁）

**一个平台都还没做稳。** 加第二个平台只会把这些 bug 复制一份，并让"到底哪一层的错"更难查。

---

## 4. 工程上的老实话：现在抽象一定是错的

`desk` 独占的东西（焦点、剪贴板、窗口激活）**是 GUI 独有的**。

要做多平台抽象，得先有**至少两个真实实现**才能抽出对的接口。现在只有一个完整的（微信 GUI）+ 一个半（QQ WS，而且从不抢键鼠）。这时候抽 `Channel`，抽出来的一定是"GUI 的形状"，将来 API 类通道会被迫适配一堆它根本不需要的概念（`desk`、`foreground`、`title_verify`）。

**当天已经吃过一次这个亏**：`verify_active_chat_title` 依赖 `_ACTIVE_ENABLED`，结果"关掉复用" ＝ "关掉校验"，把正向发送全拦死。

---

## 5. 她那一侧其实已经准备好了

多软件在**她**这边不是问题，架构早就是平台无关的：

```
world.db      inbound_event.platform / account_id
speak_policy  platform → account → chat 三层白名单
chat_alias    任意平台的 chat_id
snapshot      按 platform 分组渲染（已有「微信」「QQ」前缀）
```

**卡的只有"发送通道"这一层**——最脏、最贵、最容易崩的一层。
所以顺序应该是：**先把这一层做对，再让它变宽。**

---

## 6. 什么条件下重新评估（三条红线，全部满足才开工）

1. 微信这条路**连续 7 天**没有"话丢了"
2. 队列面板上 `pending` 的中位等待 **< 10 秒**
3. 确实有**第二个平台的真实使用场景**（不是"以防万一"）

满足后：两个实现都在手，`Channel` 接口才有依据，不会长成微信的形状。

---

## 7. 如果将来真做，最小路径草图

1. 抽 `Channel` 接口：`send(chat_id, text) -> Receipt`、`capabilities`、`verify(receipt)`
2. GUI 类通道实现里保留 `desk` 独占；API 类通道实现里不带 `desk`
3. 队列只在 `needs_desk == True` 的通道上启用
4. 回执统一成 `Receipt{kind, msg_id, ack, at}`，各通道自己填真凭据
5. 面板「通道」卡按通道渲染能力灯（已有原型：微信 / QQ 两行）
