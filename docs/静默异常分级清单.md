# 静默异常分级清单

## 这是什么

项目里 `except Exception` 超过 1200 处，其中一部分后面只跟 `pass` / 返回空值 / `continue`。这类写法让**调用方无法区分「确实没有」与「内部挂了」**，是最常见的隐性故障源。

一次性全改不现实——**不是所有 except 都该抛**。所以先分级再处理。

## 分级口径

| 级别 | 含义 | 处理建议 |
|---|---|---|
| **A** | 吞掉后把**空/假值返回给调用方**，且处于核心链路 | 必须修：至少要能区分「没有」与「挂了」（记日志 + 让调用方知情） |
| **B** | 吞掉但不外泄假值（循环跳过单条、局部兜底） | 补一条 debug/warning 日志即可 |
| **C** | 清理/收尾/可选增强/工具脚本 | 保持现状，属合理设计 |

## 怎么读 A 类 —— 它里面有两种性质，别一概而论

**① fail-closed（`return False`）**：集中在权限与准入门，例如
`BaseTool.authoritative_is_owner` / `authoritative_has_capability`、
`core/context/admission.py::enabled_for`。判定失败即「不放行」，
从安全角度这通常是**刻意**的，不要为了「报错更清楚」改成抛异常。
但仍应补一条日志 —— 否则主人权限被误判为非主人时，现场没有任何线索。

**② 静默降级（`return []` / `None` / `""`）**：集中在数据读取与上下文装配，
例如 `core/context/chat_window.py::load_messages`、
`core/context/assembler.py::read_context_trace`、记忆召回链路。
**这一类最危险**：调用方拿到的空值与「确实为空」完全无法区分，
故障表现为「助手忽然不记得了 / 群里的上下文丢了」这类玄学现象。
建议**优先修这一类**。
