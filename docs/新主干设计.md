# 新主干设计（strangler：旧主干逐刀删，新目录并存）

> 一句话：**旧主干一行不留；物理适配层（微信库解密 / UI 自动化 / 平台协议）只留实现，不留设计。**
> 立此文档的理由：2026-10-21 真机暴露的病不是「哪一步写错」，而是**有两条主干、
> 新能力装在没人走的那条上**（`_job_tick` 一条日志都没有），且没有任何闸检查「可达性」。

## 一、七条总纲（每条都可由机器检查）

| # | 纪律 | 谁来查 |
|---|---|---|
1 | **唯一入口**：一个回合只有 `core/turn/entry.py::run_turn`，九步固定 | `scripts/check_turn_reachability.py` |
2 | **形式与意图解耦**：进来先归一成 `Observation`，形式只决定「要不要先看/听/读」 | `core/intake/`（M1） |
3 | **判只有一次模型调用**：只填 `quotes/slots/gaps/timing/affect`；`risk/others` 由代码从 effects/在场者算 | `core/verdict/reading.py`（M1） |
4 | **四处置封闭**：`say / ask / do / abstain`，由 6 行矩阵唯一裁决 | `core/verdict/matrix.py`（M1） |
5 | **状态只有三处**：账本（append-only）/ 在手的事 / 政策；其余是投影 | `scripts/check_invariants.py`（I1–I7） |
6 | **出口与能力唯一**：对外只说 `deliver()`，动手只过单一工具目录，物理动作只过设备租约 | `check_single_catalog` + `check_topology` |
7 | **失败必须可见**：任何静默 `return None` 必须有日志或 raise；失败动作必须落回执 | `scripts/check_no_silent_return.py` |

## 四、M0 落地内容

- `core/turn/steps.py`：九步常量 + `is_step/order_of/before`；
- `core/turn/trace.py`：`TurnTrace` + 每步一行 `turn_step turn=… step=… status=… ms=… chat_id=… note=…`（只写日志，不写账本）；
- `core/turn/entry.py`：`run_turn(ctx)`，九步按序；某步抛异常 → 该步 `error`、后续不跑（fail-closed）、`finish` 一定跑；
- 三道新闸：`check_turn_reachability`（方向/私有孤儿/唯一入口）、`check_no_silent_return`（新目录不许静默返回）、`check_single_catalog`（`ToolSpec` 只在 `core/tools/`，MCP 声明除外）；
- 测试：`tests/test_turn_skeleton.py`（40 checks）、`tests/test_turn_gates.py`（11 checks，含合成违规必须被抓）。

## 五、与旧的关系（当下）

## 六、M1 落地内容（本次）

- `core/intake/`：`Observation`（where/by/form/text/media/quoted/mention/system）+ `normalize()` 纯函数，
  复用 `chat_type` 形状判断与平台字段，坏输入降级为空观察、不抛；
- `core/verdict/reading.py`：只让模型填 5 个标量（`quotes/slots/gaps/timing/affect` + `confidence`），
  解析器容围栏/裸 JSON，夹紧取值范围，坏输入返 None 不抛；
- `core/verdict/risk.py`：**风险由代码从 effects 算**（`read=0 / write_local·ui_control=1 / external_send=2`，
  不认识的效果按最高），在场者由 `where` 与风险算——模型无权定价；
- `core/verdict/matrix.py`：6 行表（顺序即优先级）→ `say/ask/do/abstain`，`Decision` 带 reason 与后果提示；
- `core/verdict/shadow.py`：`compare()` 只记一行 `verdict_shadow old=… new=… agree=…`，不接管出口；
- 接线一处：`core/context/intent.py` 在 `reply_intent_resolved` 之前打这行影子日志，整段 `try/except`，
  坏了只 `log.debug`——**零行为变更**；
- 测试：`tests/test_intake_verdict.py`（66 checks，含 9 个真实例子做表格规格）、
  该接线锁（`tests/test_verdict_shadow_wiring.py`）已随 N1 judge 退役（2026-10-23）一并删除：
  桩里不再有调用，锁没有对象可钉。

**已知缺口（M2 补）**：影子档现在只能对照「旧意图 vs 矩阵结论」，因为旧的 `reply_intent_resolved`
不提供 `quotes/slots`，所以矩阵多数只能落在 `say/ask`。M2 接 `say` 时补上真实 `quotes`，
`do` 才可能被点亮。

## 七、M3 第一刀：模型可见的工具名单只有一个属主

`core/tools/catalog.py`：

| 常量 / 函数 | 含义 |
|---|---|
| `PLAN_LOOP_ALLOWED` | 可以在计划里自动执行的工具（只读 + `send_plan` + `gui_state`），**唯一属主** |
| `PLAN_LOOP_READ_ONLY` | 上面的只读子集（去掉两个非只读动词） |
| `allowed_in_plan(name)` | 这个工具名能不能在计划里自动执行 |
| `read_only_in_plan()` | 只读子集（frozenset） |

`agents/planner.py` 里那张手写白名单 785 字符被删掉，改成一行别名
`PLAN_LOOP_READ_ONLY_TOOLS = _CATALOG.PLAN_LOOP_ALLOWED`——四个使用点行为不变。

闸 `scripts/check_single_catalog.py` 加规则 C：`PLAN_LOOP_ALLOWED` / `PLAN_LOOP_READ_ONLY_TOOLS`
只许在 `core/tools/catalog.py` 定义，别处只许「别名 re-export」（`= _CATALOG.…`），
否则 `FAILED C …`。

**为什么先切这张名单**：它同时是「模型看得见什么」和「什么能在计划里自动执行」两份
事实的来源。今天真机里她说「我没有往群里发消息的工具」，根因就是这两份事实各在一处，
互相不知道对方改了什么。

## 八、M3 第二刀：工具调用唯一入口 + 目录覆盖影子

`core/tools/invoke.py`：

| 函数 | 含义 |
|---|---|
| `invoke(registry, name, params, *, turn_id="", target="", mode="auto")` | **唯一调用点**：读效果走 `observe()`、写效果走 `act()`，一行 `tool_invoke name=… effects=… via=… status=… ms=…` |
| `catalog_names()` | 统一目录（`core/tools/builtin.build_registry()`）里现有的工具名 |
| `covered_by_catalog(name)` | 这个工具名在统一目录里有没有实现——**模型侧 18 个工具迁移的进度尺** |

`WRITE_EFFECTS = {write_local, ui_control, external_send}`；不认识的效果按**读**处理
（不猜写）；查不到 spec 直接抛（fail closed）。

`agents/base.py::act()` 开头加一行影子日志（`try/except` + structlog 的 f-string，
位置参数不插值这条已经踩过两次）：

```
tool_catalog_shadow tool=web_search covered=0
```

`covered=0` 就是「这个工具模型能调，但统一目录里还没有」，那就是 M3 剩余的工作量清单。

## 九、M3 第三刀：模型侧 23 个工具全部进入同一份目录

现状数字：模型侧 23 个工具，执行器侧 10 个，**交集只有 5 个**。所以「她会不会用某个工具」
取决于问的是哪份清单。

做法（尊重 layering 规则 10：core 不许 import agents）：

| 层 | 负责什么 |
|---|---|
`core/tools/declared.py` | 18 条**声明**（name / effect / 一句 purpose / owner="agents/tools"）——单一目录的「数据」 |
`core/tools/builtin.build_registry()` | 把声明汇入同一 registry（`register` 失败会打 `declared_spec_rejected reason=…`） |
`agents/tools/*` | 实现与绑定（从 agents 侧反向往 registry 里 `bind()`） |

效果按最保守口径登记：涉及对外发送的一律 `external_send`（`send_message` / `send_sticker` /
`notify_user` / `send_plan`），本机改动 `write_local`（`create_todo` / `complete_todo` /
`remember` / `correct_emoji_desc` / `create_reminder`），其余 `read`。

**踩到的坑**：`ToolSpec.validate()` 要求 `returns` 与 `owner` 非空，缺了就静默 `register` 失败
（返回 `(False, "bad_spec")` 没人看）——所以注册处现在必须检查返回值并打日志。
这条也解释了为什么「目录看着加了其实没加」。

## 十、M3 收尾：回合入口唯一化（`scripts/check_turn_entry.py`）

真机教训：能力装在旧入口 `core/routing/turn_pipeline.py::generate_turn`（LEGACY），而真人消息
走的是 `agents/conversational.py` 的 agentic 回合——于是 `_job_tick` 从来没被真人回合调用过，
「主人回可以却没人听」查了很久才发现。

闸的四条（`python -X utf8 scripts/check_turn_entry.py`，只读）：

| 规则 | 内容 |
|---|---|
R1 | `def _job_tick(` 只能有一处，且只在 `core/routing/turn_pipeline.py` |
R2 | 生产代码里调用 `_job_tick(` 的文件必须登记在 `ALLOWED_CALLERS`（当前 2 处：旧 `generate_turn` + 真人路径） |
R3 | `generate_turn` 必须带 `LEGACY` 标记（旧入口要能被认出来，否则永远删不掉） |
R4 | `agents/conversational.py` 里调用之后 900 字内必须有 `_turn.step("act"`（否则「这一步跑了吗」又变成猜） |

第一次真跑就抓到两条真问题：`generate_turn` 没标 LEGACY；R4 的窗口 400 字太窄（调用自己跨 250 字）
→ 改成 900 字。**闸的第一版误报比没有闸更有价值**，但要记住：窗口类规则要按真实代码长度定，不要拍脑袋。
