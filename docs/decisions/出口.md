# 出口（只放行 · 不判）

> 依据：`output/3d/viewer_css.html` 里 `(620, 0, 1000)` 那块板（贴图 `t_exit.png`，板面写着「只放行 · 不判 / 按注册表，不限平台」），以及 `说` 那条管子（判 → 出口）。
> 四问先答：**图上是哪块** = 判板右手第一块；**进来什么** = 判的 `deliver` 清单（0~2 条）；**出去什么** = 回执（送到没有、平台消息号）、一行账本、必要时一行回显关联；**职责** = 执行，不判断。

## 1. 图上位置

- 板子：`addBoard(300, 220, 620, 0, LLM_Z, 't_exit.png', '出口')`，在判板右侧、软件适配器左侧。
- 管子：`说`（判 → 出口，实线）；出口 → 软件适配器是下一段（同一块板后面）。
- 它与「工具包」的区别：工具包是**拿信息进来**，出口是**把结果送出去**。两者都不参与判断。

## 2. 是什么

一条流水线，四步，每步只做一件事：

```
deliver 清单
   └─ ① 校验：kind 在不在注册表、target 有没有、权限够不够、限流过没过
        └─ ② 执行：调一个 adapter（一次投递 = 一个 adapter 调用）
             └─ ③ 回执：拿到平台消息号 / 失败原因
                  └─ ④ 落账：写一行结果（成功或失败都写）
```

**它不改写内容。** 判给什么就发什么；要改，是判在给之前改。

## 3. 「只放行」意味着什么

| 出口**做** | 出口**不做** |
|---|---|
| 检查 kind 是否已注册、是否人工启用 | 不判断「该不该说」 |
| 检查 target 是否存在（会话 / 人 / 自己） | 不挑措辞、不补 @、不加语气 |
| 检查限流（每分钟 / 每小时 / 每会话） | 不决定长度 |
| 检查 dry-run 白名单 | 不重排、不合并消息 |
| 调 adapter、收回执、落账 | 不生成内容、不总结 |

一句话：**出口是执行器，不是编辑，也不是决策者。**

## 4. 输入从哪来 / 输出到哪去

### 4.1 输入从哪来（三条）

| 输入 | 谁给 | 从哪块板/管子过来 | 内容 |
|---|---|---|---|
| **① 投递清单** | 判 | 判板 `(0,0,1000)` → `说` 管子 | `deliver: [{kind, target, payload}]`，0~2 条 |
| **② 能力清单** | 人（配置） | 注册表（`data/` 配置，不在图上） | 每个 adapter 声明能发什么 kind、target 类型、限流、是否启用 |
| **③ 放行条件** | 代码 | 限流器 / dry-run 开关 / 白名单 | 每会话每分钟、每小时上限；白名单内才真发 |

**注意**：出口**不**从世界面、记忆立方体、工具包取任何东西。它的输入只有这三条。

### 4.2 输出到哪去（四条）

| 输出去向 | 谁收 | 形态 | 落哪 |
|---|---|---|---|
| **① 平台消息** | 软件适配器 → 平台 API | 一次调用一个 adapter | 平台侧（微信 / QQ / 日历 / 邮件 / 浏览器） |
| **② 回执** | 账本 + 量具 | `Receipt{kind,target,adapter,platform_msg_id,at,status}` | 账本一行（成功/失败都写） |
| **③ 回显** | ① 落屏闸门 | 平台回推的 `is_self` 消息 | 账本**另一行**，用 `platform_msg_id` 关联原行 |
| **④ 失败/跳过原因** | 账本 + 量具 | `reason`（rate_limit / dry_run / no_target / duplicate / blocked） | 账本一行 |

**出口不写世界面**：世界面是 ① 落屏后用账本后缀**渲染**出来的，不会因为出口发了什么就改变——回显得等平台真的推回来。

### 4.3 一次投递的完整路径（含上下游）

```
判 (deliver)  ──说──▶  出口
                        ① 校验 kind/target/限流/dry-run
                        ② 调 adapter ──▶ 软件·适配器 ──▶ 平台
                        ③ 收 Receipt ──▶ 账本一行
                                          └─▶ 量具（重复发送率/回执率/时延）
                        ④ 平台回显 ──▶ ① 落屏 ──▶ 账本另一行(is_self)
                                                └─▶ 世界面渲染时才出现
```

### 4.4 产物归属一览

| 产物 | 生产者 | 消费者 | 是否可改 |
|---|---|---|---|
| `deliver` 清单 | 判 | 出口 | 否（回合结束即定） |
| 平台消息 | 平台 | 群里的人 | **否**（发出去就收不回） |
| `Receipt` | 出口 | 账本 / 量具 | 否（只追加） |
| 回显行 | ① 落屏 | 世界面 / 判（下一回合） | 否 |
| 失败行 | 出口 | 账本 / 量具 | 否 |

## 5. 六种结果（不许有第七种）

| 结果 | 含义 | 要不要重试 |
|---|---|---|
| `sent` | 平台已接受，有消息号 | 不用 |
| `skipped` | 没发（限流 / 无 target / dry-run / 空内容），带 reason | 不用 |
| `blocked` | 策略拦下（权限、注册表未启用、白名单外） | 不用 |
| `failed` | 调用了但失败（网络、平台报错），带 `retryable` | 只在 `retryable` 时 |
| `partial` | 多段只成功一部分（文件 + 说明） | 只补失败那一段 |
| `pending_approval` | 动作需要人批准才能发（花钱 / 不可逆 / 涉隐私），**先挂起**，一步不带 `approval` 就一个字节都不发 | 等 `approval`，不改内容重投 |

`pending_approval` 由「在手的事」产生（见 `办_在手的事.md`）：出口只认 `approval{job_id, step_n, action_hash, who, channel}` 这一行，没有就挂起并落账（`skipped(reason=pending_approval)` 与挂起行二者只写一行，`status=pending_approval`）。

**没有「沉默地丢掉」这个选项**：凡是没发出去的，必须有一行 `skipped/blocked` 说明原因。

### 5.1 第六态由谁造、造完去哪（U-11 第一半）

`core/speech/delivery.py::deliver_pending_approvals()` 是第六态的唯一出口实现：

| `DELIVERY_CONTRACT` | 行为 |
|---|---|
| `off`（默认） | 返回 `[]`，一行日志都不写——与重构前逐字节同行为 |
| `shadow` | 每条造一条回执 + 一行日志，**不调** `ledger`（影子期不写任何账） |
| `on` | 每条造一条回执并逐条交给 `ledger` 钩子（回执表的唯一入口） |

三条硬线：**签名里没有 registry**（结构上不可能发送）、回执恒为 `ack="none"` 且两个消息号为空
（"没发出去"与"发出去了"一眼可分）、**不写** `_SENT` / `_SENT_PER_TURN`（否则会把后面真正的投递判成重复）。
`is_delivered()` 对它是 `False`——重复发送率的分母绝不把它算成已发。

真正的「要不要我帮你订」不在这里：那是**判**在下一回合用普通 `deliver` 说的话（可以先 dry-run）。
出口只负责把「挂起了、等谁批哪一步」记下来。

### 5.2 回执落到哪：`delivery_receipts`（迁移 65）

落账不是出口自己写库（出口不碰数据库），而是经 `ledger` 钩子交给
`core/terminal/delivery_receipts.py::make_ledger()`：

| 列 | 说明 |
|---|---|
| `turn_id` / `chat_id` | 哪一回合、哪个会话 |
| `status` | 六态之一（`sent` / `skipped` / `blocked` / `failed` / `partial` / `pending_approval`） |
| `kind` / `target` / `ack` / `reason` | 与 `Receipt` 同名同义 |
| `platform_msg_id` / `client_msg_id` | 平台回执号（第六态两个都空） |
| `detail` / `ref` | 一段人话 + 指向对象（`job-abc#2`） |

三条纪律：**每条回执一行**（"没发出去"也必须有行，否则重复发送率算不准）、
**同一回合 + 同一 `ref` + 同一 kind 只写一行**（唯一索引 + `INSERT OR IGNORE`，
重放不灌双份）、**写失败只 log**（旁注不许阻断回合）。整表可删可重建——
"她说过什么"在账本的回显行里，不在这张表里。

### 5.3 旧路径也留痕：一行回执（2026-10-21）

`core/speech/rhythm.py` → `core/speech/outbound.py` → provider 这条**旧出口路径一直在发消息**，
但它对「发出去的是什么」只有一个弱证据：微信输入框空了。既没有平台消息号，也没落过库
（`delivery_receipts` 长期 0 行）。

三处补齐，全部**旁注优先**：

| 位置 | 做了什么 | 失败时 |
| --- | --- | --- |
| `core/execution/provider.py::SendResult` | 新增 `ack`（`platform_id` / `unconfirmed` / `error`）、`local_id`、`server_id`；**不再把 `sent_at` 当消息号** | 无 |
| `core/execution/wx_sender.py` | 发送前记基线 `ack_baseline(who)`，发送后 `ack_after_send()` 回读对账（`mine=True` 且正文一致的新行） | 拿不到就报 `unconfirmed`，不许改判「没发出去」 |
| `core/speech/receipts.py` + `outbound.py` | 成功分支落一行 `delivery_receipts`（`DELIVERY_CONTRACT=on` 才写） | 只 `log.warning`，不许把已发出的消息写成失败 |

三条纪律：

1. **真话优先**：有 `server_id` 才写 `platform_id`；只有「输入框空了」就写 `unconfirmed`。
   两种都不是 `sent` 的替身——它们是「我知道多少」的刻度。
2. **开关默认 off**：`WECHAT_SEND` 关着不读库、不变慢；`DELIVERY_CONTRACT` 关着一行不写。
   默认行为与接线前逐字一致。
3. **回执是旁注**：写库失败、形状不对、库读不到，一律只降级，不许阻断发送或改写判定。

### 5.4 影子档接进回合（2026-10-21）

新出口（`core/speech/delivery.py`）现在挂在 `agents/conversational.py::audit_verdict_contract`
里：判决合法时，把 `deliver` 清单过一遍出口的判定分支，**恒 `dry_run=True`**，一条都不发。

三件事说清楚：

1. **为什么不发**：旧路径（`rhythm → outbound`）还在生产发消息，这里再发就是双发。
   重复发送率必须为 0，这是唯一硬指标。
2. **为什么写死 `dry_run=True`**：这一层**没有真发的能力**——要开闸得改代码 + 绑适配器，
   不是改一个开关。开关只决定「影子跑不跑」（`DELIVERY_CONTRACT`：off / shadow / on 都只影响这层）。
3. **影子得到什么**：每条投递一条回执（`skipped(reason=dry_run)` 或 `blocked(reason=adapter_disabled)`
   —— 今天没有适配器注册，所以大多是后者）。日志一行：`exit_shadow turn_id=… items=… statuses=…`。

它能回答一个以前答不出的问题：**如果换成新出口，这一回合会得到什么回执**。

适配器表用 `core/execution/wechat_adapter.default_registry()`：`wechat` 已登记、**未启用**，
所以今天拿到的是 `blocked(adapter_disabled)`；人一旦 `enable("wechat")`，影子档立刻变成
`skipped(dry_run)`——仍然一条不发，但 kinds / targets / 限流三道校验会真的跑起来。

### 5.5 真正的「唯一对外口」在哪（2026-10-21 核对）

R3 一直写着「唯一对外口 = `core/speech/rhythm.py:146`」。**这句不准确**：`rhythm.deliver()`
只是**多气泡拆分器**（一句长话拆成几条），它返回 `None` 时调用方还要再走一次单条发送。

真正的收口点是网关：

```
core/speech/outbound.py:1057  async def send_text(self, draft, snapshot, context)
core/speech/outbound.py:1062  async def send_file(self, draft, snapshot, context)
（回执记录：`core/speech/outbound.py:228 _record_delivery_receipt`；调用点：`core/speech/outbound.py:1478`）
```

现有调用点（全仓 grep，`gateway.send_text` / `gateway.send_file`）：

| 调用点 | 场景 |
| --- | --- |
| `agents/tools/messaging.py:111`（`send_text`）/ `:103`（`send_file`） | 模型决定说话（主路径，先过 `rhythm` 拆气泡） |
| `core/speech/rhythm.py:181` | 多气泡逐条发 |
| `agents/proactive_trigger.py:338` | 主动开口 |
| `core/execution/owner_ask.py:275` | 回头问主人 |
| `web/routes_api.py:1271` | 控制台手动发一句 |

（`web/routes_api.py` 里其它 `ws.send_text(...)` 是 WebSocket 往浏览器推事件，不是平台发送。）

**结论**：把旧路径换成新出口，改 `rhythm.py` 只覆盖 1/5；正确的落点是
`OutboundGateway.send_text/send_file` 这个收口点——那也是唯一能保证「每一句话都有回执」的地方。
这件事是**通道切换**（行为变化），要单独立切片 + `DELIVERY_CONTRACT=on` + 量具，不能顺手改。

### 5.9.1 桥必须取「适配器注册表」，不是「工具注册表」（2026-10-21 真机修）

影子档第一晚的日志每条都写 `exit_status=blocked exit_reason=no_adapter`——读起来像
「微信根本没接」，其实微信适配器早注册了。根因：`core/speech/legacy_bridge.py` 在不传
`registry` 时默认取的是 `core.jobs.executor.default_registry()`，那是**工具注册表**
（她办事的世界），里面没有 `wechat` 这个键，于是 `registry.get("wechat")` 恒 None。

- 改成默认取 `core.execution.wechat_adapter.default_registry()`（出口的世界）。
- 修后影子档说真话：`blocked / adapter_disabled`（注册了但没人 `enable()`），
  只有真的没登记适配器时才 `no_adapter`。
- 教训：**两个"注册表"同名不同物**（工具注册表 vs 适配器注册表），凡是拿默认值的地方
  都要写清楚拿的是哪一个；日志词表要对得上，否则没人能从日志里看出到底断在哪一环。

### 5.10 回执不在主路径上等 + 出口作用域（2026-10-21）

**一、回执改成后台补账。** 微信落盘实测 **26 秒**；原来的写法是发完立刻同步回读，
而 `refresh_db()` 在"增量没变化"时会**全量再解一次（几秒）**——于是每条回复白慢
2–5 秒，回执却多半还是 `unconfirmed`（那时候行还没落盘）。

现在：

| 位置 | 行为 |
|---|---|
| `wx_sender.send_text` | 发完立刻返回 `ack=pending`（`WECHAT_SEND=on` 时才起补账线程） |
| `wx_sender._lookup_ack` | 只做**增量**刷新（`refresh_db(full_fallback=False)`），绝不全量 |
| `wx_sender._backfill_ack` | 后台盯 30 秒（20×1.5s），拿到就写 |
| `delivery_receipts.update_pending_ack` | 只补 `ack / platform_msg_id / client_msg_id` 三列（+`detail` 后缀），**status 与 kind 一个字不改** |

为什么是 UPDATE 而不是再插一行：一个回合的回执是**一行**，此刻只是平台消息号还没到；
唯一索引 `(turn_id, kind, ref, target)` 会把第二行 IGNORE 掉。补账不许改判。

**二、出口作用域 `YINYUE_EXIT_SCOPE_CHATS`。** 在"让新出口接管传输"之前，先决定
**给谁接管**：名单内的会话才放行，名单外一律 `skipped / out_of_scope`，名单为空 =
不设限（向后兼容）。这样"只给 Elaina 私聊开"才可能，而不会顺带把 107 人群也切过去。

### 5.11 适配器启用也归人管（`YINYUE_WECHAT_ADAPTER_ENABLE`，2026-10-21）

"只给 Elaina 开新出口"需要两个前提同时成立：

| 闸 | 变量 | 管什么 |
|---|---|---|
| 准不准 | `YINYUE_WECHAT_ADAPTER_ENABLE=1` | 微信适配器是否以**启用态**构建（默认关 → 出口一律 `adapter_disabled`） |
| 给谁 | `YINYUE_EXIT_SCOPE_CHATS=wxid_seed01` | 哪些会话允许新出口接手传输（空 = 不设限） |

刻意**不做**三态开关：`registry.enable()` 是"允许她真的替你发消息"的一次运行期授权，
不是一个实验档，所以用 on/off 的 env，含糊值（`maybe`、空）一律算关。

实测（`LEGACY_VIA_EXIT=shadow`）：
- 名单内 + 启用 → `dry_run`（闸走通、零字节）；
- 名单外 → `skipped / out_of_scope`；
- 未启用 → `blocked / adapter_disabled`。

### 5.12 出口传地址，微信只认名字（2026-10-21 真机）

**现象**：第一次开新出口，私聊那条发不出去，日志是

```
wx_search_field_readback_inconclusive who=wxid_seed01
wx_open_chat_strict_mismatch reason=当前打开的聊天是"鲸鲸的测试群(3)"，与目标"wxid_seed01"不符，已中止发送
```

**根因**：出口传进来的是**地址**（`chat_id`），而微信搜索框只认**显示名**；新出口把
地址直接当成名字去找。旧路径一直有 `resolve_nickname()` 这一层，新出口漏了。

**修法**：`core/execution/gui/wechat.py::display_name_for(chat)`（`wx_chat.resolve_nickname`
→ 查不到就原样返回，不猜），`send_and_verify` 用它得到 `shown` 再去 `fill_message`；
**回执里的 `chat` 仍记地址**（地址才是投递对象，名字只是找路用的）。

顺带确认了两件好事：① 失败是 **fail-closed**——顶栏验收不符就中止，一个字节没发出去；
② 第一行真回执落地了（`status=failed, ack=error, detail=fill_failed no_target…`），
说明"发不出去也要有痕迹"这条真的成立。

## 6. 注册表：声明式 + 人工启用

- 每个 adapter **声明**它能做什么：`kinds[]`、`targets` 类型、限流参数、是否需要人工启用；
- 注册表**不自动启用**新 adapter：默认 `disabled`，由人打开；
- `kind` 在注册表里找不到 ⇒ 明确 `blocked`，不是静默丢弃；
- **不限平台**：微信、QQ、日历、邮件、浏览器、内部系统，只要注册了 adapter 就能发；平台差异全在 adapter 里，出口不管。

一次投递只调**一个** adapter：多平台分发是「投多条」，不是出口内部循环。

## 7. 幂等与重复发送

- 幂等键：`(chat_id, kind, content_hash, 回合内序号)`；
- 同一幂等键重复投递 ⇒ 第二次直接 `skipped(reason=duplicate)`；
- **重复发送率必须为 0**（这是唯一的硬指标，出过一次真实事故）。

## 8. 失败与重试

- 只对 `retryable=true` 重试，最多 1 次，退避 2s；
- 重试仍失败 ⇒ 落 `failed`，**不静默**；
- 失败要不要对她可见（「我发不出去」），见 §12 未定；
- **不许**因为发送失败就改写内容重发（那会变成出口在编辑）。

## 9. dry-run

- 全局开关 `DRY_RUN_SEND`；白名单会话真的发，其余只记账；
- dry-run 命中时也要写账本（`skipped(reason=dry_run)`），否则「她说过什么」会缺行。

| 项 | 预算 |
|---|---|
| 单回合投递条数 | ≤2 |
| 单次 adapter 调用超时 | 10s（文件类 30s） |
| 账本写入 | 与投递同事务，失败也要写 |
| 回执等待 | 同步等 1 次，不等平台二次确认 |

## 11. 边界（明确不管）

| 不管 | 归谁 |
|---|---|
| 说什么、怎么说 | 判 / 软件适配器（措辞） |
| 平台登录、扫码、封号 | 人 |
| 消息内容改写、合并、重排 | 谁都不做（要改就重投） |
| 长期存储原始负载 | 账本只存指针与 hash |
| 定时触发 | 后台任务（提醒） |

## 12. 量具

| 指标 | 口径 | 目标 |
|---|---|---|
| 重复发送率 | 同幂等键发出两次 / 总投递 | **0** |
| 回执率 | 有 `platform_msg_id` 的 `sent` / `sent` | ≥99% |
| 平均投递时延 | `deliver` → `Receipt` | ≤2s（文件类除外） |
| 失败分类 | 按 error 聚合 | 可解释 |
| 被限流次数 | `skipped(reason=rate_limit)` | 观察 |
| dry-run 命中 | `skipped(reason=dry_run)` | 观察 |
| 静默丢弃 | 应恒为 0 | **0** |

## 13. 不做

- 不做「多平台同时发」的编排；
- 不做内容改写、缩写、润色；
- 不做「发送失败的自动降级」（换平台 / 换措辞）；
- 不把回显合并进原消息行。

## 14. 已定（原「未定」五条，2026-10-19 拍）

| # | 项 | 结论 |
|---|---|---|
| 1 | 发送失败对她的可见性 | **不写死话术**：把「上一条投递失败」作为**读数**交给判（与第 5 样「限流读数」同一路），由判自己决定说不说、说什么。失败本身照常 `failed` + 回执进账本，**不许静默** |
| 2 | 平台无回执怎么计 | 三态：`sent`（有平台消息号）/ `sent_unconfirmed`（无号、无错误）/ `failed`。重复发送率把前两者都算「已发」；幂等键仍按 `content_hash + target` 拦重发 |
| 3 | 文件 + 说明算一条还是两条 | **一条投递 = 一个 `deliver` 项**（`kind=file` + 可选 `text` 作伴随语，≤40 字）。适配器内部按 part 发（先文件后文字），回执按 part 记，聚合回该项的 `ok / partial / failed` |
| 4 | 撤回算不算一个 kind | **算**（`kind=revoke`），但走**单独注册项** + 默认 `disabled` + 需人工启用 + 每会话每日上限——它不可逆 |
| 5 | `content_hash` 是否含 @ 前缀 | **不含**。哈希只算正文（剥掉前导 @ 与零宽字符）；@ 由 `target` 单独入键。含 @ 的话，「同一句话改 @ 另一个人」会被判成同一内容而漏发 |

## 5.6 最后一段传输：谁来按那个回车（U-14，2026-10-21）

出口板画的是一条管子：`说` → 出口 → 适配器。但代码里真正唯一的对外口不是
`core/speech/rhythm.py`，而是 `core/speech/outbound.py::send_text/send_file`（§5.5）。
它跑完十几道闸（策略、输出闸、社会闸、@ 裁定、语气观察、知识边界、近重复闸）之后，
最后只有一句话：

```python
result = await provider.send(target_id, applied.content)
```

`result` 只有一个 `ok` 和一个 `msg_id`——**发出去成不成、有没有平台消息号，全靠平台 provider
自报**。这一片（`refactor_plan.yaml` 的 U-14）只换这句话：

```python
bridged = await self._send_via_exit_bridge(applied, target_id, context, turn_id=...)
if bridged is not None:
    result = bridged            # 新出口（core/speech/delivery.deliver）
elif ...:
    result = await provider.send(...)   # 旧路，逐字节不变
```

于是这一次发送第一次有了：平台回执（`platform_msg_id`）、六种状态、幂等键、
`delivery_receipts` 落账（§5.2）。

**三条纪律**

| # | 纪律 | 为什么 |
|---|---|---|
| 1 | **只换传输，不换判定** | 上面十几道闸一行动不得；桥只回答「用什么送出去」 |
| 2 | **默认 off**（`LEGACY_VIA_EXIT`） | `off` 时桥一行都不参与，行为逐字节回到接线前 |
| 3 | **不确认就不算发出去，且绝不重试** | 只有 `sent`/`sent_unconfirmed` 算 ok；`skipped`/`blocked`/`failed`/`partial`/`pending_approval` 都算失败并带回原因。重复发送率必须是 0 |

**四种 fallback（`handled=False`，退回旧路，只写一条日志）**

- 平台不在 `BRIDGE_PLATFORMS`（今天只有 `wechat`）；
- 注册表里没有这个平台的适配器、或它**没被启用**——没启用不等于发不出去，旧路还在；
- 投递种类不在适配器自报的 `kinds` 里（微信今天只自报 `say`，所以**文件与图片仍走旧路**）；
- 新出口内部抛异常（新路炸了不该让回复发不出去）。

**为什么放在网关而不是 `rhythm.py`**：`rhythm` 只是多气泡拆分器，返回 `None` 时调用方还要
再发一次单条；它只覆盖 5 个调用点里的 1 个（§5.5）。

**仍未做**：判侧 `deliver` 自己走的是 `core/speech/delivery.deliver`（另一条路），两条路今天
还没合并成一条；`artifact` 的 `card`/`page`/`link` 形态也还没有渲染器。

## 5.7 交付形态：一段话可以是卡片 / 页 / 链接 / 文件（U-16，2026-10-21）

一段 `.md` 的正文发到手机微信里基本没法看；一张图能看，但图里的字不能再编辑。
所以**交付形态**不是排版偏好，而是决定这条消息有没有用的东西——实现是 `core/artifacts/render.py`。

| 形态 | 出口看到什么 | 消息里带什么 | 谁生成 |
|---|---|---|---|
| `text` | `DeliverItem(kind="say")` | 正文本身 | 判 |
| `link` | `DeliverItem(kind="say")` | 就是一个 http(s) 链接（不做短链、不加引流语） | 判/工具 |
| `card` | `DeliverItem(kind="file")` | ≤40 字伴随语 + 一张 PNG（420 宽，最多 3 页） | 本层（PIL） |
| `page` | `DeliverItem(kind="file")` | ≤40 字伴随语 + 一页 `.md` | 本层 |
| `file` | `DeliverItem(kind="file")` | ≤40 字伴随语 + **已存在**的本地文件 | 别人给的 |

**四条纪律**

1. **纯函数在前、落盘在后**：`render_card_png()` 只返回字节，`write_card()` 才写盘——测试因此不碰临时目录。
2. **有界**：卡片正文 ≤ `MAX_CARD_CHARS`（1200 字）、页 ≤ `MAX_PAGE_CHARS`（20000 字）、卡片最多 3 页；
   超了截断并**如实标 `truncated`**，不静默丢内容。
3. **文件名可预测且安全**：`<时间戳>-<slug>.png`，slug 只留中英文数字；同名不覆盖（后缀 `-2`）。
4. **`file` 不认不存在的路径**：`to_deliver("file", path=…)` 对不存在的文件直接抛——不许伪造一个路径出去，
   让出口里出现「已发送但其实没有东西」。

**今天它接上了吗**：没有。`core/artifacts/` 是纯产出层，出口注册表里目前只有微信适配器，
它自报 `kinds={say}`，所以文件类投递会得到 `skipped(reason=unsupported_kind)`——
**这是如实的结果，不是本层的失败**。要真发文件，需要微信那条路的 `kind=file` 落点（另立切片）。

### 5.8 改口（更正）也走出口（U-26，2026-10-21）

说错了要能改。更正**不是新结果态**——它就是一条普通消息（`kind=text`），只是措辞带前缀、且可能先撤回上一条。

收口在 `core/speech/correction.py`：

| 函数 | 作用 |
|---|---|
| `correction_mode()` | 唯一读点：`features.CORRECTION`（三态，默认 `off`） |
| `correct(receipt, fix, *, deliver=None, revoke=None, ledger=None, recorder=None, chat_id="", turn_id="", now=None, mode=None) -> CorrectionResult` | 从一条已发回执生成改口；`mode=off` 直接拒 |
| `correct_ref(ref, fix, ...)` | 只知道回执号时先查 `delivery_receipts.find_ref(ref)` |

四条 fail closed（任一条不成立就一个字节都不发）：没有原回执 / 没有 `ref` / 改口为空 → `no_receipt` / `no_plan`；
原文已经是更正（`更正：…`）→ `already_corrected`（不许连环改口）；没有投递通道 → `no_plan`；`mode=off` → `off`。

窗口内（`can_revoke`，120 秒）**先撤回再改**；撤回失败不阻断更正（人需要的是一句正确的话，撤回只是顺手止损）。
状态三种：`corrected` / `revoked_and_corrected` / `shadow`（算出来但不发）；理由名 `off` / `no_receipt` / `no_plan` / `already_corrected` / `deliver_failed`。

出口**没有新增结果态**：更正发出去仍是六种里的 `sent`；它自己的账在 `CorrectionResult.receipt`（`ref` 指向原条），
由调用侧交给 `record_delivery_receipt` 落 `delivery_receipts`。它也能当「在手的事」里的一步：
`correct:<回执号>|<改口>`（见 `办_在手的事.md` §18.1）。

### 5.9 接管第一个调用点：`owner_ask`（U-33，2026-10-21）

R3 要真正成立，缺的不是「新出口能发」，而是**旧调用点一个个让位**。第一个选
`core/execution/owner_ask.py`（最窄、只有一处 `gateway.send_text`），用来把套路定死：
**双跑对照 → 等价测试 → 删旧**。

三档（唯一读点 `owner_exit_mode()` 认 `DELIVERY_CONTRACT`）：

| 档 | 旧路 | 出口 | 结果听谁的 |
|---|---|---|---|
| `off` | 真发 | 一条不碰 | 旧路（行为逐字不变） |
| `shadow` | 真发 | `dry_run=True` 走一遍闸门，只记一行比对日志 | 旧路 |
| `on` | **一条不走** | 真发（`build_registry(enable=True)`） | 出口 |

两条不许破的纪律：

1. **`on` 档失败绝不回落旧路**——回落就是「失败重发」，重复发送率立刻不为 0；
2. **两档不许同时真发**——`send_owner_question()` 在 `on` 分支里 `return`，物理上到不了旧路。

比对日志一行就够判断要不要继续扩：

```text
owner_ask_exit mode=shadow chat_id=<会话> legacy_ok=1 exit_status=blocked exit_reason=adapter_disabled same_text=1
```

`exit_status=blocked / adapter_disabled` 是**正常**的：适配器登记但没启用。要看的是
「旧路成功而出口 failed」——那说明新出口在真通道上还发不出去，别急着把 `on` 打开。

### 5.9 影子档：一次覆盖所有调用点（2026-10-21）

上一节说「要验新出口能不能发，只能逐站点改代码」。实际上不必：**所有**发送都从
`OutboundGateway._send_text_or_file` 过，桥就在那里。所以给 `LEGACY_VIA_EXIT` 加中间一档：

| 档 | 旧路 | 新出口 | 传输归谁 |
|---|---|---|---|
| `off` | 真发 | 不调 | 旧路 |
| `shadow` | 真发 | `dry_run=True` 只走闸门 + 一行日志 | 旧路 |
| `on` | 不调 | 真发 | 新出口 |

影子档的硬纪律：**返回值一律 `None`**（桥不许接管传输），且桥里「非 `on` 且非 `dry_run`
直接退」——两道锁叠起来，影子档物理上发不出去。

要看的只有一行：

```text
legacy_exit_shadow platform=wechat target=<会话> kind=say handled=0 exit_status=failed exit_error=blocked:adapter_disabled
```

`handled=0 / blocked:adapter_disabled` 是**正常**的（适配器登记未启用）。要盯的是
`exit_status=ok` 出现得少、或出现 `deliver_failed`——那才说明新出口在这条真通道上有问题。

## 5.9.1 影子档必须报「回执原话」，不许把没走下去说成 failed（2026-10-21 真机）

第一次真机影子档（`LEGACY_VIA_EXIT=shadow`）日志长这样：

```
legacy_exit_shadow platform=%s target=%s kind=%s handled=%s exit_status=%s exit_error=%s
```

两个毛病，都属「日志在骗人」：

1. **`%s` 原样留在事件名里**：`core/speech/outbound.py` 的 `log` 是 structlog，只吃
   「一个事件名 + 关键字」，printf 位置参数被塞进 `positional_args` 而不插值。
   **规矩：structlog 一律先拼好字符串再交，不用 `%`。**
2. **`exit_status=failed` 是错的**：影子档 `handled=False` 是**设计**（不接管传输），
   译成 `failed` 会让量具把「正常」读成「故障」。改成一律打印**回执原话**。

状态词表（`BridgeResult.status/reason`，封闭）：

| 走到哪一步 | status | reason |
|---|---|---|
| 开关 off | `blocked` | `mode_off` |
| 影子档但没带 `dry_run` | `blocked` | `shadow_needs_dry_run` |
| 平台不在 `BRIDGE_PLATFORMS` | `blocked` | `platform_not_bridged` |
| 没注册表 / 没这个适配器 | `blocked` | `no_registry` / `no_adapter` |
| 适配器登记了但没启用（**今天微信就是这个**） | `blocked` | `adapter_disabled` |
| 种类不在自报 `kinds` 里 | `blocked` | `kind_unsupported` |
| 自报能力炸了 | `blocked` | `caps_failed` |
| 走到闸门、`dry_run` 放行 | `skipped` | `dry_run` |
| 桥内异常 / 没拿到回执 | `failed` | `bridge_exception` / `no_receipt` |
| 真发（`on` 档） | `sent` / `sent_unconfirmed` / … | 平台原话 |

判据：`l0_glance` 的 `SHADOW_BAD_STATUSES = ("ok", "deliver_failed")` ——
`adapter_disabled` **不该**报警，它是「今天还没让它发」的正常状态。

## 5.13 一条消息只落一行回执（2026-10-21 真机）

真机第一次把私聊交给新出口（`WECHAT_SEND=on` + `DELIVERY_CONTRACT=on` + `LEGACY_VIA_EXIT=on`），
两条都发成功、都在 `delivery_receipts` 里有真回执（`ack=platform_id`、`local_id`/`server_id` 俱全），
但每次发送都多一条 `delivery_receipt_record_failed adapter=text`。两个 bug：

| # | 症状 | 根因 | 修法 |
|---|---|---|---|
| 1 | 出口那行回执从来没写进去，只留一条 warning | `core/speech/receipts.py::build_receipt` 交出去的是 **`Receipt` 对象**，`core/terminal/delivery_receipts.py::record_receipt` 里却直接 `receipt.get(...)` → `AttributeError` 被 `except` 吞掉 | `record_receipt` 入口先过一遍 `_as_mapping(receipt)`（对象与 dict 都收），签名改 `receipt: Any` |
| 2 | 若 bug 1 修好，每条消息会落**两行**回执 | 桥接管时 `wechat_send._record` 已经写过一行（带 `ref=wechat#<local_id>`），出口再写一行 `ref=""`，唯一索引 `(turn_id, kind, ref, target)` 拦不住 | `OutboundGateway._record_delivery_receipt(..., skip=bridged is not None)`：新出口自己发的，出口不再记账 |

**为什么这条不是洁癖**：`duplicate_rate = duplicate / sent` 是我们唯一的重复发送量具
（`docs/decisions/出口.md` §12）。用自己的重复记账把它从 0 抬到 50%，等于把量具调坏——
以后真的重发了也看不出来。

**纪律**：一条消息在账上只应有一行回执；两行必须是两个真实事件，
不许是两条代码路径各记了一次。
