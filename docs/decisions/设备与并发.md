# 设备与并发：真的动手之前

> **状态（2026-10-21）**：v0.1 设计定稿，**零实现**。
> 本文不是「计划」，是「闸门」：任何会让电脑自己动手的代码（点、打、发、撤、拖、填），
> 在合入前必须能指出它守住了本文的哪几条；说不出就不许合。
> 位置：**横贯四块板**——#9 出口（发什么）、#10 软件·适配器（有哪些通道）、#11 工具包（有哪些工具）、#12 在手的事（做什么）；
> 它本身不对应图上任何一块板，所以坐标校验里没有它。

## 0. 为什么这份文档重要

这份文档管的是**「设计」与「世界」之间那道缝**。前面十六份文档回答「应该是什么样」，这一份回答「真的按下去会发生什么」。

它重要，是因为它守的三类事故都是**不可撤销**的：

1. **发错人**：把 A 的话发进 B 的会话。消息一旦出去，撤回有时间窗、对方可能已经看到。
2. **重复发**：同一句话发两遍。技术上只是重试，观感上是"她不对劲"。
3. **锁屏误发**：电脑锁屏/切用户时，按键进到登录框或别的应用里。这是唯一可能**污染系统本身**的一类。

还有第四类，更隐蔽：**假活**——开关打开了、日志写着 on、实际什么也没接上。它不会报错，只会让人以为这块有了。

**谁能改**：只有人。改本文任何一条，必须同时改 §13 的放行判据与相应检查器；只改代码不改这里，视为未完成。

**它和别的文档怎么分工**（避免同一件事写两处）：

| 问题 | 归谁 |
|---|---|
| 该不该开口、说什么 | `判投记.md`、`出口.md` |
| 有哪些通道、每种的边界 | `软件适配器.md` |
| 有哪些工具、各自的效果等级 | `工具包.md` |
| 一件事做到哪一步、谁能批准 | `办_在手的事.md` |
| **怎么把手放上去、放多久、失败怎么办** | **本文** |

**怎么落实**：见 `docs/设备与并发_实施手册.md`（六步施工单 / 签名 / 断言清单 / 验收命令 / 故障对照表）。本文写「为什么与判据」，手册写「第一步做什么」。

**违反它的后果**：不是"体验差一点"，而是"系统在无人看管时做了不可撤销的事"。所以本文的默认值是 `blocked`，不是"尽力而为"。

## 1. 五条真实约束（都有实测，不是假设）

| # | 约束 | 实测依据 |
|---|---|---|
C1 | **只有一只手**：OS 输入是全局单例，光标只有一个、`SendInput` 进同一条系统队列 | `core/execution/wx_human.py` 全仓唯一 SendInput 出口 |
C2 | **只有一个前台**：键盘事件打到当前前台窗口；锁屏/切换用户时前台不是微信 | 真机：窗口最小化到托盘时 `GetWindowRect=(-21333,-21333,...)`、`IsIconic=True` |
C3 | **平台延迟不可压缩**：微信消息落盘平均 26 秒；撤回只在约 120 秒内可用 | 真机：`local_id=87` 发送后 26 秒才出现在库里；右键菜单 2 分钟后没有「撤回」 |
C4 | **能力是脆的**：Qt 自绘控件、独立顶层弹窗（`Qt51514QWindowToolSaveBits`）、UIA 名缺失、DPI 缩放、UIPI 完整性级别 | 真机：@ 名单在独立窗口；venv 被降到 Low 后 16/29 条测试红 |
C5 | **真人和我们共用同一个账号**：用户随时会自己发消息、自己切会话 | 用户自己也用这个微信号，`is_sender=1` 无法区分谁发的 |

C1/C2 决定了「必须串行」；C3 决定了「不能等」；C4 决定了「随时可能失效」；C5 决定了「不能只信数据库」。

## 2. 总纲：三个回合，一句不变式

```
① 扫描回合   scan_once()      无锁 / 无模型 / 只读 / 节流 ≥1s
   微信未读（库） + 全屏分区截图 + 同进程顶层窗口枚举 + CDP 多 tab
   → ElementTable（绑窗口代次）+「有事发生」清单

② 决策回合   plan_round()     模型，全局并发 ≤2，按会话合并
   → ServiceRound：一个会话的一串动作（回话 / 撤回 / 标已读）

③ 服务回合   DeviceWorker     独占资源，按截止时间排序，一次打开干完多件
   acquire(target) → check → 动作 → check → release → 回执
        └ 证据与对账：锁外旁路，只读，不占手
```

**一句话不变式**：**看可并行，动必独占；切要合并，丢要记账；世界是主，日志是仆。**

为什么是三个回合而不是一个：一个回合里同时做"看、想、动"，就没法在"动手前最后一刻"再确认一次世界；拆开之后，"确认"才有一个明确的时刻。

## 3. 十二条法则（每条都带反例）

1. **按不可逆性定价**：可逆动作（读、查、打字、草稿、跳转）用最便宜的判据；不可逆动作（发送、撤回、付款、@ 到人、删）用最贵的，且放在最后一步之前。
   反例：为了省 40ms 跳过回车前的顶栏校验——省的是 40ms，赔的是发错人。
2. **世界是主、日志是仆**：恢复、对账、判断一律先读世界（屏幕/前台/库），日志只用来提示"可能发生过什么"。
   反例：日志写"已粘贴"，重启后照日志再粘一次——重复发。
3. **确认点紧贴最后一步**：动作序列里只保留一次"关键确认"，位置在最后一步之前 10–30ms。此窗口内的残余风险**显式接受**并记录（§16）。
4. **一段动作只用一种资源，或一次性取全**：不要"先拿 A 再等 B"。
   反例：任务甲拿 `input` 等 `page`，任务乙拿 `page` 等 `input`——死锁。固定顺序也不够，必须 all-or-nothing。
5. **状态机收敛，禁止自由组合**：任务只有 §6 表里那些状态与迁移；组合维度（资源×目标×元素表×预算×确认）由状态机承载，不允许自由交叉。
6. **丢弃必须记账**：任何"看到但没做"都要留一条原因，无记录的丢弃视为事故。
7. **失败要快，成功可以慢**：`fail-closed` 必须在动手前出结论；"发出去没有"的确认走异步，不占锁。
8. **为未来留接缝，不为未来付成本**：今天单消费者，但设备入口、资源获取、阈值、触发源、量具五处留接口；不预写调度器。
9. **能机器检查的写进检查器，检查不了的写进演练**：静态规则（谁可以按回车）进 `scripts/check_topology.py`；时序与恢复进故障注入。
10. **降级要有一句人话，且有频率上限**：内部状态码（`input_busy` / `no_target` / `human_active`）绝不进聊天文本。
11. **自己的行为必须能和别人的行为区分**：回执靠"文本指纹 + 时间窗 + 每会话自增行号基线"三重匹配；只有 `is_sender=1` 不算证据（C5）。
12. **假设必须标记**：没被标记的假设就是未来的 bug。所有未实测的数值集中在 §14，并在配置里带 `# 假设，未校准`。

## 4. 资源与租约

### 4.1 资源表

| 资源 | 谁需要 | 生命周期 | 说明 |
|---|---|---|---|
`input` | OS 级输入（`SendInput`/`mouse_event`/按键） | TTL 60s + `hard_ttl` 120s（**不可续期**） | 全局唯一；持有时必须前台正确 |
`page:<tab>` | CDP 页面动作（合成事件、`insertText`） | TTL 300s | 不要求前台；可与其他会话的页面动作并行 |
`screen` | 全屏截图 | 单次（≤2s） | 不与 `input` 互斥；但**不能**当作 CDP 动作的证据 |
读（库/UIA 树/无副作用读取） | 扫描回合 | 不占资源 | 只读不排队 |
证据（`evidence`） | 落盘截图/回放帧 | 60s | 与 `input` 同持有者时自动具备 |

**判定方式**：由工具自己声明 `needs`（`ToolSpec` 里加字段），**不按平台猜**。
反例（真实风险）：CDP 的 `insertText` 在 `contenteditable` 上可能被忽略而退回 OS 键盘——那一瞬间它就需要 `input`。所以"CDP 不需要 input"这句话只在**具体工具路径**上成立。

### 4.2 获取与释放

- **all-or-nothing**：动作开始时一次性取全部所需资源，取不到就整体放弃并重试；不允许"拿一半等一半"。
- **不嵌套**：一个动作块内只出现一种资源。
- **跨进程**：`data/.locks/<resource>.lock` + `msvcrt.locking` 真互斥；持锁方每 5s 心跳。**真机实测（2026-10-21，`scripts/lease_probe.py`）**：① 崩溃由系统立刻回收（kill -9 后毫秒级可接管，**不用等 TTL**）；② **活着的持有者抢不动**——同一个文件区间锁还被它的句柄占着，`hard_ttl` 到期也只能在「锁已空闲（进程死了但状态没清）」时才接管。所以真正的兜底是 `wait_s` + fail-closed + 心跳日志；要抢占活着的持有者只能杀进程（kill switch 属另一机制，未做）。
- **等不到怎么办**：等待上限 8s（动作本身 ≤2s），超时 `blocked(input_busy)`，并**用一句人话告诉她/他**"另一个任务正在动手"，不是静默失败。

### 4.3 动手前的六项能力自检（失败即 `blocked(capability)`）

1. 进程与目标窗口的**完整性级别**：`integrity(target) <= integrity(self)`（UIPI 否则静默丢事件）
2. **会话状态**：`WTSQuerySessionInformation(WTSConnectState) == Active`，且 `OpenInputDesktop` 成功（锁屏即失败）
3. **DPI 一致性**：进程 Per-Monitor-V2 感知；断言 `UIA 矩形 ≈ win32 矩形`（我们验过 1.0 时相等）
4. **窗口身份**：类名 + 顶栏指纹匹配预期
5. **可写性**：输入框能读到、能写入后读回
6. **界面版本**：菜单项集合包含预期项（微信升级/换肤会变）

### 4.4 真人优先（让位）

扫描回合读 `GetLastInputInfo`：真人输入距今 <3s → 所有自动化动作 `blocked(human_active)`，只保留只读。理由：用户在用电脑时，任何自动按键都可能进错地方。

### 4.5 停止语义（kill switch）

- **安全点**只有五个：`S1 打开完成 / S2 聚焦完成 / S3 粘贴完成 / S4 回车（原子，不可中断）/ S5 校验完成`。
- 停止请求只在安全点生效；`S4` 一旦开始必须走完（半按回车比不按更糟）。
- kill switch 必须能"立刻停止领取新任务"，而不是"立刻杀进程"。

## 5. 目标与元素表

### 5.1 目标（CurrentTarget）

```
platform, handle, pid, exe, title, rect,
identity（会话/标签的身份）, fingerprint（顶栏/网址指纹）,
generation（每次成功切换 +1）, owner（谁持有的任务）, verb, since
```

- `generation` 是**乐观并发**：动作开始时记住代次，动作前比对；不一致 → `blocked(window_changed)`，零副作用。
- 目标必须由**证据档位**决定（`explicit > anchor > ocr > recent_db > none`），`recent_db` 只说明"最近有消息"，不说明"屏幕上是哪个会话"。

### 5.2 元素表（ElementTable）

```yaml
name: "发送"          # UIA Name / DOM 文本 / OCR 文本
role: button          # button / listitem / edit / menuitem
rect: [x, y, w, h]    # 屏幕绝对坐标（不是窗口内）
source: uia           # uia > dom > ocr
window: 527494        # 它属于哪个顶层窗口 —— 独立弹窗靠这个字段活着
confidence: 1.0
```

四条纪律：

1. **抓全屏，不裁主窗**：@ 名单、右键菜单、输入法候选都是独立顶层窗口，裁主窗永远看不到。
2. **三源合并，UIA 优先**：UIA 有 role + 精确矩形；OCR 只补 UIA 看不见的自绘控件。
3. **唯一性分档**：不可逆动作要求 `unique()`（0 或多于 1 → `no_target`）；可逆动作允许"排序取第一 + 记录理由"。
4. **按窗口分代次**：任一窗口移动/切换/关闭，该窗口的表作废；不可逆动作前**重扫目标窗口**（~100ms），可逆动作才信任旧表。

### 5.3 坐标与隐私

- 一律**虚拟屏幕绝对坐标**（多显示器可为负值）；DPI 变化必须重算，不允许缓存跨 DPI 的坐标。
- 截图**默认不落盘**：只有不可逆动作留一张，保留 7 天，纳入清理任务；需要时支持打码区配置。

## 6. 状态机（唯一合法迁移）

| 当前 | 事件 | 下一状态 |
|---|---|---|
`queued` | 取到资源 | `running` |
`queued` | 截止时间已过 | `expired` |
`queued` | 人取消 | `cancelled` |
`running` | 需要批准 | `awaiting` |
`running` | 动作全部成功 | `done` |
`running` | 动作失败 | `failed` |
`running` | 前置检查不过 | `blocked` |
`running` | 超时 | `expired` |
`awaiting` | 人批准 | `running` |
`awaiting` | 人拒绝 | `cancelled` |
`awaiting` | 批准超时 | `expired` |

- 终态（`done/failed/cancelled/expired/blocked`）**不可复活**；要继续就新建一件新的事。
- **`awaiting` 不占"同会话在飞"名额**：否则一件等批准的事会让她在群里不再说话。
- **追加语义**：同一会话在 30s 窗内到达的新消息，追加进当前 `ServiceRound`（标记 fresh），不新开回合；冲突内容（"订票"与"别订"）以最后一条为准并允许追问。

## 7. 恢复（世界优先）

### 7.1 三读顺序

动作被打断后，**不许按日志重放**；只允许：

1. 读**输入框**（有无残留文本、是否等于上次草稿）
2. 读**顶栏**（还是不是那个会话）
3. 读**库**（该会话有没有新行、文本指纹是否匹配）

三者对齐后的唯一合法结论：

| 输入框 | 库 | 结论 |
|---|---|---|
等于草稿 | 无新行 | 只补按回车（`S4` 重做一次） |
空 | 有新行且指纹匹配 | 已完成，补写回执 |
空 | 无新行 | 没发生，可重试（记一次 attempt） |
有别的文本 | — | `blocked(composer_dirty)`，先清空再决定，绝不覆盖别人的字 |

### 7.2 自己的 vs 别人的（C5）

回执判定三重匹配，缺一不可：**我们发出的文本指纹** + **发送后时间窗** + **该会话 `local_id` 基线之后的新行**。
只有 `is_sender=1` 不算证据——用户也用这个账号。
外部新增行（不是我们发的）必须**更新基线但不产生回执**，否则"重复发送率"永远算不准。

### 7.3 重启

- 入队即落 `job_events(kind=queued)`，含 `deadline`；
- 重启后按 `queued` 重放，已过期 → `expired` 不执行；
- 落盘里的 `running` 一律降级为"待核对"，走 §7.1 三读。

## 8. 调度（**接缝，默认不启用**）

当前没有高并发需求，所以本节只定义接口与语义，**不实现排队**。

| 概念 | 语义 | 今天的样子 |
|---|---|---|
排序 | 有截止时间的按时间（撤回 120s 最优先），没有的按优先级 | 单消费者，直通 |
合并窗口 | 500ms 内同会话消息合成一批 | 收到即处理 |
配额 | **全局硬顶 60 动作/分钟**；每会话 20/分钟只是参考上限 | 不生效，只记账 |
饥饿保护 | 每 60s 至少放行一个低优任务 | 不生效 |
过载 | 队列上限 200，超出 `drop(overload)` 记账 | 不生效 |

**配额的算术事实**（必须写在实现旁边）：100 个会话 × 20/分 = 2000/分，远大于全局 60/分。所以**多数会话只能不回**——这不是缺陷，是算术；每会话配额永远不能突破全局硬顶。

## 9. 速度与安全

### 9.1 三档（由不可逆性自动判定，不做人工开关）

| 档 | 触发 | 行为 |
|---|---|---|
`strict` | 花钱、撤回、@ 到人、删除、给某人的第一条消息 | 每次验目标 + 截图留证 + 幂等键 + 人确认 |
`normal` | 默认（已有会话发消息、办事的只读步） | 验目标 + 值比对，不留截图 |
`fast` | 纯读（读屏、查询、草稿、闲聊回应） | 不占手、不验目标、不留证据；**永远不允许发消息** |

### 9.2 人确认

- 一次确认 ≈ 一个回合（3–6 秒），只用在 10% 不可逆动作上。
- 三档授权：`read` 自动 / `write_local` 可用 grant（问一次管 30 天）/ `external_send` **永不 grant**，每次都要人。
- 确认请求本身有截止时间：超时 `expired` 并告诉她"来不及了"，不留悬空请求。
- 只有**本人私聊**算数：群里第三人说"订"不算授权。

### 9.3 证据分级

| 动作来源 | 证据方式 |
|---|---|
OS 级动作（微信/原生） | 全屏截图（前后各一张，命名含 `turn_id` 与 `before/after`） |
CDP 动作 | `Page.captureScreenshot`（**不能**用全屏，浏览器可能在后面） |
只读动作 | 只记摘要指纹，不留图 |

### 9.4 量具（先于功能落地）

`input_wait_ms` / `preempt_count` / `dirty_composer_cleared` / `starvation_skips` /
`blocked_capability` / `lease_stuck`（第六项，2026-10-21 加：**心跳年龄 > 2×TTL 才算卡死**——
进程一死 OS 立刻回收锁，所以等不到手通常意味着持有者还活着，要靠心跳区分「排队」与「事故」）
外加 `unique() 失败率`、`回执三重匹配失败率`、`降级话术触发次数`。

**缺口（诚实）**：这些量具都测"快不快、稳不稳"，测不出"做对了吗"。后者只能靠**每天抽 N 条回执人工核对**。

### 9.5 周报：把量具算成一张纸（U-29）

量具在进程内存里，看过就没了；回执和事件在库里，但没人会去 join。周报把两边收成一张纸：

```text
.venv_it\Scripts\python.exe -X utf8 -m scripts.weekly_report            # 打印
.venv_it\Scripts\python.exe -X utf8 -m scripts.weekly_report --json     # 机器看
.venv_it\Scripts\python.exe -X utf8 -m scripts.weekly_report --days 30 --out data/weekly.md
```

五节：发生了什么（回合数 / 决定分布）、说不说与指不指得回（弃权率 / basis 覆盖率）、
发得对不对（回执状态 / 越权被挡率 / 重复发送率）、手有没有被卡住（锁等待 p90 / 僵死 /
能力阻断 / 脏输入框清理）、事有没有办完（done / awaiting / 交接出去）。

两条口径纪律：

1. **`未采集` ≠ `0`**：查不到（库没开、表不在、列变了）写「未采集」；查得到但空表写「0」并注明
   「这一周 0 条」。混成 0 会让「她从不弃权」这种结论凭空出现；
2. **报表只读**：用 `db.write_guard.read_only_engine()` 拿只读句柄，绝不走可写 engine
   （生产路径上会被 `ProductionWriteRefused` 拦住，**这是对的**——报表不该有写权限）。

已知局限（必须写在纸上，不许藏）：进程内量具重启清零，跨周比较要看日志；`TURN_TRACE=off`
时弃权率恒为「未采集」；重复发送率依赖出口真的落了 `duplicate` 回执。

## 16. 明确不做，以及接受的风险

**不做**：取号排队（瓶颈是吞吐不是争抢）、跨进程共享"当前会话"（省 1.5s 换错发风险）、`foreground` 独立资源（与 `input` 合一）、鼠标位置复位、多线程 worker、动作中途"回滚世界"（只做清理）、为假想的高并发预写调度器。

**接受的风险**（写下来，不假装解决）：

1. 确认与回车之间 10–30ms 的窗口：概率极低，不为零。
2. 微信行为风控（封号）：只能限速、拟人、失败即停，**不能保证不被封**。
3. 平台落盘延迟：只能异步，不能消除。
4. 租约不是安全边界：静态白名单只防"无意绕过"，不防"恶意绕过"。
5. 没有真实高并发场景：B 类数字靠合成流量近似，C 类（人类行为）无数据。

## 17. 附录：被正文压成结论的推导

正文为了能扫读，把几处推理写成了结论。细节原文收在这里，**正文与附录冲突时以附录为准**（附录更细）。

### A. 人类怎么对付「4 个窗口但只能动 1 个」→ 三个回合的由来

| 策略 | 人怎么做 | 落到哪 |
|---|---|---|
先看全再决定动哪个 | 扫一眼四格（红点/闪动/安静），一次看省三次切换 | 扫描回合不占资源，读可并行 |
不占手的活干完 | 心里起草、算账、查资料不占鼠标键盘 | 决策在锁外，只有最后一下占手 |
一次只服务一个窗口，服务完再走 | 切窗成本远大于在同窗多做一件事 | `ServiceRound` 合并同会话动作 |
打字到一半不切 | 打完这句、发出去，再切；切走前清输入框 | 五个安全点 S1–S5 |
有截止时间的先做 | 撤回只剩 40 秒 > 老板问话 > 群聊 | 截止时间排序（EDF），不是静态优先级 |
留便签不靠脑子记 | 「回 A 群：可以，明天」 | `job_events(awaiting)` + `CurrentTarget` |
能委托就不自己干 | 能邮件就邮件、能电话就电话 | 通道优先级 API > 推送 > UI |
高峰降质 | 先回「稍等」，完整回复留到空了说 | `skip` / 短回复档 + 配额 |
承认容量上限 | 手速 1–2 次/秒，丢得体面 | 全局 60 动作/分硬顶 |

结论不是「造更强的并发框架」，而是**把「动」的次数压到最小，并让「不动」也有记录**。

### C. 容量算术链（推算式，待 §14 校准）

```
17 条/s 入站
  → 500ms 合并窗 → 约 6 批/s
  → 模型并发 2 → 每批 1 次调用 → 队列单调增长（必须作为可观测指标，超 200 降级丢弃）
  → UI 物理 1–2 动作/s → 全局硬顶 60 动作/分
  → 100 个会话 × 20/分 = 2000/分 ≫ 60/分 → 多数会话只能不回
```

这不是妥协，是算术：**任何"每会话配额"都不能突破全局硬顶**。

### F. 八道关口具体怎么注入

1. **状态机穷举**：§6 迁移表逐条正测 + 非法迁移逐条负测（必须拒绝）。
2. **故障注入 200 次**：动作前 / 粘贴后未回车 / 回车后落库前 / 切换中途，各 50 次；每次断言「重复发 0、错发 0、能恢复」。

6. **会话安全**：锁屏 / 切换用户 / 拔显示器 → 必须 `blocked`，零按键。
7. **降级话术**：8 种状态各一句人话 + 频率上限。
8. **kill switch**：停领新任务 + 在安全点生效。

### H. 假活（开关 on 了但没接上）怎么查

启动时打印「生效矩阵」：每个开启的开关 → 它真正被调用的函数/表。未接上必须醒目警告。
已知依赖：`JOB_LEDGER=on` 需块已登记进 `core/context/assembler.py::_BLOCK_POLICY`；`WECHAT_SEND=on` 需 `WECHAT_UI=on`；`SENSORY=on` 需屏幕捕获能力可用。

### I. 为什么「回车」必须原子不可中断

`S4` 之前做最后校验，`S4` 内部是 keydown + keyup 成对。中断在中间会留下「按下未抬起」或「输入框已清、消息未出」，恢复代价远高于等 30ms。所以停止请求在 `S4` 期间排队，到 `S5` 再生效。

## 19. L0 只读观察期（7 天，怎么判）

L0 的定义在 §13（只读、不阻断推进）。观察期靠一个脚本收敛，不靠记性：

    .venv_it\Scripts\python.exe -X utf8 -u scripts/l0_glance.py

它做三件事：

1. 扫 `logs/*.log`（JSONL）数七个信号：`device_guard_shadow` / `input_busy` / `lease_stuck` /
   `dirty_composer` / `blocked_capability` / `correction` / `legacy_exit_shadow`（第七个，2026-10-21 加，
   另统计 `exit_status` 分布）；
2. 看残留租约：`data/.locks/*.json` 中心跳超过 120 秒的（= 可能卡死），把 `pid` 打出来；
3. 给结论：`lease_stuck > 0` 或残留租约 → 「先查 pid 再谈升级」；`blocked_capability > 0` → 「先修探针」；
   影子档出现 `exit_status=ok` 或 `deliver_failed` → 「先查为什么放行」（见 §19.3）；
   天数不足 → 「还差 N 天」；全正常且满 7 天 → 「L0 通过，可进 L1」。

到期日写在脚本常量 `DUE_DATE = "2026-10-27"`，过期会打印「该看了」。

### 19.1 放行闸：L0 → L1 → L2 是同一张表（U-31）

`l0_glance.py` 判「观察期过没过」，`stage_gate.py` 判「这一级能不能放行、下一级要做什么」。
两级判据写在同一处，才能避免「感觉差不多了就升档」：

```text
.venv_it\Scripts\python.exe -X utf8 -m scripts.stage_gate                     # 判 L0
.venv_it\Scripts\python.exe -X utf8 -m scripts.stage_gate --level L1 --since 2026-10-27
.venv_it\Scripts\python.exe -X utf8 -m scripts.stage_gate --json --out data/stage.md
```

| 级 | 放行条件（全满足） |
|---|---|
| L0 只读 | 观察 ≥ 7 天；`lease_stuck` / `blocked_capability` / 残留租约都为 0；`input_busy` 每天 ≤ 5 次 |
| L1 自己给自己发 | ≥ 7 个不同日期、≥ 20 条（只算 target 命中「文件传输助手 / 自己的号」）；`duplicate` 0；`failed` ≤ 2%；`unconfirmed` ≤ 20%；L0 的七信号仍干净 |
| L2 测试群单条 | 群里每天 1–2 条，**人抽检 ≥ 98%**（脚本不判这条，人在纸上签字） |

三条口径纪律（与周报一致）：

1. **未采集 ≠ 0**：回执读不到（库/表/列缺失）或分母为 0，写「未采集」；
2. **只算发给自己的**：L1 的分母是 target 命中的那批行，群聊行一律不进分母——否则「发群里练手」会伪装成 L1 通过；
3. **一票否决优先于天数**：`lease_stuck` / `blocked_capability` / 残留租约任意一个非 0，直接「停」，天数再够也不放行。

判定优先级与 `l0_glance.verdict` 一致：**停 > 修 > 等 > 过**。

### 19.3 影子档的判据（2026-10-21 追加）

`legacy_exit_shadow` 每天被数一次；`exit_status` 的分布单独统计，因为**正常与异常在分布上分得开**：

| 分布 | 含义 | 动作 |
|---|---|---|
| 绝大多数 `blocked:adapter_disabled` | 闸门在拦——正常 | 不动 |
| 出现 `ok` | **闸门放行了**（`WECHAT_SEND` 被打开过？） | 压成【修】，先查为什么放行 |
| 出现 `deliver_failed` | 新出口在真通道上炸了 | 压成【修】，先别翻 `on` |

优先级：卡死（【停】）> 能力不足（【修】）> 影子档异常（【修】）> 天数不够（【等】）> 通过（【过】）。
