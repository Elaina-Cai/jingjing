# 在手的事（一件事 · 四槽 · 等批准才动手）

> 依据：`output/3d/viewer_css.html` 里 `(620, -300, 1000)` 那块板（贴图 `t_job.png`，板面写着「在 手 的 事 / 一件事 · 四槽 / 目标 · 步骤 · 安全点 / 只由判推进，等批准才动手」）。
> 四问先答：**图上是哪块** = 出口板 `(620, 0)` 正下方那块；**进来什么** = 判的提案（`plan`）/ 出口的逐条回执 / 人的批准；**出去什么** = 一行 job（append-only）、一行读数（进下一回合的判）、一条**已批准**的动作（送出口）；**职责** = 记住「一件事办到哪一步了」，不判断、不说话、不自己发东西。

## 1. 图上位置

- 板子：`addBoard(300, 220, 620, -300, LLM_Z, 't_job.png', '在手的事')`，在出口板正下方。
- 三条管子：

| 管子 | 端点 | 方向 | 含义 |
|---|---|---|---|
| `job 读数 / advance()` | `[280, 200, LLM_Z]` → `[470, 300, LLM_Z]` | 双向 | 判读「办到哪了」，判推进「下一步」 |
| `只送已批准` | `[620, 190, LLM_Z]` → `[620, 110, LLM_Z]` | 单向 ↑ | 只有带批准的动作才进出口 |
| `任务预算` | `[770, 330, LLM_Z]` → `[950, 320, 280]` | 单向 ↘ | 一件事的工具次数上限（跨回合累计） |

> **坐标口径（踩过的坑，v0.2 修）**：`addBoard(w, h, x, y, z)` 的 `y` 是**世界坐标（向上为正）**，渲染成 `translate3d(x, -y, z)`；而 `addPipe3D([x, y, z], ...)` 的 `y` 是 **CSS 坐标（向下为正）**。同一块板 `y = -300` 在画里落在 CSS `+300`。接线时必须按 CSS 口算：判板 `x, y ∈ [-280, 280]`；出口 `x ∈ [470, 770], y ∈ [-110, 110]`；在手的事 `x ∈ [470, 770], y ∈ [190, 410]`；工具包线框立方体以 `(950, 600)` 为中心、半边长 280、近面 `z = 280`、`y ∈ [320, 880]`。v0.1 的三条管子照世界坐标写，于是整段悬在板上方（业主肉眼发现）；v0.2 按上表改正，并由 `tests/test_job_wiring.py` 十项断言钉住。

- 与**出口**的区别：出口是「把一句话 / 一个文件送出去」，一次投递（≤2 条、回合内、幂等）；在手的事是「把一件事办完」（跨回合、有步骤、有等批准）。出口不认识 job，它只收到一条**已经带批准的动作**。
- 与**账本**的区别：账本记**已经发生**的事实（append-only，唯一写入口在 ① 落屏）；在手的事记**还没发生完**的事（可推进、可取消，取消也追加一行）。job 不进 `terminal_events`。
- 与**工具包**的区别：工具包是「拿信息进来」的一次调用；job 是「什么时候该调第几次」的预算与步骤，工具包不持有状态。

## 2. 是什么 / 不是什么

**是**：一条 `job` 记录 + 一个可 diff 的方案文件（`data/jobs/<job_id>.md`）。它是系统里**唯一**表达「进行中」的地方。

**不是**：

- 不是第二个决策器——**判照旧是唯一模型点**；`advance` 是判每回合给出的一次判断；
- 不是任务队列 / 工作流引擎——没有 DAG、没有并行、没有失败编排，`steps` 是**线性列表**；
- 不是记忆——不进记忆立方体、不进常驻、不参与检索；
- 不是账本——不写 `terminal_events`，也不改变世界面；
- 不是「Plan-and-Execute」——判每回合重算，读 job 只是第 6 样输入。

## 3. 进来的是什么（三条）

| 输入 | 谁给 | 内容 | 预算 |
|---|---|---|---|
| **① 提案 / 推进** | 判 | `plan{goal, steps[], awaiting}` 或 `advance{job_id, done_n, next}` | 每回合 ≤1 次 |
| **② 回执** | 出口 | 逐条 `Receipt`（`status` / `ack` / `reason` / 平台号） | 与投递同数 |
| **③ 批准** | **人** | `approval{job_id, step_n, action_hash, who, channel, at, expires_at}` | 每步 ≤1 条 |

**批准只从人来**，而且只有**私聊本人**才算（群里第三人说「订吧」不算授权）。群里可以说「要不要我帮你订」，但**授权必须落到本人私聊**。

## 4. 出去的是什么（四条）

| 输出 | 谁收 | 形态 |
|---|---|---|
| **① 一行 job（追加）** | 自己（下一回合读） | `{job_id, state, goal, step_n, awaiting, updated_by}` |
| **② 一行读数** | 判（第 6 样输入） | `job_id · 目标 · 到第几步 · 在等什么`，**≤60 字** |
| **③ 已批准的动作** | 出口 | 一次投递的 `deliver` 项（`kind` 由出口注册表决定） |
| **④ 方案文件** | 出口（`kind=file`）/ 人 | `data/jobs/<job_id>.md`，可 diff、可改版 |

读数（②）是这块板存在的**唯一理由**：判无状态，每回合重算，唯一的跨回合连续性是这一行 ≤60 字。读数里必须带**已经问过 / 已经确认**的清单，否则会重复提问。

## 5. 四槽（这块板唯一的「结构」）

换一件事不该改骨架，只该换槽的取值。四个槽都是**数据形状**，不是新代码路径：

| 槽 | 字段 | 例 |
|---|---|---|
| **trigger** | `{kind: once\|cron\|condition\|event, expr, next_fire_at, enabled}` | `{kind: once}` / `{kind: cron, expr: "0 9 * * *"}`（每天 9 点提醒吃药） |
| **policy** | `{scope, condition, max_amount, expires_at, revocable, approved_by}` | `{scope: "订票:杭州→深圳 2026-11-02", max_amount: 1200, expires_at: "2026-10-30"}` |
| **artifact** | `{kind: text\|file\|card\|page\|link, renderer, ttl}` | `{kind: page, renderer: "itinerary"}`（出行程网页而不是 .md） |
| **handoff** | `{url, prefilled[], screenshots[], note}` | `{url: "https://www.12306.cn/...", prefilled: ["2026-11-02", "杭州", "深圳"]}` |

**判据**：凡是**动作形状已有**的任务（说、发消息、发文件、查、抓网页）→ 只加槽，属加法；凡是**引出新动作形状**的（点击、填表、付款）→ 必须先加槽，否则会以临时补丁的方式长进判或出口 = 架构腐蚀。

## 6. 安全点（断点恢复的唯一依据）

- 每一步声明 `safe_point: true | false`：**只有 `safe_point: true` 的边界可以中断**（发出去等结果、表单已提交、付款中 = 不可中断）。
- 进程被杀 / 超时 / 用户打断时，job 从**最后一个安全点**恢复，恢复率必须 **100%**（量具）。
- 恢复不许重放「不可中断」的那一步（否则就是下两单）。
- job 自己不带锁；同一 `job_id` 同一时刻只有一个推进者（`updated_by` 记是谁推的）。

## 7. 谁能改它（4.5）

| 谁 | 能改 | 不能改 |
|---|---|---|
| 判 | `goal` / `steps` / `step_n` / `awaiting` | 不能自己写 `approved_by` |
| 出口 | 只追加 `receipt` | 不能改 `steps`、不能改 `state` 为 done |
| 人 | 只能写 `approval` / `cancel` | 不能编辑 `steps`（要改就让判重提） |
| 时间 | 到期只置 `expired` | 不能推进 |

三个写者字段不相交 = 单写者纪律在 job 上的落法。

## 8. 三条硬红线

1. **不自作主张**：不可逆 / 花钱 / 涉及隐私的动作，没有本人的 `approval` 一律不调出口；这条比「办成」优先。
2. **不在群里说隐私或钱**：群里只出「要不要我帮你办」和公开事实；金额、证件、地址、订单号只走私聊。
3. **不绕过出口**：job 不持有平台通道，所有动作经 `出口 → 适配器`；job 也不许自己发消息。

### 8.1 三级授权（`core/jobs/policy.py`）

| 档 | 覆盖什么 | 凭据 | 没有凭据时 |
|---|---|---|---|
| `auto` | `read`（看一眼、查一下） | 无 | —— |
| `grant` | `write_local`（只动我们这一侧：写文件、记便签） | `Policy.approved_by` 非空 + 未过期 + 在 `scope` 内 + 不超 `max_amount` | 退化成 `confirm`（逐次点头） |
| `confirm` | `ui_control`（动别人的界面）、`external_send`（对外说话） | 一行 `Approval(job_id, step_n, action_hash)` | 停在 `need_approval` |

四条纪律：

1. **档位由 `effects` 决定，不由工具名决定**——改个名字绕不开档位。
2. **`grant` 默认不存在**：`approved_by` 空就是没人批过，一律按 `confirm` 走（默认拒绝）。
3. **人的逐次批准最硬**：某一步已被 `Approval` 盖过章，就不再看长期授权。
4. **授权只决定「要不要问」，不决定「能不能做」**：`external_send` 拿了批准也不许从执行器走，
   它只走出口注册表（R3）。

停下来时回执要说清卡在哪一档：`reason` ∈ `needs_grant` / `no_grant` / `grant_expired` /
`out_of_scope` / `over_amount` / `needs_confirm`。判据此决定怎么问（「要你点头」还是「授权过期了」）。

### 8.2 授权从哪来：人说一句（`core/jobs/approval.py::apply_grant`）

长期授权不是系统自己攒出来的，是**人说出来的一句话**。入口只有一条：私聊本人对着
一件在手的事说「这类事以后你自己办」。

| 说法样例 | 认不认 | 为什么 |
|---|---|---|
| 以后这类事你自己办 | ✅ | 有长期语义（`GRANT_TOKENS`） |
| 这类事以后不用问我 | ✅ | 同上 |
| 以后别问我，直接办 | ✅ | 「别问」+「直接办」 |
| 可以 / 好 / 行 | ❌ 走 `Approval` | 那是点头某一步，不是授权一类事 |
| 以后这类事不用问我了，先别办 | ❌ | 否定优先（`DENY_TOKENS` 命中即拒） |
| 群里第三个人说「以后你自己办」 | ❌ | 不是本人 |
| 对着 `ui_control` / `external_send` 说 | ❌ | `confirm` 档不接受一次性升级 |

四条纪律：

1. **一句话只给一件事授权**：同一会话有两件以上在用手的事，直接放弃并记 `grant_ambiguous`。
2. **授权同时是这一句的点头**：人正被问「要不要写这个文件」，说「这类事以后你自己办」
   = 这次也办 + 以后不问，所以同时落一行 `Approval` 把他从「在等」里解开。
3. **可撤销、会过期**：`revocable=True`，默认 30 天（`GRANT_TTL_DAYS`）；过期后自动退化成逐次点头。
4. **只升 `grant` 档，不升 `confirm` 档**：`external_send` 永远一次一句。

落库形状：`granted` 事件 → 投影把 `jobs.policy_json` 换成新 `Policy`；事件与 `Approval`
都写 `actor=human`。审计时能回答「这份授权是谁、哪句话、什么时候给的、什么时候过期」。

### 8.3 授权是能收回的（U-27，2026-10-21）

`revocable=True` 不是装饰：人说一句「以后别自己办了」「撤回授权」「还是问我吧」，
那张长期授权就**当场作废**，不用等 30 天。

| 环节 | 落点 |
|---|---|
| 判句 | `core/jobs/approval.py::parse_revoke_grant(text, *, is_private, speaker_id, owner, job, now) -> str` |
| 落库 | `record_revoke(job, *, store, who, reason)` → 追加一行 `grant_revoked`（`actor=human`） |
| 生效 | 投影把 `policy_json` 的 `expires_at` 钉到**此刻之前**，`grant_allows()` 立刻返回 `grant_expired` |
| 接线 | `core/routing/turn_pipeline.py::_job_tick`，与「点头」「授权」同一处、同一句话型判定 |

五道闸（任一条不成立 = 什么都不做）：

1. **私聊、本人说**（群里第三人说「别让他自己订」不算）；
2. 不超过 40 字（更长多半是新话题，交给判）；
3. **否定优先**：出现「不用撤回 / 别取消」这类说法一律不撤（`KEEP_TOKENS`）；
4. 必须有明确的收回语义（`REVOKE_TOKENS`：撤回/撤销/取消/收回 + 授权/权限，或「以后都问我」）；
5. 那件事上**确实还有一张有效授权**（撤一张不存在的票没有意义）。

三条纪律：

- **不猜**：同一会话两件事都还有效 → 一句都不撤（回空 + 记 `grant_revoke_ambiguous`）；
- **只动 policy，不动状态**：正在等批准的事仍然是「在等」，撤权不会替人把事推进或取消；
- **留痕**：事件里存撤掉的那张票（`policy`）与撤后的样子（`revoked_policy`）+ 撤的人 + 命中的说法，
  审计时能回答「谁、哪句话、什么时候撤的」。

### 8.4 办不下去时交给人什么（U-28，2026-10-21）

一路走不通就停下，但**停下不等于「抱歉我没办成」**。人接手需要三样东西，交接单只写这三样：

| 要回答的 | 写什么 | 不写什么 |
|---|---|---|
| 为什么停 | `没办完（这一步的工具预算用完了）：<目标>` | 不写「系统错误」这类黑话 |
| 走到哪 | `已经走到：第 2 步「write:行程.md」` | 不写「进度 60%」（没有分母） |
| 还差什么 / 你要动哪里 | 剩下步骤原文 + `handoff{url, prefilled, screenshots, note}` | 不写「请稍后再试」 |

哪些停因才交（`HANDOFF_STOPS`）：

| 停因 | 交不交 | 为什么 |
|---|---|---|
| `budget` / `turns` | ✅ | 预算或回合用完，剩下的只能人来 |
| `failed` | ✅ | 某步失败且停在安全点 |
| `no_executor` / `blocked` | ✅ | 我没有能做这一步的执行器，或被人为闸挡住 |
| `done` | ❌ | 办成了（那是 `done`，不在这里） |
| `need_approval` / `awaiting` | ❌ | **正在**等人，那有第六态回执（`pending_approval`）管 |
| `shadow` / `state` | ❌ | 一个是开关档位不是事实，一个是终态 |

三条措辞纪律（每条都有测试钉住）：

1. **不假装办成**——不出现「已完成 / 已办」；
2. **不假设人会接手**——不出现「我等你确认」（那是把球又踢回去）；
3. **一次一件**——`handed_off` 事件幂等，同一件事只交一次。

落点与三档：

| 项 | 落点 |
|---|---|
| 文本（≤400 字，三句结构） | `core/jobs/handoff.py::handoff_text(job, handoff, *, reason)` |
| 可交付的完整单 | `handoff_markdown(...)` → `write_handoff(...)` 落 `data/handoff/<job_id>.md`（出口当 `kind=file` 发） |
| 落库 | `handed_off` 事件（`reason` / `handoff` / `steps_left` / `text`），投影只换 `handoff_json`，**不动推进状态** |
| 三档 | `off` 一行都不算（默认）/ `shadow` 只算文本写日志 / `on` 才落事件 + 进 `extra["job_handoff"]` |

一条边界：交接单**不推进**任何一步——人接手了由下一次 `advance()` 自己往前走，人不管它由 `expires` 收尾。

## 9. 大小与预算

| 项 | 预算 |
|---|---|
| 同一会话同时在手的 job | ≤3（超了先让判收尾或放弃最旧的一条） |
| 进判的 job 读数 | ≤3 条 / 每条 **≤60 字** |
| 一件事的工具调用 | **回合 ≤2 次 + 任务累计 ≤12 次**（跨回合） |
| 一件事的模型推进 | ≤20 回合（超了必须向人报告「还没办完」） |
| 方案文件 | ≤4000 字；超了拆多页，不塞进 prompt |
| 等待批准的超时 | 默认 24h，到期置 `expired` 并说一句「我先搁着」 |

## 10. 边界（明确不管）

| 不管 | 归谁 |
|---|---|
| 说还是不说、对谁说 | 判 |
| 动作怎么发出去、发没发成功 | 出口 / 软件 · 适配器 |
| 查到的东西从哪来 | 工具包（它只给次数与预算） |
| 「这件事值不值得办」 | 判（五问里的「代价值得吗」） |
| 定时器本身怎么跑 | 调度器（`scheduler/`，job 只声明 `trigger.next_fire_at`） |
| 凭据 / 登录态 | 人（`appdata` 与 `.env`，job 只存「用哪个账号」的引用） |

## 11. 意义

- 让「办一件事」不需要新架构：**判还是那个判，出口还是那个出口**，多的只是一行状态；
- 让不可逆动作有**闸**：批准是一个可审计的行（谁、何时、批了哪个 hash、从哪个通道），不是一句口头同意；
- 让失败可交接：办不下去时给人 `handoff{url, prefilled, screenshots}`，而不是「抱歉我没办成」；
- 让「换一件事」变成配置：十类任务（信息 / 代笔 / 文件 / 社交 / 跨天追踪 / 长表单 / 长文 / 监控 / 代人 / 多平台）里，大多数只换槽，不改代码。

## 12. 量具

| 指标 | 口径 | 目标 |
|---|---|---|
| 中断恢复率 | 从最后一个安全点恢复成功的 job / 被中断的 job | **100%** |
| 安全点违规 | 在 `safe_point: false` 的边界被中断的次数 | **0** |
| 越权动作 | 没有 `approval` 就调出口的次数 | **0** |
| 进度问句命中率 | 用户问「到哪了」时读数能直接回答的比例 | ≥90% |
| 重复提问率 | 同一 job 内问过又问的事 / 总提问 | ≤10% |
| 任务预算超支率 | 超「累计 ≤12 次」的 job / 总 job | **0** |
| 办成率 / 交接率 | 办成 / 走 handoff 的比例（按任务类别分开算） | 观察，不设目标 |
| 方案改口率 | 同一 job 里 `steps` 被整体重写的次数 | 观察（高 = 判没看懂） |

## 13. 未定

1. `halt` 与 `silent` 的关系：办不下去时要不要在群里说一句？（默认：只在本人私聊说一次）
2. 一件事能不能跨会话（群 → 私聊 → 群）？默认：能，但读数只在**授权通道**里给。
3. 多件事的优先级：≤3 条读数里谁先？默认按 `updated_at` 新者先。
4. job 保留多久：默认办完 30 天，之后只留一行摘要。
5. `approval` 能否批量（「这一周的都按这个办」）？默认：能，但必须带 `expires_at` 与 `max_amount`。

## 14. 不做

- 不做并行：一件事的步骤串行推进，多件事也由判串行处理；
- 不做自动重试编排：失败交回判，由判决定「我再试一次 / 换路 / 交给人」；
- 不做「替人做决定」：模糊就问，问不到就交人；
- 不做钱：不存支付凭证、不代付；付款一律人自己点；
- 不做绕过风控（验证码、逆向接口、模拟器批量）；
- 不把 job 写进 `core/routing/turn_pipeline.py` 的判决路径（办与判分离）。

## 15. 落库形状（台账 · 投影 · 三档开关 · 推进器）

一件事落库只有三张表，全部在应用库（还有 `terminal_events` 的库）：

| 表 | 是什么 | 关键约束 |
|---|---|---|
| `job_events` | **唯一事实源**：一次状态变化一行，`(job_id, seq)` 主键 | append-only，永不改旧行；`kind ∈ created / planned / turn / step_done / awaiting / approved / done / cancelled / expired` |
| `jobs` | 当前状态的**投影**（判读的就是它） | 删掉整表可由 `job_events` 重放回来（`JobStore.rebuild()` 就是干这个的，用例拿它当断言） |
| `job_approvals` | 人给的批准 | 主键 `(job_id, step_n, action_hash)`：同一个动作批两次幂等，过期不算批 |

开关 `JOB_LEDGER` 三档（默认 `off`）：

- `off`：写读全 no-op。判拿不到读数，行为与没有这一片时逐字相同；
- `shadow`：**写**事件与投影，但 `readouts()` 一律返回 `[]`（不进 prompt），写失败只记日志；
- `on`：写读都开，写失败**抛**——读侧依赖它，静默丢事件等于让判在假状态上推进。

推进器 `core/jobs/runner.py::advance()` 只接只读（`allow_effects=("read",)`），停因是封闭集合：
`done / need_approval / awaiting / budget / turns / state / failed / no_executor`。三条不许越过的线：

1. 没有批准，`effects != "read"` 的步骤一步都不跑（停 `need_approval`，同时写一条 `awaiting{kind: approval}`）；
2. 只在 `Step.safe_point` 上停——`safe_point=False` 的步骤表示「跑起来就不许中断」（提交表单、扣款），这是「半个订单」的唯一防线；
3. 预算一本账：工具累计按**这件事**算（`TOOL_CALLS_PER_JOB`），回合数按判调 `advance` 的次数算（`MAX_TURNS_PER_JOB`）。

本片**不接行为**：`core/routing/turn_pipeline.py` 尚未调用 `advance`，`JOB_LEDGER` 默认 `off`。

## 16. 读侧接线（判的第 6 样输入）

台账落库是一件事，**让判看见它**是另一件事。读侧只走一个模块：

| 位置 | 做什么 | 不许做什么 |
|---|---|---|
| `core/context/job_readout.py::collect_job_readouts` | 见开关 → 取 `JobStore.readouts(chat_id)` → 写进 `extra["job_readouts"]` | 不许自己拼提示词、不许调模型、不许写台账 |
| `core/context/job_readout.py::build_job_readout_block` | 只读 `extra`，渲染成 `[在手的事]` + 1~3 行 `- job_id · 目标 · 第 n 步 · 在等什么` | 不查库（查库在上面那一步），不做截断以外的加工 |
| `agents/conversational.py::_job_readout_block` | 在 `_read_block` 之后贴一次，装配路径与回退路径共用 | 不许改动既有任何块的字节与顺序 |

**已知未做**：块走 `_append_prompt_block` 追加（与 `[按需记忆]`、`[读取]` 同一位置），
还没登记进 `core/context/assembler.py::_BLOCK_POLICY`（那层管预算与 trace）。
`on` 档转正之前必须补登记，否则读数进了 prompt 却不在预算与 trace 里——`shadow` 攒数据期间不影响。

三档开关就是三行结果：

- `off`（默认）：**连台账都不碰**，函数返回空串，`extra` 里不多任何键 —— 既有提示词逐字不变（`tests/test_job_readout_block.py` 拿"假台账一次没被调用"当断言）；
- `shadow`：查一次 `open_jobs(chat_id)`，只落 `extra["job_readout_shadow"] = {"open": n}` 与一条日志，**一个字符都不进 prompt**；
- `on`：读数进 prompt，形状固定为块头 + 每行 ≤3 条 × ≤60 字（常量在 `core/contracts/plan.py`，改数要同步契约 §1 与 §12 量具）。

降级只有一种：**任何异常 → 空串**。读数丢一轮，判只是不知道有件事在手，不会因此说错话；抛出去会让整个回合拼不出提示词。反过来说，`shadow` 档攒的就是"如果给了读数，判会不会问进度"——这是 `进度问句命中率 ≥90%` 的分母。

### 16.1 判的调用点（阶段 3 第一刀）

`core/routing/turn_pipeline.py::_job_tick` 是「判 → 在手的事」这根管子唯一落地的地方，
挂在 `generate_turn()` 里（全仓唯一的回合生成口），所以每回合至多一次。三档开关：

| 档 | `_job_tick` 做什么 |
|---|---|
| `off`（默认） | 读到开关就返回：**不打开台账、不查库、`extra` 不多一个键** |
| `shadow` | 查 `open_jobs(chat_id)` → 对每件事调一次 `runner.advance(job, store=store)`（**不给 `execute`**，只回 `stop=no_executor`，一个字节都不写台账）→ `collect_job_readouts` 只落 `{"open": n}` 与一条日志 |
| `on` | 同上，并把读数写进 `extra["job_readouts"]`，由 `agents/conversational.py` 渲染成块 |

**为什么 `shadow` 也要调一次 `advance()`**：U-10 之前这个函数没有任何调用者，等于死代码。
先让真实回合摸到它（哪怕只返回 `no_executor`），才能在日志里量「有没有事在手」与「推进器会不会
自己乱动」。真正的执行器（`execute=`）由 U-11 注入，那时才谈「跑一步」。

台账坏了不许拖垮回合：整个 `_job_tick` 吞异常，只写一条 `job_tick_failed` 警告。

### 16.2 判怎么开一件事（阶段 3 第二刀）

`core/jobs/ingest.py::ingest_plan` 是「判 → 台账里多一行 `created`」唯一落地的地方，
调用点在 `agents/conversational.py::audit_verdict_contract()`（全仓唯一「模型一次性给出判决载荷」的落地点），
所以**同一份载荷只可能开一次**。

| 检查 | 不合格怎么办 | 为什么 |
|---|---|---|
| `goal` 非空且 ≤200 字 | 整段拒收 | 没有目标的事推不动，也没法判「办完了」 |
| `steps` 1~12 步、每步 `action` 非空 ≤120 字 | 整段拒收 | 步数上限就是工具预算（`TOOL_CALLS_PER_JOB`），再多也跑不完 |
| `effects` ∈ `read/write_local/ui_control/external_send` | 整段拒收 | 未注册的副作用一律不认（工具包同一套四档） |
| 步骤号唯一 | 整段拒收 | 重复号会让 `next_step()` 卡在同一处 |
| 载荷里的 `approved` | **一律抹成 `False`** | 判不能自己批自己：批准只从 `Approval`（人、私聊、带 `action_hash`）来 |

幂等键是 `plan_job_id(chat_id, trace_id, goal)` = `job-` + sha256 前 16 位：
同一回合、同一目标重复投递**不开第二件**（第二次直接返回台账里那件）。

三档开关：

| 档 | `ingest_plan` 做什么 |
|---|---|
| `off`（默认） | 读到开关就返回：**不读载荷**（用例拿"一被读就抛"的 dict 钉住）、不碰台账 |
| `shadow` | 只解析 + 记 `job_plan_shadow`（会开成几步、哪些 effects），台账一个字节不写 |
| `on` | 校验通过就 `store.create()`；`JobLimitExceeded`（同会话已 3 件）与台账异常都只记日志、返回 `None` |

`pending_approval` 的生产者也在推进器里：`core/jobs/runner.py::pending_approval_receipts(result)`
只在 `stop == "need_approval"` 时产出**一条**回执（`status=pending_approval` / `ack="none"` /
`job_id` / `step_n` / `action_hash` / `channel="private"`）。`_job_tick` 的 `on` 档把它放进
`extra["job_approvals"]`；消费方是出口（U-11），**本片不发任何字节**。

### 16.3 只读执行器（阶段 3 第三刀）

`advance()` 要一个 `execute(step)` 回调；`core/jobs/executor.py::read_only_executor` 是它的**只读实现**：

| 判据 | 结果 |
|---|---|
| `effects != "read"` | `{"ok": false, "detail": "blocked:non_read:<effect>"}`，**registry 一次都不碰** |
| 没有绑定注册表 | `{"ok": false, "detail": "no_tool:registry 未绑定"}` |
| `Step.action` 形如 `web_search:杭州机票` | 工具名与 `what` 用第一个 `:` 分开（无冒号则 `what` 为空） |
| 工具返回 `status == "ok"` | 成功；正文截到 600 字（超过补 `…`） |
| `no_result` / `timeout` / `rate_limited` / … | **失败**，`detail` 以状态码起头（「没查到」不等于「办到了」） |
| registry 抛异常 | 这一步失败，异常被吞（不许冒到 `advance()`） |

注入很克制：`_job_tick` **只在 `JOB_LEDGER=on` 且 `executor.default_registry()` 非空**时才注入执行器。
`shadow` 一个工具都不发（那会真的上网/截图）；`on` 但没绑注册表时仍停 `no_executor`——**宁可不跑，
也不许空转烧预算**。`turn_id` 传的是 `job_id`，所以工具预算按「这件事」数，一次失败也算一次。

### 16.4 第六态交出去（阶段 3 第四刀）

`_job_tick` 在 `on` 档把这一回合的挂起回执交给出口：`extra["job_approvals"]` 给判（读），
`extra["job_approval_receipts"]` 给出口已经造好的 `Receipt` 列表。出口那一步
（`core/speech/delivery.py::deliver_pending_approvals()`）**一个字节都不发**，只造回执；
挂 `DELIVERY_CONTRACT`（默认 `off`，`shadow` 只写日志）。

回执经 `ledger` 钩子落进 `delivery_receipts`（迁移 65，唯一索引 `(turn_id, kind, ref, target)`，
重放同一回合不会灌双份）；`ref` 形如 `job-abc#2`，指出挂起的是哪一件哪一步。

同时修掉一个顺序 bug：`advance()` 原来先判「有没有注入执行器」再看「这一步要不要批准」，
于是 `on` 但没绑工具注册表的会话里，写操作永远只报 `no_executor`——「等你点头」这部分
永远不会出现在回执里，判也就无从知道有一件事卡住了。现在**先问批准，再谈执行器**：
等批准是人的事，不是工具的事。

## 17. 审批入口：人回一句怎么变成一行批准

入口只有一条：回合生成口 `generate_turn()` 把这一句原话交给 `_job_tick()`——
`approval_text=ctx.inbound.content`、`is_private=not ctx.decision.is_group`、
`speaker_id=ctx.decision.sender_id`——再由 `core/jobs/approval.py::apply_approval()`
决定它是不是对某一件在等的事的批准。**判不参与这一步**：判在下一回合照旧只有
「说 / 问 / 沉默 / 弃权」，盖章的不是模型。

五道闸，任一不过就返回 `None`（方向固定为「不办」，不是「办错」）：

| 闸 | 判据 | 为什么 |
|---|---|---|
| 私聊 | `is_private` 为真 | 群里第三人打字不算授权（§8 第二条红线） |
| 短句 | ≤40 字 | 长句多半是新话题，那是判的活 |
| 否定优先 | 出现「不用 / 别 / 算了 / 取消 / 不行 / 改成」即不批 | 「可以，但是先别订」是人话里的常见反悔 |
| 一件 | 同一会话只有一件事在等批准 | 一句「可以」不许同时给两件盖章 |
| 批动作 | `action_hash = step_action_hash(job_id, step)` | 批的是那一个动作，不是那句话 |

落库两步（缺一不可）：

1. `store.approve(approval)` → `job_approvals` 插一行（唯一键 = `(job_id, step_n, action_hash)`，
   `INSERT OR IGNORE`，重复说「可以」返回 `False`、不造第二行）；
2. `store.append(job_id, "approved", actor="human")` → 投影把 `awaiting_kind` 清空、
   `state` 回 `open`，`advance()` 里那句「`awaiting.kind` 非空就停」才会放行。

于是同一回合里「她刚点头 → 写操作解冻 → 推进器继续跑」成立，而**在没人点头之前，
写操作一步都跑不了**（`advance()` 的 `_await_approval` 先于执行器判断）。

不做：不解析「同意」以外的语义（那不是审批，是判）、不许群里批、不做「撤回批准」
（要说「算了别订了」是新的否定，另记一条 `cancelled`）、批准不跨会话复用。
过期照 `APPROVAL_TTL_HOURS = 24`：过期后 `is_approved()` 一律 `False`，人得再说一次。

量具（E3 起算）：批准误记率 0（每 20 条抽 1 条人工核）、越权动作 0、重复批准行 0、
「批了但没动静」0（批准后同一回合必须能看到推进或一条停因）。

### 17.1 写操作执行器：只许量、不许做

`core/jobs/executor.py::write_executor(registry, *, turn_id, target, shadow=True)` 是
`advance()` 的第二个 `execute(step)` 实现，比只读那个多认一种 effect：

| effect | 执行器怎么处理 |
|---|---|
| `read` | 走 `registry.observe()`，照旧 |
| `write_local` | 走 `registry.act()`；**`shadow=True`（默认）时一次都不调**，只返回 `{"shadow": True}` |
| `ui_control` | 一律 `blocked:non_writable:<effect>`（effect 位就是 `ui_control`；要三条判据，见工具包 §4.1） |
| `external_send` | 同上一条代码路径（effect 位是 `external_send`）；只许走出口注册表，R3 |

影子档对应 `advance()` 的新停因 **`shadow`**，三条都不许做：
**不推进步号**（下次还得从这一步起）、**不写 `step_done`**（否则台账会把「没办」记成「办过」）、
**不算 `done`**（事儿没办完）。它也**不算失败**——她没做错事，只是手被按住了。

为什么默认按住：写操作**没有幂等键**（App 上点重了就是两单），
所以在「状态差异式回执」（`state_before / state_after / changed`）与三级授权落地之前，
这条路只许量、不许做。`_job_tick` 里那句 `shadow=True` 是刻意的常量，
`tests/test_job_write_executor.py` 钉住它，谁把它翻成 `False` 谁就得先补那两样东西。

量具（E3 起算）：影子档停因次数（=「本该写多少次」）、批准后仍停 `shadow` 的比例、
越权动作 0（`ui_control` / `external_send` 出现在执行器调用记录里的次数必须恒为 0）。

### 17.2 状态差异式回执：写操作「怎么才算办成了」

写操作**没有幂等键**。消息有 `external_msg_id`、邮件有 `message-id`，
可「在表单里点一下提交」什么号都不给——同一个动作做两次，就是两张单。

所以这一层不要幂等键，要**状态差异**：

| 字段 | 含义 |
|---|---|
| `state_before` | 动手前那一处的摘要（文件内容 sha256 前 16 位 / 表单关键字段的指纹） |
| `state_after` | 动手后同一处的摘要 |
| `changed` | 变了什么（`{path, before, after}` 这类）。**空 = 什么都没变** |

三条纪律：

1. **`changed` 为空 = `no_change` = 失败**。写完跟写前一模一样，不是「办成了」，是「什么都没发生」；
   执行器据此判失败，判看到的是「这一步没成」，不是「已办完」。
2. **前后两半都要进台账**（`step_done{state_before, state_after, changed}`）。
   只留 `changed` 会丢掉「从什么变成什么」，事后无法回答「她到底改了哪一版」。
3. **采不到状态就不许写**。有些 App 不暴露可比对的状态，那时宁可停在 `no_state`
   （等 UI/ADB 通道做出可比对的取样点），也不许拿「点了一下没报错」当成功。

量具（E3 起算）：写步里 `no_change` 的比例（不为 0 就说明要么重复点、要么根本没生效）、
`state_before / state_after` 缺失率恒为 0。

### 17.3 界面步（`ui_control`）接进执行器：三把钥匙

`ui_control` 以前在执行器里是 `blocked:non_writable`——判能选中 `gui_click`，但「一件事」永远点不了。
2026-10-21 接上，接线方式刻意让**放行**和**批准**是两个不同的动作：

| 钥匙 | 谁转 | 不转会怎样 |
|---|---|---|
| `allow_ui=True` | 调用方（`_job_tick` 显式给） | 执行器直接 `blocked:non_writable:ui_control` |
| 一行 `Approval` | 人（私聊本人说「可以」，`confirm` 档） | `advance()` 停在 `need_approval`，执行器零调用 |
| `changed` 非空 | 工具自己（`gui_click` 的像素差与状态差异） | `no_change` / `no_state`，不算办成 |

为什么要拆成三把：**执行器不查批准**（它只认调用方说了允许），批准只由 `runner._gate()` 与
`core/jobs/policy.py` 的三档决定——「谁能放行」全仓只有一处，改动错不了地方。

参数怎么落：`Step.action` 只有 ``工具名:半句话``，所以执行器按工具声明的 `args` 猜**主参数**
（`selector` → `url` → `query` → `content` → `name` → `text`），把半句话填进去，同时保留
`params["what"]`（老工具读它）。没有这一层，`gui_click` 拿到的 selector 会是工具名自己。

`external_send` 在 §17.4 之后也有了自己的门（默认仍然关）：`allow_external=True` **且**
调用方递进一个发送器回调，才会走那条路；否则照旧 `blocked:non_writable:external_send`。

真机证据（2026-10-21，本机 Edge + `--remote-debugging-port=9222`，`GUI_CHANNEL=on`，
本地试验页 `http://127.0.0.1:8765/index.html`）：

- `snapshot()` 读到标题 `鲸鲸点击试验`、正文 13 字、指纹 `1ce7933d31f08c1d`；
- `navigate(...?t=2)` 的状态差异有 `url` / `title` / `digest` 三项；
- `click("#go", window_title="Edge")` 三条判据 `{foreground: true, title: true, pixels: true}`，
  像素差 **514101**，标题从 `鲸鲸点击试验` 变成 `鲸鲸点击试验-已点`，`expect_found=true`，
  证据两张：`data/evidence/realtest_click_before.png`（18617 B）与 `…_click_after.png`（18447 B）。

### 17.5 `read` 步的主参数：`target` 排在最后

执行器给工具的 `target` 是**会话**（谁的事），不是「读哪个窗口」。所以 `gui_state:微信` 这半步
必须落到 `params["target"]`，而工具里取值顺序是 `params["target"] → what → target`——
**params 优先**，否则一律读到会话名。

- `_PRIMARY_ARGS` 的次序就是覆盖力的次序：`selector, url, query, content, name, text, target`。
- 有测试钉住：`tests/test_gui_snapshot_tool.py` 的「params.target 优先于调用方传的 target」。

### 17.4 对外发送接进执行器：第二条路也还是一个出口

`external_send` 到 2026-10-21 为止在两个地方被按住：出站只许走出口注册表（R3），执行器里一律
`blocked:non_writable:external_send`。可「帮我发一句『明天见』」这种事实在没有第二条路走不通——
它不需要 `deliver` 的判决、渲染、语气，它就是一件事的最后一步。

所以接线做成**注入一个回调**，而不是在执行器里开一个口子：

| 钥匙 | 谁给 | 不给会怎样 |
|---|---|---|
| `allow_external=True` | 调用方（`_job_tick` 按「有没有发送器」决定） | `blocked:non_writable:external_send` |
| `external(to, text, *, turn_id)` | `core/routing/turn_pipeline.py::_external_sender()` | `no_sender:…`（路上没人，不是拒绝） |
| `WECHAT_SEND=on` | 人（开关） | `_external_sender()` 直接返回 `None` → 上一条 |

`_external_sender()` 的实现是**固定的一行**：`core/execution/gui/wechat_send.py::send_and_verify`
（按回车全仓只有它跟 `wechat_send` 那一处，`scripts/check_topology.py` 规则 8 用
`ENTER_SITES` 白名单钉住）。所以「对外说话」仍然只有一条被允许的路，只是这条路现在可以被
一件事调用，而不只是被一个回合调用。

载荷怎么拆：`Step.action` 形如 `send:明天见`（发给这个会话）或 `send:张三|明天见`
（`|` 前是收件人）。`external` 只拿三样：收件人、正文、`turn_id`。

回账怎么算（`_run_external`）：

| 发送器回的 `status` | 结果 |
|---|---|
| `sent` | `ok=True`，`changed={local_id, server_id}`，`state_after="wechat#<local_id>"` |
| `unconfirmed` | **也 `ok=True`**（已经到人手上了，重发就是重复发送） |
| `failed` / 其它 | `ok=False`，**只调一次**，停在 `failed` 交给人 |
| 抛异常 | `ok=False`，`detail` 带异常类型 |

不做：不重试（重复发送率必须为 0）、不在执行器里判「这句话会不会冒犯谁」（那是判的事）、
不绕过 `wechat_send` 的发送后回读（`sent` 的含义由它定义）。

量具（E3 起算）：`no_sender` 出现次数（=「判想发但没接上发送器」的次数）、
`failed` 后重试次数恒为 0、`unconfirmed` 占比、按回车调用点数量（`check_topology` 里恒为 5 处）。

## 18. 发出去之后：撤回窗口与更正（阶段 7）

一件事办完不等于办对。发错了、说错了、订错了，系统必须能做两件事：**收回**，或者**更正**。
这一节只落地了「判断 + 措辞」，接线在下一刀（要动判的输出契约，新增 `correct` 意图）。

| 手段 | 什么时候能用 | 现实约束 |
| --- | --- | --- |
| 撤回 | 发出后 **120 秒**内（`can_revoke`） | 微信撤回要右键菜单 + UI 自动化，比发送更脆；菜单这条路还没验过 |
| 更正 | 任何时候 | 就是一条普通消息——走已经真发通过的 `send_and_verify`，风险归零 |

三条纪律：

1. **只认回执里的时间**：`can_revoke` 读 `receipt.at`，不读「我记得是刚才」；时间读不出来按**过期**处理
   （宁可只能更正，也不要瞎撤回）。
2. **说不清就不发**：没有 `ref`（不知道在更正哪一条）→ 不出计划；正文为空或超过 200 字 → 不出计划。
3. **更正必须带原话片段**（≤20 字，超出截断 + `…`）：否则对方不知道在更正哪句，更正反而制造困惑。

形状：`Correction(ref, target, text, original_excerpt, mode)`，`mode` 只有 `revoke` / `correct` 两值。
`correction_text("明早九点开会", "改到十点")` = `更正：明早九点开会 → 改到十点`。

### 18.1 更正也能当一步动作（`correct:<回执号>|<改口>`，2026-10-21）

撤回是「把话拿回来」，更正是「补一句对的」。在动作串里它写作：

    correct:wechat#89|周四改到下午

- 冒号切工具名，`|` 切「回执号」与「改口」（同 `send:会话|正文` 的口径）；
- 走 `external_send` 的同一把钥匙：`write_executor(..., allow_external=True, correct=...)`——
  没放行就 `blocked:non_writable:external_send`，没注入就 `no_sender`；
- 更正失败**不重试**（重试会产生第二条改口，比错话更糟）；
- 注入点 `core/routing/turn_pipeline.py::_correction_sender()`，只有 `features.CORRECTION=on` 才给（默认 off）。

## 19. 真机驱动：把一件事从开到办完走一遍（`scripts/job_drive.py`）

**为什么要有它**：判 → 一件事 的总闸是 `agents/conversational.py::audit_verdict_contract`，
而它在旧 pipeline 里**没有任何生产调用点**（模型还不输出判决 JSON）。所以这一段机械虽已落地、
测试也绿，**真机上一次都没通电**。驱动脚本绕开模型，直接喂一份合法载荷，把
「开一件事 → 只读步跑完 → 停在等批准 → 私聊一句『可以』→ 放开那一步 → 跑完 → 读数出现在下回合 prompt」
逐段点亮。

用法：

    python -X utf8 -m scripts.job_drive --allow-production [--leave-awaiting] [--tag HHMMSS]

- `--allow-production` 必须显式给：它会往**生产库**的 `jobs / job_events / job_approvals` 写行
  （操作员工具，不是测试；与 `scripts/reimport_speech_seed.py` 同类，入口处
  `db.write_guard.declare_writes_allowed(declared_by=...)`）。
- `--leave-awaiting` 额外留一件「等你批准」的事，用来在真机上验证读数进 prompt。
- 每次换 `--tag`（默认当前时分秒）：`job_id = hash(chat, trace, goal)`，同一目标第二次跑会**命中上一件**
  （幂等），演示就变成「推一件旧事」。

**16 条断言覆盖**（`RESULT 0 failed`）：开出一件事 · 只读步真跑完 · 停在 `need_approval` 且**没批的步一步没执行** ·
台账 `awaiting/approval` · 产出 `pending_approval` 回执 · 读数取得到（含「等批准」）· 私聊本人「可以」判成批准 ·
群里说不算 · 「算了」否定优先 · 别人说不算 · 批准落库 · 回到 `open` · 批了才跑那一步 · 停因 `done` · 终态 `done` ·
事件序列 `created → step_done → awaiting → approved → step_done… → done`。

**它没有证明的**：载荷不是模型给的。`plan` 目前只能从脚本喂进来——让判自己输出判决 JSON
是阶段 3 的另一刀，在那之前这条线不会自发发生。

**三条纪律（都是踩出来的）**

1. 演示载荷的副作用步用**只读工具配高档 effects**（`gui_state` + `ui_control`）：批准后执行器调 `act()`，
   工具当场拒绝，于是「批准闸真的放行」被证明，而真机一动没动。
2. `what`（动作里冒号后那半句话）是**自然人话**，不能当窗口标题用。`gui_state:` 后面要写**真窗口名**
   （如 `微信`），否则一律 `no_target`——这是 fail closed 的正确行为，但意味着将来的规划 prompt
   必须写清「每个工具的第一个参数长什么样」。
3. 事件顺序上 `done` 之后还会有一条 `turn`（回合级计数统一在循环末尾写）。量具按 `kind` 计数，
   不依赖末条是谁，所以不改。
4. **`AgentContext.extra` 的键必须先登记**（`core/routing/turn_pipeline.py::EXTRA_CONTRACT`）。
   2026-10-21 真机实况：`job_readouts` 没登记，strict 档抛 `ExtraContractViolation`，而
   `collect_job_readouts` 按 fail-closed 吞掉异常——于是**一件事的读数一整天没进过她的 prompt**，
   日志里只有一条 `extra_contract_violation`。已补登记 9 个键（job_* 八个 + `senses_block`），
   并把 `scripts/audit_extra_contract.py` 的扫描范围补上 `core/context/job_readout.py` 与
   `core/senses/snapshot.py`，同时把这条审计提升为不变量闸 `I7`（`scripts/check_invariants.py`）。
   教训：**契约类守卫「运行期才生效 + 写侧 fail-closed」= 静默失效**，必须有一条静态闸盯着。

## 20.1 计划器：结构性地问「哪几步」（真机三次失败后的结论）

让模型在聊天正文里**自己**夹一段 `<plan>`，这条路真机验过三轮、结论是**不可靠**：

| 轮次 | 提示词状态 | 结果 |
|---|---|---|
| 1 | 145 字、只说「决定真的去办时」 | 她答完了，`jobs` 0 行 |
| 2 | 196 字、点明「查资料也算」、补「不附就别答应」 | 仍 0 行 |
| 3 | 217 字、表头与装配登记名对齐、判级 AUX→RELATION、`plan_hint_injected chars=217` 证明进了 prompt | 仍 0 行 |

所以不再靠措辞，改成**结构性**做法（`core/jobs/planner.py`）：

1. **要不要动手**由代码判：`looks_like_task(text)` 只认动词表（发/查/订/买/打开/填/撤回…），
   便宜、可解释、可测；不像任务的**连一次模型都不调**。
2. 真要动手才问一次「哪几步」：`maybe_open_job(...)` 用一次很小的模型调用，
   system 只有一句「只输出一行 JSON」，`max_tokens=400`、`temperature=0`。
3. 输出严格校验后交给 `ingest_plan` —— 开事这条路一个字没变。
   坏 JSON / `act=false` / effects 非法 / action 空 → **当没这回事**（只记日志）。

三条纪律：门仍是 `JOB_LEDGER`（off 档连动词表都不查）；计划器不执行、不发消息、不自己写台账；
任何失败只记一行日志，**不许影响这一句话**。接线点在 `core/routing/turn_pipeline.py::_send_reply_impl`，
`_had_plan` 保证「模型自己附了块」时不再重复问。

## 19.5 失败也要进她的读数（`[最近没成]`）

台账里 `step_failed` 从前只写事件、不进 prompt。后果是真机上她**不知道自己失败过**：
2026-10-21 一整个下午她反复说「我这边发不了消息」，而台账里躺着 `fill_failed no_target`。

- `core/jobs/store.py::recent_failures(chat_id, *, limit=3, within_hours=72) -> list[dict]`
  （只读；`off` 档返空；异常只记 `job_recent_failures_failed`）。
- `core/context/job_readout.py`：`on` 档把最新一条拼成 `[最近没成] <detail>` 追加进
  `extra["job_readouts"]`（**不加新键**，避免再撞 `EXTRA_CONTRACT`）；渲染时
  `READOUT_MAX_ITEMS = 3` 的上限**不给失败行让路**——在等的事本来就有上限（同会话 ≤3 件）。

判据：失败进读数不是为了认错，是为了让她**换方法或改口**；一行 detail 就够。

钉住：`tests/test_failure_visible.py`（真库读、跨会话隔离、`off` 不读、渲染保失败行、`extra` 不多键）。
