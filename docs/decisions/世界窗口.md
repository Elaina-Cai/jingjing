# 世界窗口（世界面 · 这一屏）

> 依据：`output/3d/viewer_css.html` 里那块贴 `window.png` 的竖板（标签「世界面（取景框 A · 这一屏）」）+ 管子 `read_screen()`；细则见 `窗口_渲染规格.md`。
> 四问先答：**图上是哪块** = 判板左手边那块竖板；**进来什么** = 账本的后缀 + 标注层；**出去什么** = 一份只读快照（有序的行）；**职责** = 把后缀渲染成「她此刻看得见的一屏」，别的一概不做。

## 1. 图上位置

```
   账本·事件流  ──(后缀)──┐
                          ▼
                   ┌──────────────┐
                   │ 世界面 · 这一屏 │  <- 本文：一块竖板，贴着一屏原文
                   └──────┬───────┘
                          │ read_screen()
                          ▼
                    判 / 投 / 记
```

- 板子：`translate3d(-250px, -300px, 0)`，贴图 `window.png`（`240 × 560` 竖板），在原点左前方。

| 与谁相连 | 方向 | 说明 |
|---|---|---|
| 账本·事件流 | 只进（后缀） | 只取这一段，不取全量；全量是记忆立方体的事 |
| 标注层（媒体描述 / 转写） | 只进 | 只读，用来把 `[图片]` 变成 `[图片：描述]` |
| 判 | 只出（`read_screen()`） | 判只看这一屏，看不到更早的、也看不到别的会话 |
| 记忆 / 自我 / 工具包 / 出口 | **不相连** | 图上没有管子 |

## 2. 它是什么（先破一个误解）

**它不是存储，也不是缓存，而是一次计算结果。**

```
世界面 = render(账本后缀)        # 纯函数：同样的后缀，逐字同样的屏
# 「后缀」即 账本·事件流.md §6.1 的『窗口格式』那一份投影；全量那一份给记忆
```

- 图上那块板画的是「某一刻的那一屏」，是**实例**；规则是函数，随时可重算；
- 不存在「世界面文件」「世界面表」这种东西——重启后从后缀重放，结果必须逐字相同；
- 因此它**可以随时丢弃**：丢了只是要重算，而不是丢信息。

## 3. 进来的是什么

| 输入 | 具体 | 不许做什么 |
|---|---|---|
| 账本后缀 | 该会话最近的、按（时间, 顺序）排好的一段 | 不许按「重要」重排；不许跨会话拼接 |
| 标注层 | 媒体描述、语音转写（有就显示，没有就 `[图片]`） | 不许让标注改写原文；不许标注失败就丢行 |
| 平台事实 | 引用关系、拍一拍、撤回、入退群 | 只认平台给的（引用字段、系统消息）；**我们解析出来的一律不进屏** |

**时间不进**：渲染器不读 `now()`。跨天分隔由行自己带的时间决定，不是由「现在几点」决定——否则同一份数据隔一天渲染就会变。

## 4. 出去的是什么

一份**只读快照**，给两类人：

| 谁 | 拿到什么 | 用途 |
|---|---|---|
| 判 | 一屏有序的行（时间 / 显示名 / 正文 / 引用块 / 系统行） | 决定说不说、说什么 |
| 运维与量具 | 同一个函数的结果 + 预算标记 | 核对「她当时到底看到了什么」 |

快照带三样元信息：**起点（最早那行的 id）、终点、是否触发了逐出**。这样判与量具都能说清「我看到的是哪一段」。

## 5. 职责：四条铁律 + 一份预算

| 铁律 | 含义 | 反例（都不许做） |
|---|---|---|
| 可见性 | 把同一份数据交给平台自己的界面，用户能看到什么，这里就显示什么 | 把 `at_body` 解析成「回 X」；把推断写成引用 |
| 哑渲染 | 取字段 -> 排版。不匹配、不解析、不推断、不联网、不读 now() | 渲染时现查名册补名字 |
| 可重建 | 纯函数，重放逐字相同 | 缓存里塞「上次渲染结果」并长期信任 |
| 有界 | 预算满了从最早处逐出 | 无限追加，把整段历史塞进提示词 |

**预算三条同时生效，先到先逐**：

| 约束 | 默认 | 为什么 |
|---|---|---|
| 条数 | 40 条 | 快群几分钟就 40 条，慢群能覆盖半天 |
| 时间 | 2 小时 | 防止「40 条跨了 96 小时」这种私聊场景 |
| 字符 | 3600 | 提示词预算的硬边界 |

**逐出 ≠ 销毁**：滑出窗口的行还在账本里，可以被引用副本带回来（引用块算在**当前行**的预算里，所以能跨出窗口）。

## 4.5 什么能改变它（写入路径）

世界面是**渲染结果**，不是存储。它「变了」有且只有四种原因：

| 能改变它的 | 谁 | 形式 |
|---|---|---|
| 账本多了一条事件 | 落屏 | 后缀变了 → 重渲染 |
| 标注层多了一条（图片描述/语音转写） | 观察器 | 同一行的 `[图片: …]` 从占位变成描述 |
| 预算参数变了（40 条 / 2 小时 / 3600 字符） | 人（配置） | 下一次渲染生效 |
| 渲染器版本变了 | 代码 | 全量重渲染（必须逐字可复现） |

**改不动它的**：

| 禁止 | 为什么 |
|---|---|
| 手工编辑渲染结果 | 它是算出来的，编辑等于制造第二真相 |
| 把它当存储长期缓存 | 账本是真相；缓存坏了必须能重算 |
| 把推断写进这一屏 | 屏上只能有平台会显示的东西 + 标注层 |
| 渲染时现查名册补名字 | 改昵称会改写历史；显示名必须存快照 |

## 6. 大小

它的体量 = **一个纯函数 + 一份平台差异表 + 一份预算 + 一份穷举画布**。没有缓存策略、没有判断、没有索引。

细则（行模型、引用 45 种、媒体退化、钱、通话、异常、平台差异 21 项）全部在 `窗口_渲染规格.md`，本文只管**边界与语义**，不重复那些表。

## 7. 边界（它明确不管什么）

| 不管 | 归谁 |
|---|---|
| 在跟谁说、该不该开口 | 判 |
| 这条重不重要、要不要往前翻 | 判 + 记忆面（`unresolved` 才翻） |
| 存多久、怎么删 | 账本 |
| 怎么找旧事 | 记忆立方体 |
| 她的情绪/态度/人设 | 自我立方体 |
| 平台 UI 长什么样（气泡、头像） | 平台自己；这里只保证**文字与关系**一致 |

## 8. 意义（为什么它值一份文档）

因为**她只能看见这一屏**。这一屏之外的东西，对她来说等于不存在——除非她主动去翻（那是记忆面的动作）。

于是三个推论：

1. **这一屏就是她的「当前世界」**：屏上没有的事，她不会想到；屏上被逐出的事，她会「忘」；
2. **逐出策略就是注意力分配**：预算太小，她永远在猜（看到的都是半句话）；预算太大，关键那行被淹没；
3. **渲染错一次，她会错一辈子**：因为她的「事实」来自这一屏，而账本里的原文她平时看不见。

## 9. 量具

| 指标 | 口径 |
|---|---|
| 存活率 | 后缀原始字符 -> 渲染后字符（衡量「一屏能装下多少」） |
| 覆盖时长 | 一屏最早与最晚的时间差（快群/慢群/私聊分别看） |
| 跨天分隔正确率 | 有跨天的样例里，分隔行是否出现在正确位置 |
| 重建一致率 | 同一后缀重放两次，逐字相同（必须 100%） |
| 逐出触发分布 | 按条数/时间/字符三条分别统计，看哪条在起主导 |
| 引用副本跨窗命中 | 引用块带回了窗口外的行，占全部引用的比例 |
| 不可渲染率 | 遇到未知类型/坏数据时是否退化成了占位（不许静默丢行） |

## 10. 不做清单

沿 `窗口_渲染规格.md` §9，并补三条边界：

- 不判「在跟谁说」「该不该开口」「语气/意图/噪声」；
- 不做摘要、不压缩正文、不把推断写成「回 X」；
- 不读 now()、不联网、不查名册补名字；
- **不因为下游要用而加字段**（下游要的东西要么在账本里，要么自己算）；
- **不缓存判断结果**（缓存只能缓存「同一后缀的渲染结果」，且必须可校验）。

## 12.1 第二投影：这一屏不只是聊天（阶段 5 · 感官）

上面十一节说的都是「**这个会话的**这一屏」——它的唯一输入是账本后缀。但判说「看一眼这个网页」
时，她要的是**此刻屏幕上真实存在的东西**：前台是哪个窗口、屏幕上是什么、剪贴板里是什么。

这三样不是账本：

| 为什么不是账本 | 说明 |
|---|---|
| 不是「外部发生」 | 它是我方这一侧的观察，同一秒可以拍十张，它们不是不可再分的事实 |
| 不可回放 | 账本可逐字重放；屏幕重拍一次就是另一张图 |
| 不唯一 | 账本一行只有一次；「这一屏」每 20 秒都可以变 |

所以它走**第二投影**：一份随时可丢、随时可重拍的快照（`core/senses/`），只给判看"此刻"。

| 档位（`SENSORY`） | 做什么 | 不做什么 |
|---|---|---|
| `off`（默认） | 什么都不做——**连窗口都不读** | 不截图、不落盘、提示词逐字不变 |
| `shadow` | 读窗口标题与剪贴板**长度**，记一条日志 | 不截图、不落盘、不进提示词 |
| `on` | 窗口 + 剪贴板 + 截图，排成 `[现在这一屏]` 进判的输入 | 不写账本、不写记忆、不发消息 |

四条纪律：

1. **屏幕不落账本**（R1 不受影响）：截图落 `data/evidence/senses/<yyyymmdd>/`，与 `gui_click`
   的证据同一棵树——那是"我们做过/看过什么"的旁证，不是事实流；
2. **同画面不重复落盘**：指纹 `sha256(画面)[:16]`，画面一样就是同一张；
3. **节流 20 秒**：一个回合可能连着来几条消息，这一屏本来就是"此刻"，20 秒内的差别远小于
   多拍十张的成本（`core/senses/snapshot.py::MIN_INTERVAL_S`）；
4. **读不到就是读不到**：窗口读不到、粘贴板被占、截不到屏，都只在注里留一句，
   **绝不拿上一张假装是这一张**（`notes` 会写进块里）。

**已知边界**：截图是全屏（含用户其它窗口），所以 `on` 档等于把整个桌面交给模型看——
这是隐私层面的强假设，所以默认 `off`，且只有人在配置里打开才会发生。
通知（Windows toast）这一档**没做**：读它要 UIA 遍历操作中心，脆且收益低，留作后续。

## 12.2 分窗键：`chat_id` + 时间不够（2026-10-21）

**结论：`chat_id` 只在 (平台, 账号) 里唯一，只按 `chat_id` 分窗会在多账号/多平台时串。**

| 事实 | 落在代码里 |
|---|---|
| `terminal_events` 已有 `platform` / `bot_account_id` / `chat_id` / `chat_type` 四列 | `db/meta_models.py:643-646` |
| 唯一索引按四元组建 | `ux_terminal_events_external_msg (platform, bot_account_id, chat_id, external_msg_id)` |
| 但读窗口只按 `chat_id` 过滤 | `core/context/chat_window.py::load_messages`（接线前） |
| 群/私聊靠命名约定推断 | `db/models.py::is_group_chat_id()`（`group:` 前缀 / `@chatroom` 后缀） |

因此窗口口径定三条：

1. **会话键 = `conversation_key(platform, account_id, chat_id)`**（`core/context/chat_window.py`，
   分隔符 `|` 并对 `|` 与 `%` 转义，保证可逆；`split_conversation_key` 是逆运算）。
   不用 `:` 拼是因为微信 id 里有 `@`、`group:` 前缀里也有 `:`，会与 QQ 群号撞键。
2. **`load_messages` 的 `platform` / `account_id` 留空 = 存量语义（只按 chat_id，逐字节不变）**；
   多账号接入时必须传，否则两个账号在同一个群的视角会被合并成一份。
3. **`chat_type` 以字段为准，不以 id 形状为准**；跨软件时钟不同步时排序用
   `metadata.received_at`（我们收到的时刻）而不是平台自带时间。

量具：`tests/test_conversation_partition.py`（键可逆 / 默认不变 / 账号隔离 / 跨群不串 / 群私不混 /
天数生效 / 自动定档三档：`single` 过滤、`ambiguous` 超集 + 告警、`none` 不加条件、显式优先）。

## 12.3 两个身份，四道闸（2026-10-21）

**会话只按会话、人只按人。** 这两个概念在代码里各有自己的类型和键，混用一次就会串话。

| 概念 | 类型（已有） | 键 | 用途 |
|---|---|---|---|
| 会话 | `core/contracts/events.py::ConversationRef`（`platform` / `account_id` / `chat_id`） | `ConversationRef.key` 三元组 | 窗口、回执、任务投递目标 |
| 人 | `core/contracts/events.py::PersonRef` | `PersonRef.key` 三元组（含平台账号） | 记忆、授权、称呼、归属 |

> 同一个人在群里和私聊里是**两个会话**（不同 `chat_id`），本来就该分两份窗口；
> 「是同一个人」靠 `person_id` 归一，不靠 `chat_id`。

`conversation_key()`（`core/context/chat_window.py`）只是三元组的**串化**（字典键/日志字段），
必须与 `ConversationRef.key` 逐字一致，且**全仓只许这一处**——第二个拼法就是这次要防的错。

### 「人 ∈ 会话」是有意建模，不是串话

`group_memberships` 的唯一键是 `(person_id, platform, account_id, chat_id)`，
`group_membership_periods` 再加 `epoch` 表示退群/重进。它们回答的是**「这个人在不在这个群」**，
不是「这是谁的会话」——所以允许人+会话同时出现在一个键里，别处不允许。

### `chat_type`：字段优先，形状兜底，冲突记一笔

`core/identity/platforms.py::chat_type_checked(platform, chat_type, chat_id)`：

1. 平台给的 `chat_type` 说了算；
2. 没说才用 id 形状推（`@chatroom` / `group:` 是**兼容兜底**，改平台就得改 adapter）；
3. 两者都说得清但**不一致** → 仍听字段，但记一条 `chat_type_mismatch` 告警与计数
   （`mismatch_counts()`）。静默改判是这里最坏的错法：平台改了 id 形状而我们没跟上时，
   只有这一笔能让它可见。

### 四道机器闸：`scripts/check_identity_keys.py`

| 规则 | 断言 | 防的是什么 |
|---|---|---|
| A 窗口按会话 | `core/context/` 里提到 `terminal_events` 的文件必须提到 `chat_id` | 先读全局再在 Python 里筛 |
| B 人≠会话 | 「人+会话」同键的表只许 `group_memberships` / `group_membership_periods` / `conversation_windows` | 拿人当会话键 |
| C 一处串化 | 模块级 `conversation_key` 只许 `core/context/chat_window.py` 定义 | 出现第二种键 |
| D 会话键带平台与账号 | 含 `chat_id` 的唯一键必须同时含 `platform`（或 `source`）与 `account_id`（或 `bot_account_id`） | 两个账号在同一个群撞键 |

外加一条 **parity**：串化 == `"|".join(ConversationRef.key)` 且可逆。

**已知缺口：已清空（2026-10-21）**。`utterance_edges` 的唯一键此前是
`(platform, chat_id, msg_id)`，缺 `bot_account_id`——多账号时同群同消息会撞键，
撞了就是**静默丢一行，而且丢的是"谁看到的"**。现已：
① `db/meta_models.py` 的 `UniqueConstraint` 补 `bot_account_id`；
② 迁移 66（`db/migrations.py::_m066`）重建索引（新键更宽，旧数据不可能违规，无需清洗）；
③ `scripts/check_identity_keys.py::KNOWN_MISSING_ACCOUNT` 删空，规则 D 现在**零缺口**。
回滚代价写进迁移 docstring：先删掉"同群同消息、不同账号"的那一行，否则旧键重建会当场失败。

### 5 个调用点：改成「自动定档」而不是逐个传参（2026-10-21）

5 个读窗口的调用点（`core/routing/router.py`、`agents/conversational.py`、
`core/context/retrieval.py`、`core/context/admission.py` …）**不需要各传一遍**
`platform`/`account_id`：`load_messages` 在两者都留空时自己问
`resolve_scope(chat_id)`（`core/context/chat_window.py`），三档：

| reason | 条件 | 行为 |
|---|---|---|
| `single` | 该会话窗口内只有一个 (平台, 账号) 视角 | 按它过滤——语义定死，行数不变 |
| `ambiguous` | 两个及以上视角 | **不过滤** + `window_scope_ambiguous` 告警（宁可是超集） |
| `none` | 一行都没有 / 库没开 | 不加条件 |

为什么不取"最新那个视角"：那会把另一账号在同一群里更早的消息**悄悄排除**。
窗口是"这一屏发生过什么"的事实来源——多一行只是噪音，少一行会让判
"没看见却说没看见"。**歧义只准出现在日志里，不准出现在数据里。**

显式传 `platform`/`account_id` 永远赢过自动档。

## 12.4 装配块的优先级："她会什么"和"她看见什么"不是可丢的

`core/context/assembler.py::_BLOCK_POLICY` 给每个装配块一个优先级，`AUX` 的语义是
**预算压力下整块丢弃**。2026-10-21 真机暴露了用错地方的后果：

- `[本轮可用的工具]` 曾登记为 AUX → 被整块丢掉 → 她答「我这边没有往群里发消息的工具，
  只有查东西、记笔记这些」，而 `send_plan` 其实早在注册表里。
- `[现在这一屏]` 同理：看不见屏幕时，她会把"我刚看到"说成猜测。

**判据**：`AUX = 丢了不影响正确性`。而"我会做什么"与"我此刻看见什么"直接决定同一句话的
对错，所以它们是 `RELATION`（按比例裁，裁掉一行而不是整块消失）。

| 块 | 旧 | 新 | 为什么 |
|---|---|---|---|
| `[在手的事]` | RELATION | RELATION | 决定她改不改口 |
| `[现在这一屏]` | AUX | **RELATION** | 看不见 = 把未知说成已知 |
| `[本轮可用的工具]` | AUX | **RELATION** | 看不见 = 否认自己有能力 |

钉住：`tests/test_failure_visible.py`（静态断言两块都不是 AUX、且指向正确模块）。
