# 软件 · 适配器（平台差异的唯一发生地）

> 依据：`output/3d/viewer_css.html` 里 `(1050, 0, 1000)` 那块板（贴图 `t_soft.png`，板面写着「聊天 · 日历 · 邮件 · 浏览器 / 内部系统 · 任何注册过的软件 / 一次投递 = 调一个 adapter」）。
> 四问先答：**图上是哪块** = 出口右边那块；**进来什么** = 出口的一次投递（kind + target + payload）；**出去什么** = 平台消息 + 回执（或错误码）；**职责** = 把「统一意图」翻译成「某个平台的具体调用」。

## 1. 图上位置

- 板子：`addBoard(380, 240, 1050, 0, LLM_Z, 't_soft.png', '软件 · 适配器')`，在出口右侧。
- 上游：出口（`说` 管子之后的下一段）。下游：真实平台（微信 / QQ / 邮件 / 日历 / 浏览器 / 内部系统）。
- **它不是「又一个出口」**：出口决定「放不放行」，适配器决定「怎么调」。

## 2. 是什么

一个 adapter = 一套「能力声明 + 一个发送函数」。

```
capabilities()  -> 我能发哪些 kind、支持哪些 target、要不要登录
send(kind, target, payload) -> Receipt | Error
```

- **一次投递 = 调一个 adapter = 一次平台调用**（不在适配器里循环）；
- 平台差异（消息号有无、限流口径、@ 写法、文件上传方式、鉴权）**全部关在这一层**；
- 出口之上看到的永远是同一个 `Receipt` 形状。

## 3. 输入从哪来 / 输出到哪去

### 3.1 输入（三条）

| 输入 | 谁给 | 内容 |
|---|---|---|
| **① 投递请求** | 出口 | `{kind, target, payload, idempotency_key}` |
| **② 能力声明** | 适配器自己（注册时） | `kinds[] / targets / rate_limits / needs_auth` |
| **③ 凭据与账号映射** | 人（配置文件 / 环境变量） | token、session、`(platform, account_id) → 具体身份` |

**凭据不进 prompt、不进账本、不进日志正文**（只记「用过哪个账号」的 id）。

### 3.2 输出（三条）

| 输出去向 | 谁收 | 形态 |
|---|---|---|
| **① 平台消息** | 群里的人 / 日历 / 收件人 | 平台侧真实消息 |
| **② 回执** | 出口 → 账本 | `{platform_msg_id?, client_msg_id, at, status}` |
| **③ 错误码** | 出口 → 失败分类 | `auth_expired / rate_limited / target_not_found / unsupported_kind / platform_error / network` |

**适配器不写世界面、不写记忆**：它只回执；要不要把这次投递记进世界面，由 ① 落屏按平台回显决定。

### 3.3 一次投递的完整路径

```
出口 ──▶ adapter.send(kind, target, payload, key)
            ① 取凭据（只在适配器内）
            ② 组装平台调用（@ 写法 / 文件上传 / 日历事件…）
            ③ 调平台 API
            ④ 返回 Receipt（有消息号就带，没有就带 client_msg_id）
         ──▶ 出口 → 账本一行 → 量具
         ──▶ 平台侧：消息真的出现在群里
         ──▶ 平台回显 → ① 落屏 → 账本另一行 → 世界面
```

## 4. 五类适配器（现在与将来）

| 类 | 例子 | 特点 |
|---|---|---|
| 消息类 | 微信、QQ、短信 | 有 `platform_msg_id`，需要 @ 写法适配 |
| 邮件类 | SMTP | 回执只有 message-id，无「已读」 |
| 日程类 | 日历 | 无消息号，幂等靠 `client_msg_id` |
| 浏览器类 | 网页动作（点击/填表/抓取） | 无消息号，失败语义多（超时/元素消失） |
| 内部系统 | HTTP / webhook | 只有 2xx/4xx/5xx，需自定义成功判定 |

## 5. 幂等

- 有消息号的：用 `platform_msg_id` 回填，重复调用由平台侧去重或出口侧幂等键拦截；
- **没有消息号的**（日历/浏览器/内部系统）：必须自己生成 `client_msg_id` 并在平台侧落库（或在本地记「已发出」），否则重试就会重复；
- **这一条是出口「重复发送率=0」的地基**：适配器不回 `client_msg_id`，出口就无法判断「上次到底发没发出去」。

## 6. 错误分类与可重试性

| 错误 | 含义 | 可重试 |
|---|---|---|
| `auth_expired` | 登录失效 | 否（要人重新扫码/换 token） |
| `rate_limited` | 平台限流 | 是（退避后 1 次） |
| `target_not_found` | 会话/人不存在 | 否 |
| `unsupported_kind` | 该平台发不了这种内容 | 否 |
| `platform_error` | 平台 5xx/未知 | 视情况（默认 1 次） |
| `network` | 本地网络 | 是（1 次） |

**不许把 `auth_expired` 说成「发送成功」**，也不许静默丢弃。

## 7. 大小与性能

| 项 | 预算 |
|---|---|
| 单次调用超时 | 10s（文件 30s，浏览器动作 20s） |
| 适配器数量 | 不设上限（注册表驱动） |
| 每个适配器代码面 | 只暴露 `capabilities()` / `send()` 两个入口 |
| 凭据读取 | 每次调用时读取，不缓存到进程外的日志 |

### 7.1 第一个真适配器：`wechat`（2026-10-21）

`core/execution/wechat_adapter.py` 是第一个实现 `Adapter` 协议的适配器。它只是**翻译层**——
真发那套（顶栏验会话、验字、按回车、落盘等待、回读 `server_id`）在
`core/execution/gui/wechat_send.py` 里，已经真机跑通。

| `send_and_verify` 的 status | 出口的 `status` × `ack` |
| --- | --- |
| `sent` | `sent` × `platform_id`（带回 `server_id`） |
| `unconfirmed` | `sent` × `unconfirmed`（发出去了，库里还没行） |
| `failed` | `failed` × `error`（reason 由 detail 前缀翻成六类错误码：`no_target→target_not_found`、`timeout`/`not_connected→network`、其余 `platform_error`） |
| `blocked` | `blocked` × `none`（开关关着/影子档，一次都没碰平台） |

能力自报：`kinds={say}`、`targets=∅`（不限制）、`needs_auth=true`（账号态在客户端里）、
`rate_limits={"per_turn": 2, "per_minute": 6}`、`enabled=false`（**注册不等于启用**）。

**只会发 `say`**：文件/图片/表情还没有能真发的实现，一律 `unsupported_kind`；空正文 `skipped(empty_content)`。

#### 出口必须认 `_resolve` 的判决（真机自检抓到的 fail-open）

`deliver()` 原来把 `_resolve()` 返回的第三个值（block reason）**丢掉了**，只判 `adapter is None`。
后果：适配器登记了但**没启用**时，`dry_run=True` 会碰巧落到 `skipped(dry_run)` 看起来正常，
而 `dry_run=False` 会**直接往没启用的适配器发消息**。已修：`why` 非空 → 每条都 `blocked(reason=why)`，
一个字节都不发；`tests/test_wechat_adapter.py` 钉住这条（未启用 + 真发档 → `blocked` 且零调用）。

## 8. 边界（明确不管）

| 不管 | 归谁 |
|---|---|
| 该不该发 | 判 |
| 放不放行（限流、白名单、dry-run） | 出口 |
| 内容措辞、长度、@ 谁 | 判（适配器只做平台格式转换） |
| 跨平台群发 | 出口（多条投递），不适配器 |
| 失败重试编排 | 出口 |
| 账号登录 / 扫码 | 人 |

## 9. 意义

**把平台的脏差异关在一个笼子里**：出口之上只有五种结果和一个 `Receipt`；加一个新平台 = 加一个 adapter + 在注册表里声明 + 人工启用，不改主链路。

## 10. 量具

| 指标 | 口径 | 目标 |
|---|---|---|
| 各 adapter 成功率 | `sent / (sent+failed)` | >99%（消息类） |
| 时延 p50 / p90 | 按 adapter 分 | 消息类 p90 ≤2s |
| 错误分布 | 按六类聚合 | auth_expired 应长期为 0 |
| 能力漂移 | `capabilities()` 变化次数 | 变更要人确认 |
| 无回执率 | 没有 `platform_msg_id`/`client_msg_id` 的 `sent` | **0** |

## 11. 不做

- 不在适配器里做「重试 + 换平台」的编排；
- 不在适配器里改写内容（@ 写法转换除外）；
- 不把凭据写进账本 / 日志 / prompt；
- 不做「一个 adapter 发多平台」。

## 12. 未定

1. 无消息号平台（日历/浏览器）的幂等要在平台侧落库还是本地记；
2. `auth_expired` 要不要主动提醒主人（还是等下一次失败）；
3. 同一平台多账号时，`target` 怎么区分（现在靠 `(platform, account_id)`）；
4. adapter 热加载（不改进程就能加新平台）要不要做；
5. 浏览器类动作的「成功」怎么判（页面变了算不算成功）。

## 13. GUI 驱动：只读先行（`core/execution/gui/`）

适配器板块管的是「一次投递 = 调一个 adapter」。**动别人的界面**是同一块板上的另一族：
它不是「发一条消息」，而是「点一下 / 输一段」——没有幂等键，点重了就是第二单。
所以这一族先只做**读**。

### 13.1 一个驱动层，四个 backend

| backend | 覆盖面 | 可靠性 | 状态 |
|---|---|---|---|
| **CDP**（Chrome / Edge / Electron 系：QQ NT、飞书、Slack、VSCode） | 广 | 高（读 DOM 不读像素） | **本片已做（只读）** |
| ADB + uiautomator2（安卓全 App） | 最广 | 高 | 未做（下一步） |
| UIA（Win32 / UWP：微信 PC 4.x、Office） | 中 | 中（控件树不稳、会抢焦点） | 未做 |
| Vision（截图 + OCR + 坐标） | 兜底 | 低 | 未做（且必须先有人确认） |

### 13.2 三条纪律

1. **只连本机回环**（`http://127.0.0.1:<port>`，协议白名单 `http://` / `https://`）。
   远端调试端口一旦暴露，等于把浏览器交出去。
2. **开关关着连端口都不摸**：`GUI_CHANNEL` 三态，默认 `off`；`off` 直接抛 `blocked`，
   连 `/json` 都不请求——免得一个「顺手读一下」变成后台扫描。
3. **只读**：本片没有任何 `act`（不点、不输、不导航）。写动作要等状态差异与三级授权一起到位。

### 13.3 形状与错误码

`GuiSnapshot(target, url, title, text, taken_at, truncated)` + `digest()`（`sha256(url|title|text)[:16]`，
将来写回执的 `state_before/state_after` 就用它）；正文只做三件事：去行尾空白、压连续空行、按字数截断
（≤4000 字）——**不摘要、不重排**。

错误码是封闭集合：`not_connected`（端口没开 / 没有 ws 地址）/ `no_target`（选不到页面）/
`timeout`（命令没回来）/ `unsupported`（页面里报错、返回值不是 JSON、backend 不支持）/
`blocked`（开关没开 / 端点不是本机 http(s)）。「读不到」与「读到了但没有」必须分开。

### 13.4 它长在工具包的哪里

驱动本身**不是工具**：判看到的是一个 effects = `read` 的工具 **`gui_snapshot`**
（`core/tools/builtin.py`），参数只有一个 `target`，返回「标题 + URL + 正文」。三件事因此成立：

1. **不需要任何授权**（策略矩阵里 `read` 是 auto 档），也不占写预算；
2. **开关关着时它返回 `ui_blocked`，不是 `not_connected`**——「不许读」和「读不到」是两回事，
   判与量具必须能分开；
3. `digest()` 留在快照里，将来 `act` 的 `state_before / state_after` 直接用它，不必另造指纹。

### 13.5 `act` 的第一小步：只跳转（`gui_navigate`）

`act` 的第一步不是点击，是 `Page.navigate`。为什么是它：**可逆**（跳错了再跳回来就行；点错了就是第二单）、
**证据好取**（跳转前后 `url / title / text` 一定变，`diff_snapshots()` 直接给出 `state_before /
state_after / changed`；点击常常「看不出变了没有」）、**不靠幂等键**（同一地址跳两次等价于一次）。

四条纪律：

1. 协议白名单 `NAV_SCHEMES = ("http://", "https://")`：`javascript:` / `file:` / `data:` / `chrome:`
   一律 `blocked`——前两者等于在页面里执行代码或读本地文件。`check_nav_url()` 与驱动层各拦一次
   （校验是纯函数，可穷举；驱动层再拦是防绕过）。
2. effects 是 `ui_control`，所以**默认只登记不启用**：`build_registry(enable_ui_control=True)` 才
   `enable()`，默认连 prompt 清单都进不去（工具包 §5 的 ≤6 个名额不该被它占）。
3. 三级授权里它是 `confirm` 档：一行 `Approval(job_id, step_n, action_hash)` 才能解冻（办 §8）。
4. 回执必须带 `state_before / state_after / changed`；`changed` 空就是 `no_change`（当成失败），
   不许拿「请求发出去了」当成功。

`expect` 是「我要看到的那句话」：给了就轮询（`NAV_POLLS=3` × `0.2s`）直到它出现在 URL / 标题 / 正文里，
回执记 `expect_found`——这是「到底跳过去了没有」唯一可判的证据。

**它仍然不会点击、不会输入**：那要 `ui_control` 的三条判据（前台可见 / 标题匹配 / ≥100 像素变化）
与点击的证据链一起到位（工具包 §4.1）。

### 13.6 `act` 的第二步：真点击（`gui_click`）

点击比跳转危险一个量级：**不可逆**（点到「提交订单」就是第二单）、**常常看不出变了没有**。
所以它动手之前要过两道闸、动完要量一件东西，缺任一条就是失败：

| 判据 | 怎么判 | 不满足时 |
|---|---|---|
| 前台可见 | `foreground_window_title()` 的标题里含声明的 `window_title` | `ui_blocked` |
| 标题匹配 | 目标页面自己的 `title` 非空（空标题 = 不知道这一下点在谁身上） | `ui_blocked` |
| 真的变了 | 点击前后各截一张，`count_changed_pixels(before, after) ≥ MIN_CHANGED_PIXELS`（100） | `no_change` |

三条判据的**唯一裁决者是工具包的 `can_ui_control()`**（`core/tools/registry.py`），驱动层只负责照办：
前两条在动手之前判（不成立就一步不动），第三条只能在事后量，量不到就由调用方判成失败。

四条纪律：

1. effects 仍是 `ui_control`：默认只登记不启用，`build_registry(enable_ui_control=True)` 才 `enable()`；
2. 三级授权里是 `confirm` 档：一行 `Approval(job_id, step_n, action_hash)` 才能解冻（办 §8）；
3. **证据必落盘**：点击前 `data/evidence/<turn_id>_click_before.png`、点击后 `…_click_after.png`
   （名字**定死**、不覆盖，同一回合重名时加 `-2` / `-3` 后缀；不用自增序号——序号随进程历史漂移，
   重跑一次就对不上上一次的证据）。回执写 `state_before / state_after / changed{pixels}` 与两个证据路径
   ——没有截图就没有证据，没有证据不算做成；
4. 选择器只认 CSS：`check_selector()` 拦空串与超长（`SELECTOR_MAX_CHARS = 200`）、`document.querySelector()`
   拿不到元素或元素矩形宽高为 0 一律 `no_target`；坐标取元素中心，派发 `mousePressed` + `mouseReleased`
   两次（`button="left"`、`clickCount=1`）。

它仍然**不会输入文字**：`Input.insertText` 在整个驱动里一次都没有（`tests/test_gui_cdp_reader.py` 有静态断言）。
输入要单独一刀：写进去的字就是发给对方的内容，得先想清楚「填了什么」怎么留证。

## 13.7 微信：读库、写 UI，这一片只到「填进输入框」

微信有两条**互不相干**的通道，别混：

| 通道 | 技术 | 位置 | 特点 |
|---|---|---|---|
| 读 | SQLCipher 解密后的明文库 | `db/decrypt.py` → `data/decrypted/wechat/<account>/merge_msg.db` | 全量、可回溯、拿得到撤回（`WECHAT 的 REVOKE = 10002`）、**不需要窗口在前台** |
| 写 | 真实 Windows 输入队列（`SendInput`） | `core/execution/wx_human.py` | 要窗口在前台；微信 4.x 不是可调试的 Chromium，CDP 够不着 |

所以**不读控件树**：UIA 那一套对微信是多余的一层，库里已经有原文。

这一片（`core/execution/gui/wechat.py`）只做「半程」：

```python
snapshot(chat, *, db_path=None, account_id="", limit=20, max_chars=4000) -> GuiSnapshot
read_recent(db_path, chat="", *, limit=20) -> list[dict]
render_lines(rows) -> str                      # HH:MM 我/对方: 正文
fill_message(chat, text, *, deps=None, turn_id="", evidence_dir="data/evidence") -> FillResult
```

- `snapshot()` 读的是**库**，不是界面：表名认 `Msg%` / `MSG%` / `ChatMsg%`，列名认
  `str_talker/StrTalker`、`str_content/StrContent`、`is_sender/IsSender`、`create_time/CreateTime`
  两套；取不到列的表整张跳过（宁缺勿猜）。
- `fill_message()` 的顺序是**找窗口 → 开聊天 → 聚焦输入框 → 粘字 → 核对**，`FillResult.sent`
  恒为 `False`（`as_receipt()` 里也写死 `False`）。
- 证据名定死：`<turn_id>_wechat_fill_before.png` / `_after.png`，同名加 `-2`、不覆盖。

四条纪律（`tests/test_gui_wechat.py` 有静态断言）：

1. **不按回车**：模块里 `press_enter` / `VK_RETURN` 一次都不出现；
2. **不走发送口**：不 import `core.speech`、不调 `wx_executor.send`——发送仍必须过出口
   （`core/execution/wx_executor.py` 里 `SEND_TEXT 必须经由 OutboundGateway 发送` 的纪律不改）；
3. **开关能一键停**：`WECHAT_UI` 三态（`off` 连窗口都不找 / `shadow` 只读库 / `on` 才碰界面），默认 `off`；
4. **读失败少看一条，写失败不发一句**：库打不开 → `not_connected`，窗口标题不含「微信/WeChat」→
   `not_connected`，输入框没聚焦 → `no_target`，三种情况都不动界面。

**下一步（还没做）**：回执不靠像素差——库里 `local_id` 与 `msg_svr_id`（服务器消息号）能对账，
发送后回读一行命中「`is_sender=1` + 目标会话 + 正文一致」才算发出去。这比 `gui_click` 的
「像素差 514101」强一个数量级，也是唯一能让「重复发送率 0」这个硬指标在微信上真的算得出来的办法。

### 13.8 读侧的真库形状（2026-10-21 实测，不是推测）

读的是 `data/decrypted/wechat/<wxid>/merge_msg.db`（明文库），同级还有 `contact.db`。真库长这样：

| 事实 | 形状 |
|---|---|
| 会话表 | **每个会话一张表**，表名 `Msg_<md5(会话 id)>`；**没有** `str_talker` 列 |
| 身份字典 | `Name2Id(user_name)`；`Msg_*.real_sender_id` 就是它的 `rowid` |
| 「是不是我」 | `real_sender_id` == 自己在 `Name2Id` 里的 rowid |
| 正文 | `message_content`：可能是 `str`，也可能是 **zstd 压过的 bytes**（`WCDB_CT_message_content` 标记）；`compress_content` 是压缩副本 |
| 时间 | `create_time`（秒） |
| 昵称 | 不在消息库里，在兄弟文件 `contact.db` 的 `contact(remark, nick_name)` |

渲染四条纪律（每一条都是被真数据打出来的）：

1. **先解压再念**：`zstandard` 解不开就念占位，绝不把字节当正文（最初把 `b'(\xb5/\xfd…'` 念进了 prompt）。
2. **先剥发送者前缀，再判类型**：群消息正文常以 `wxid_xxx: ` 或 `xxxxx@chatroom: ` 开头。
   顺序反了会漏——`10000000005@chatroom: <?xml …` 这种行在「先嗅 XML」时前缀不是 `<`，嗅不出来。
3. **卡片/系统一律念占位**：`<msg>` / `<appmsg>` / `<sysmsg>` / `<?xml` 一律 `[链接/文件]` / `[系统]`。
   XML 进 prompt 等于把结构噪音当话听。
4. **昵称查不到就念「对方」，不念 wxid**：`_looks_like_id()` 挡掉 `wxid_` / `@chatroom` 形状的名字。

兼容：老形状（一张大表 + `str_talker`）仍能读，走 `_rows_legacy`。量具：7 个群各取 20 条全量跑，
**XML 泄漏 0**、zstd 正文可读、自己/对方分辨正确；`tests/test_wechat_db_read.py` 25 项钉住。

**仍未做**：发送后回读对账（`local_id` + 服务器消息号）——见 §13.7 末尾。

### 13.9 「现在开着哪个会话」：按可信度排队，认不准就弃权

内容以数据库为准（§13.8），但**「哪个会话」只能靠屏幕**——数据库只知道「最近有消息」。
所以这里不猜，只排队问，并把证据档写进回执标题。

| 档 | 来源 | 置信度 | 它到底知道什么 |
|---|---|---|---|
| 1 | `explicit` | 1.0 | 调用方直接给会话 id——不用猜 |
| 2 | `anchor` | 0.9 | 我们自己打开/确认过、且没过期的那一个（`core/execution/wx_chat.py::active_chat_id()`，hwnd + 顶栏指纹） |
| 3 | `ocr` | 0.7 | 屏幕上顶栏读到的显示名，经 `contact.db` 反查成会话 id |
| 4 | `recent_db` | **0.3** | 只是「最近有消息的那个」——**不是**你屏幕上那个 |
| — | `ambiguous` | 0.5，且 `chat_id` 空 | 名字认不出或**重名**：错会话比没会话更坏，弃权 |
| — | `none` | 0.0 | 什么都没有 |

四条纪律：

1. **数据库那档必须自报家门**：`snapshot()` 的标题在 `recent_db` 时会写「（最近活跃，不是屏幕上的会话）」，
   不许冒充屏幕——prompt 里一句假话比没读到更贵。
2. **重名弃权**：同名会话多于一个 → `GuioError("no_target")`，不随机挑。
3. **探针不许打挂回合**：锚点/OCR 抛异常只降档，不向上冒。
4. **锚点会过期**：`_ACTIVE_TTL_S`（默认 300 s）以外一律作废。

实测（本机）：无 chat → `recent_db 0.3`；给锚点 → `anchor 0.9`；OCR 读「概率论与数理统计计算机」→ `ocr 0.7` 命中；
读不存在的名字 → `ambiguous`；快照标题 `微信 · 遥途逢星溯随天赴山海 · 20 条（最近活跃，不是屏幕上的会话）`。
`tests/test_wechat_current_chat.py` 23 项钉住。

**仍未做**：顶栏 OCR 探针还没接真窗口（`ocr=` 参数留好了位，`wx_chat.get_ocr()` 那条路要真窗口才敢接）；
`msg_message_fts.db` 的全文索引只有 9985 行、**只覆盖 4 个会话**，所以不能当全量检索用。

### 13.10 「发出去了」怎么证明：回读微信自己的库

仓库里原本就有发送路径（`core/execution/wx_sender.py`），它证明的是**发之前**——
OCR 确认「开的是对的人」。但「按了回车」和「消息真的发出去了」之间还有一道缝：
输入法吃掉回车、风控拦下、网络断在本地落库之前……这些都会让界面看起来成功。

微信自己给了唯一硬证据：消息**写进本地库之后**才会有 `server_id`（服务器消息号）。
所以判据是三条同时成立：

| 条件 | 查什么 | 没有它就会怎样 |
|---|---|---|
| 有新增 | 行号 `> 按下之前的 max_local_id` | 历史里某句一模一样的话冒充这次 |
| 是我发的 | `real_sender_id == 自己那行` | 把别人刚说的话当我们发出去的 |
| 内容相同 | 抹空白后 sha256 相同 | 认错行，回执指向别人的消息 |

三种结果，**没有第四种**：

| 状态 | 含义 | 回执 `ack` |
|---|---|---|
| `sent` | 库里出现了这一行，且拿到了 `server_id` | `platform_id` |
| `unconfirmed` | 本地库有了，`server_id` 还没回来（正常会有，但可能晚） | `unconfirmed` |
| `failed` | 按了回车，回读窗口里库里没有我们这句 | `error` |

四条纪律：

1. **失败不重发**。`failed` 就是 `failed`。「再试一次」是重复发送的唯一来源，而重复发送率必须为 0。
2. **影子档不碰不可逆动作**。`WECHAT_SEND=shadow` 连填字都不做——按住回车回不了头，
   不可逆动作没有影子档。
3. **回读失败不打挂回合**。读库抛错只降级成 `failed`，不向上冒。
4. **回执照落 `delivery_receipts`**（迁移 65），`ref=wechat#<local_id>`；
   记账失败不影响回执本身。

回读节奏：8 次 × 0.4 s ≈ 3.2 s（本地落库通常 < 1 s，余量留给「网络慢但真发出去了」）。

实测（本机真库，只读、不发送）：

```
max_local_id = 31
local_id 27  server_id 4700371881238744822  mine=True   "flask方面，我之前有用过，会"
local_id 30  server_id 4871318051106822465  mine=False  "会react应该问题不大"
```

`tests/test_wechat_send_verify.py` 34 项钉住（含「内容对不上不算」「不是我发的不算」
「回读抛错不崩」「回执落库失败照返回」「只发一次：`fill_message` 与 `press_enter` 各只有一个调用点」）。

**仍未做**：从没真按过回车（上面那张表的实测是**只读，不发送**）。`WECHAT_SEND` 的转正条件
就写在这上面：「真发过并回读到 `server_id`、重复发送率 0」——在没人盯着的情况下按回车，
是这一层最后一次要人来开的闸。

接线见 §13.11：它现在是「一件事」的 `external_send` 步唯一被允许的实现，
不再是一个谁都能显式调用的能力。

### 13.11 接进一件事：外发仍然只是一个注入的回调

`send_and_verify()` 长出来了，但「谁能在什么时候调它」比它本身更重要。2026-10-21 的接法：

- **执行器不 import 它**。`core/jobs/executor.py::_run_external()` 只认调用方递进来的
  ``external(to, text, *, turn_id)`` 回调；没有回调就 `no_sender`。
- **回调的唯一来源是 `core/routing/turn_pipeline.py::_external_sender()`**，而它里面的
  实现固定一行：`wechat_send.send_and_verify`。`WECHAT_SEND` 不是 `on` 就返回 `None`。
- **按回车仍然只有那几处**。`scripts/check_topology.py` 规则 8 用 `ENTER_SITES` 白名单钉住
  `core/` 下所有出现 `press_enter(` / `VK_RETURN` 的文件（当前 5 处，每处都有登记理由）。

于是「对外说话」在微信这条线上仍然只有一个能被叫到的实现，多出来的只是**说话的理由**
（一件事的最后一步，而不是某个回合的判决）。三条不许：

1. 不许在执行器里判「这句话该不该说」——那是判的事，执行器只认 `step.action` 的正文；
2. 不许在 `wechat_send` 之外再写一个按回车的发送器；
3. 不许重试 `failed`（重复发送率必须为 0）。

### 13.12 「切到那个会话」怎么算成功（2026-10-21 真机重写）

- **事故**：搜索列表的 OCR 会截断（`文件传输助手` 读成 `文件传输...`），于是
  `_verify_search_result` 经常拒绝一个其实已经打开的会话——好的被当成坏的。
- **改法**：不在**搜索结果列表**上验收，改成「按回车打开 → 读会话顶栏 → 顶栏里必须有这个名字」：
  `core/execution/wx_chat.py::open_chat_strict(who, raw_who="")`。顶栏是会话里唯一稳定的大字，
  只读顶部一条，截断风险远低于列表。
- **三条判据**（全过才算打开）：① 微信窗口在前台且不是最小化；② 顶栏文字里包含这个名字
  （`(3)`、`[草稿]` 这类前缀先剥掉）；③ 输入框能聚焦。
- **失败就是失败**：返回 `{"ok": False, "error": ...}`。调用方
  （`core/execution/gui/wechat.py::fill_message`）**必须看返回值**——不看就是静默地把话打进
  别的会话。这是 2026-10-21 真实踩到的 fail-open。

### 13.13 微信多久才把话写进库（实测 26 秒）

- **现象**：回车之后立刻回读，库里没有；等 20 秒还没有；再等，26 秒才出现
  （`local_id=87`、`server_id=4324064563963797869`）。
- **结论**：回读窗口必须覆盖落盘延迟。`core/execution/gui/wechat_send.py` 现在是
  `POLL_INTERVAL_S = 1.5`、`POLLS = 16`（≈24 秒，另加每轮刷新耗时）。
- **回读前必须刷新快照**：`core/execution/gui/wechat.py::refresh_db()`
  （`decrypt_and_merge(..., incremental=True)`）；`_external_sender()` 把它当 `refresh=` 传进去。
  不刷新就是拿旧快照去证明「没发出去」。
- **三态判定**（`send_and_verify`）：
  - 回读到 `mine=True` 且指纹一致 → `sent`（`platform_msg_id = server_id`）；
  - 等满、库里没这一行、但**输入框已空**（`message_box_has_text() is False`）→
    `sent_unconfirmed`（说出去了，只是没拿到证据）；
  - 等满、库里没这一行、输入框里字还在（或探针拿不准）→ `failed`。
- **真跑**：`status=sent`、`platform_msg_id=4324064563963797869`、`client_msg_id=local:89`、
  `ref=wechat#89`、耗时 29.2 秒（含两次解密）。

### 13.14 群里 @ 一个人：先验名单，再让人看见

- **「@」不是文字**。在群里打 `@小奇` 只是一串字符，微信**不会通知任何人**。真 @ 必须走成员名单：
  打 `@` → 弹出名单 → 选中 → 输入框里出现 `@小奇`（chip）。所以「文本里带 @」和「真的 @ 到他」是两件事。
- **实现**：`core/execution/wx_chat.py::mention_member(name)` —— 打 `@名字` 筛名单 → OCR 读名单 →
  **只选唯一匹配**：0 个（名单里没有）或 >1 个（同名多人）都失败。`@ 错人比不发更糟`，因为通知会
  真的送到别人手机上。失败时清空输入框、一格字不填、不按回车；回车后还要在输入框里读到 `@名字` 才算成功。
- **顺序**：@ 必须在正文之前——名单是靠「`@` + 前缀」筛出来的，先把正文打进去会把名单筛空。
  `fill_message(chat, text, mention="小奇")` 把这一步放在 `paste` 之前，失败抛
  `GuiError("unsupported", "mention_failed…")`，于是 `send_and_verify` 直接 `failed`、不按回车。
- **2026-10-21 真机结论（重要，别再重复踩）**：
  1. **敲字永远不会变成 @**。`type_unicode("@Elaina")` 之后输入框里是**普通文字**，
     证据：一次退格只少一个字（真 chip 会整体消失）。所以「文本里看到 @名字」不能当成 @ 成功。
  2. **名单是独立顶层窗口**，不在主窗口截图里：`hwnd` 属同一 pid、`class='Qt51514QWindowToolSaveBits'`、
     大约 327×180、贴在输入框上沿。主窗口截图里「输入框上方 300px」读到的是聊天正文，不是名单。
  3. **病因不是 DPI，是 OCR 文本框落在行的下半部**：`忽念` 那一行的 OCR 文字 y≈1090，
     而它真实的 `ListItemControl` 矩形是 **1038–1086**（中心 1062）；点 1090 已经进了下一行
     （`Elaina` 1086–1134），于是「点忽念插进来 Elaina」。两个坐标系都是物理像素
     （主窗口 win32 `(-9,0,1289,1537)` vs UIA `(1,0,1277,1525)`，差的 12px 是 DWM 边框），
     **没有 1.5 倍缩放错位**。
  4. **修法：名单改读 UI Automation**（`_picker_items()`）：同一 pid 的独立顶层窗口
     （`Qt51514QWindowToolSaveBits`）里，`auto.ControlFromHandle(hwnd)` → 递归找
     `ListItemControl`，直接拿 **Name + BoundingRectangle**。实测名单两项：
     `忽念 (301,1038,544,1086)` / `Elaina (301,1086,544,1134)`，名字与矩形都精确。
  5. **仍然 fail closed**：名单里没有 / 同名多行 / 点完输入框不是恰好一个 `@名字` /
     退格还剩字（说明只是文字不是 chip）—— 四条都失败且**不按回车**；`dry_run=True` 只读名单不点。
  6. 备用路线（UIA 读不到时）：③ 把「选谁」交给人确认（`pending_approval` 的另一种形态）。
- **仍未做**：`external_send` 的动作格式里还没有 mention 位（`send:群名|@小奇 在吗` 目前只会发纯文本）；
  真机上还没在群里发过（代码与单测齐了，等一个安全的目标群）。

## 13.15 `@` 怎么进到动作串里（2026-10-21）

「在手的事」里的界面步，动作串只写得下「工具名 + 半句话」；而 @ 是**两个动作**
（插 chip + 打正文）。约定就写在一行里：

```
send:鲸鲸的测试群|@小奇 在吗
```

- `|` 左边是收件人；右边若以 `@名字` 开头，名字交给 `fill_message(mention=…)` 去插真 chip，
  **正文里不再留那份 `@名字`**（否则是「chip + 文字」，看起来像 @ 了两次）。
- 只有 `@` 没有正文也合法（就是拍一下）；`@` 后面没有名字（`@ 在吗`）不认，当普通正文。
- 拆这一层的是 `core/jobs/executor.py::split_mention`；执行器只把 `mention=` 交给注入的发送器，
  发送器（`wechat_send.send_and_verify`）再往下传给 `fill_message`。

## 13.16 窗口唤出：托盘里也要救得回来

微信 4.x「关窗口」= 隐藏到托盘（`IsWindowVisible` 可能是 False），而 `ShowWindow` 在**低完整性**
进程里还会 `err=5`（本项目踩过：`.venv_it` 被打成 Low 标签，`SetForegroundWindow` 全失败）。
`core/execution/gui/wechat.py::wake_window()` 因此是三段：

| 段 | 动作 | 为什么 |
|---|---|---|
| 1 | UIA `Show()` / `SetFocus()` | Qt 窗口隐藏时，UIA 比 win32 更常成功 |
| 2 | `wx_vision.activate_window()` | SW_SHOW + SW_RESTORE + AttachThreadInput + BringWindowToTop |
| 3 | 验：`GetForegroundWindow()==hwnd` 且 `IsIconic()==False` | 只信结果，不信调用返回值 |

`fill_message()` 在「前台不是微信」时先调它；**唤不出来就 `no_target` 停下**，不往别的窗口敲字
（出过事：字打进浏览器、回车发给当时开着的那个会话）。真机读数：`wake_window() -> True`，
1.2 秒，`fg==hwnd`，`iconic=False`。

## 13.17 控件树读屏：`gui_state`（只读）

OCR 只能看到字；`core/execution/gui/uia.py` 读的是**控件树**：角色、名字、矩形、能不能动。

- 形状：`[深度] 角色 "名字" (x,y,w,h) *可动`，先序；空名字的容器也留着（它们提供结构）。
- 预算：`MAX_ELEMENTS=500` 个节点 / `MAX_CHARS=4000` 字，超了标 `truncated`
  （借 Windows-MCP 的「有预算的树」思路）。
- 选窗口：`target` 空 = 前台；否则标题或类名子串，**只认唯一命中**——两个窗口都叫「微信」就
  `no_target`（@ 名单弹窗开着时正是这种情形，宁可不读也不猜）。
- 三档开关：`GUI_CHANNEL=off/shadow` 一律 `ui_blocked`，**连 UIA 都不初始化**。
- 实测（微信 4.x，2026-10-21）：63 个节点，能看到导航栏按钮（微信 / 通讯录 / 收藏 / 发现）与
  窗口按钮；聊天区是自绘的、没有逐条消息节点——所以微信的**内容**仍然只能从库里读（§13.8），
  控件树只用来定位「哪里能点」。
- Windows-MCP 里另外两件值得抄、这次没做的：`App` 工具的窗口切换（已在 §13.16 用别的路子实现）、
  动作建议表（每个角色给「建议的动词」，我们暂时只标 `*可动`）。

## 13.18 打字：判据是「值变了没有」，不是像素

`gui_input(selector, text)` 是 `ui_control` 的第三个动作（读屏 → 跳转 → 点击 → **打字**）。

| 项 | 取值 |
|---|---|
| 输入方式 | CDP `Input.insertText`（页面内合成事件：不抢系统焦点、不动剪贴板） |
| 动作 | 聚焦（`el.focus()`）+ 选中原值（`el.select()`）→ 插入文字 → 读回输入框的值 |
| 判据 | **输入框的值**变没变（`value_before` / `value_after` / `changed{value_len,value_sha256}`） |
| 前置两关 | 前台（窗口标题包含声明）、页面有标题——不过就一步不动 |
| 文字限制 | ≤200 字；不许 NUL / CR / TAB（这两个在网页里是「切换焦点 / 提交」，会把打字变成回车） |
| 失败 | 元素找不到 / 聚焦失败 → `no_target`（一个字都不输）；值没变 → `no_change`（不许当成功）；没连上 → `not_connected` |

三条纪律：

1. **第三条判据换证据**：打一个字只变十几个像素，用 `can_ui_control` 的 100 像素门槛会把「打成功」判成失败。
   所以打字时第三条用 `value_changed`（`can_ui_control(..., value_changed=True/False)`），**两个证据不会同时用、也不会都不用**。
2. **只在 `type_text` 里出现 `Input.insertText`**：读屏 / 跳转 / 点击三条路径一个输入事件都没有（测试按方法切片钉住）。
3. **不模拟按键**：整个驱动没有 `dispatchKeyEvent`——「按下回车」是另一件事，走微信那条路（`wx_chat.press_enter`）。

已知限制：受控输入（React/Vue 把值存在自己的 state 里）可能出现「DOM 上的值对了，但框架 state 没更新」；
这类页面提交时可能读不到。真遇到时，回执里 `value_after` 是对的，但下一步的结果会不对——那就该停手交人。

### 13.18.1 真机验证（2026-10-21，Edge + CDP 9223）

| 场景 | 结果 |
| --- | --- |
| 往空输入框打 12 字 | `value_before=''`、`value_after='鲸鲸打字试验 19:58'`，`changed={'value_sha256','value_len'}`，`criteria={'value': True}` |
| 再打一次（覆盖写） | `'鲸鲸打字试验 19:58'` → `'第二次'` |
| 选择器不存在 | `GuiError(no_target)`，一个字都不输 |
| 文字里带 `\r` / `\t` | `blocked`：「要输入的文字里含控制字符（NUL/CR/TAB）」 |
| 文字里带 `\n` | 允许（浏览器按 HTML 规则归一成空格：`'带\n换行'` → `'带 换行'`）；单行输入框里它不构成提交流，多行文本域里它是正常换行 |

结论：**打字这条路的判据站得住**（值真的变了），且失败路径都 fail closed。

## 13.19 发送回执：`platform_id` 还是 `unconfirmed`

微信**没有**「平台返回消息号」这回事。旧路径（`rhythm → outbound → WxSenderProvider`）
的「成功」只是「输入框空了」——那是弱证据，可能是换行，也可能是别的窗口吃掉了回车。

现在的口径（真话优先，三级）：

| 拿到什么 | 报什么 | 用什么证明 |
| --- | --- | --- |
| 库里出现 `mine=True` 且正文一致的新行 | `ack=platform_id` + `local_id` + `server_id` | `max_local_id` 基线 + `rows_after` 回读 |
| 发出去但库里没有 | `ack=unconfirmed` | 输入框空了（弱证据，不许升格成 `platform_id`） |
| 发送失败 | `ack=error` | provider 的错误串 |

四条纪律：

1. **基线必须在按回车之前取**（`ack_baseline(who)` 在 `press_enter()` 前面），否则回读会把上一条消息当成这一条。
2. **回读要刷新库**（`wxgui.refresh_db()` 增量解密），旧快照永远读不到刚发的那行（实测落盘 26 秒）。
3. **只在 `WECHAT_SEND=on` 时做**：默认 off 不读库、不变慢，逐字与接线前一致。
4. **回执是旁注**：读库失败、`delivery_receipts` 写失败一律降级为 `unconfirmed` / 只 log，
   不许把「已发出」改判成失败，也不许把「没证据」写成「有号」。

## 13.20 配方：加一个 App = 加一个文件（U-20）

前面十六条写的都是"**某一次**动作怎么做得可靠"。这一条换问题：**下一个 App 从哪来**。

答案不是再写一个 `gui_xxx` 工具，而是一份声明——`configs/apps/<app>.yaml`：

```yaml
name: demo_reader
version: 1
enabled: false            # 由人改 true
window_title: 记事本       # 三条窗口标识至少一条
window_class: Notepad
exe: notepad.exe
effects: [read]           # read / write_local / ui_control；external_send 一律拒
steps:
  - n: 1
    do: wake              # wake / navigate / click / type / wait
    expect: 前台窗口标题里出现「记事本」
    safe_point: true
```

| 词 | 意思 |
|---|---|
| `wake` | 把目标窗口唤到前台（三段式，见 §13.16） |
| `navigate` | 在页面里跳一个 http(s) 地址（CDP 才有） |
| `click` | 点 `target` 一个元素/控件 |
| `type` | 在 `target` 里输入 `text` |
| `wait` | 等 `wait_s` 秒（0 < x ≤ 30） |

`target` 的语义**由 backend 决定**：CDP 是 CSS 选择器，UIA 是控件名。配方不该知道
自己跑在哪个 backend 上——这就是"换 harness 不用改配方"。

四条纪律（`core/execution/gui/recipe.py` 逐条实现，`tests/test_app_recipes.py` 逐条钉住）：

1. **每步 `expect` 必填**。没有 `expect` 的步骤等于"永远成功"，是假绿的源头，所以
   加载期就拒（`empty_field`）。
2. **未知字段报错**。`expect` 拼成 `expec` 若被静默忽略，整条配方就变成永远成功
   （`unknown_field`）。
3. **`external_send` 不许写进配方**（`forbidden_effect`）。发消息只能走出口注册表（R3），
   配方只能在本机界面上动手。
4. **默认不启用**（`enabled: false`）：人改 true，执行器还要过三级授权。

另外三条加载期判据：步号必须从 1 起连续（不许跳号/重号）；有 `click`/`type` 却没写窗口
标识一律拒（`no_window`——事后无法确认点在了哪个窗口）；声明 `effects` 时必须是"步骤需要的
超集"（不写则按步骤推导）。

**现在到哪一步**：加载器有了、模板有了（`configs/apps/_example.yaml`，下划线开头不加载），
**执行器还没有**——所以今天 `enabled_recipes()` 的调用者只有测试。下一步（U-21）才是
"按配方走一遍"的 backend 抽象。

## 13.21 撤回：菜单里的「撤回」**只在 2 分钟内**存在（U-25）

真机时间线（2026-10-20，`鲸鲸的测试群`，右键自己的消息）：

| 距发出 | 菜单里有什么 |
|---|---|
| 7.8 秒 | `复制 / 放大阅读 / 翻译 / 搜一搜 / 转发 / 收藏 / 多选 / 提醒 / 引用 / `**`撤回`** |
| 3 分钟以上 | 同一份菜单，**最后一项「撤回」消失**，其余都在 |

所以撤回不是「技术上做不到」，是**窗口只有 120 秒**。`send_and_verify` 真发一次 15–30 秒，
撤回再走一遍约 13 秒——发出后立刻撤，来得及；拖一轮、或重试一次，就过头了。

四条真机教训（每条都踩过）：

1. **菜单是另一个顶层窗口**（类名 `Qt51514QWindowToolSaveBits`，同 pid、可见、约 315×296）。
   OCR 读它三次得三种结果（同一份菜单读出 4 / 7 / 10 项，偶尔把「翻译」和「搜一搜」粘成一行），
   菜单项**只能靠 UIA**（`MenuItemControl.Name` + 矩形中心）。
2. **坐标有两套**：OCR 给窗口内坐标，鼠标要屏幕坐标。少加窗口原点，右键就落在屏幕左上，
   菜单不出现（真机表现：`no_menu`）。
3. **只认正文区**：左侧会话列表会把同一条消息的预览也念出来，右键它会点在列表上，菜单不出现。
   用 `wx_vision.detect_layout()` 的 `chat_left` / `input_box` 排除。
4. **右键不能用 SendInput**：微信 4.x 对合成短按右键没反应，必须
   `SetCursorPos` + `mouse_event` + 按住 180 ms（`wx_human.click_menu()`，全仓只此一处）。

fail closed 六条（任一成立就不点，且不乐观报成功）：开关关着 / 没给会话 / 没给正文 /
屏幕上找不到这句（或有两句一模一样）/ 菜单里没有「撤回」/ 点完看不出变化
（那句还在，且没出现「撤回了一条消息」）。

### 被刷走了怎么办：拿账本里的链路一步步逼近，不要盲翻

「屏幕上找到那一句」这个前提会被刷屏打破。第一版做法是「滚一屏、截图、再找」——**这是瞎猫碰死耗子**：
估不准一屏几行、估不准滚轮一格走多远、每次都要重新截 2560×1600 再 OCR，翻 12 屏也可能白翻。

正确的是**用库里的有序链路当路标**（`wechat.recent_rows(chat)`：`local_id` 单调、正文、时间）：

1. 屏幕上随便挑几条**在库里只出现一次**的行当**锚点**（同一句话说过两遍的不当锚点，宁可少认几个）；
2. 每对锚点给出一个偏移「屏幕第 i 行 = 库里第 j 条」，取**中位数**当这一屏的基准（抗个别错配）；
3. 目标那句在库里的下标已知 → 它在上方还是下方、差几行，**一目了然**；
4. 一行约对应 `ROWS_PER_PAGE = 5` 行的滚轮量，差 175 行就一次滚 35 屏（夹在 `MAX_PAGES_PER_ROUND = 20`），
   而不是一格一格试；滚完**重新对齐**再算——每轮都把误差纠回来，所以通常两三轮到，最多 `MAX_APPROACH_ROUNDS = 4` 轮；
5. 停在三种情况之一：找到（点它）、目标落在两锚点之间但屏幕上没有可点的行（媒体/被折叠 → 停手不猜）、
   锚点不足（屏上全是重复句/OCR 全丢 → 退回盲翻 `BLIND_MAX_PAGES = 3`）。

为什么这条路稳：**库是账本，屏幕只是它的一个窗口**。屏幕会动、会滚、会被折叠，但 `local_id` 与 `create_time`
 的顺序不会变——只要有几个锚点，就能把「屏幕上第几行」换算成「库里第几条」。

纪律（不变的部分）：

- 找到了：撤回，回执写「先逼近了 N 屏才找到」，**滚回原位**——撤回不该把用户视野留在半天前。
- 翻不到：滚回原位，报 `not_found: 屏幕上找不到这一句（逼近 4 轮 × ≤20 屏也没找到）`，一次点击都不发。
- 滚轮只在鼠标挪到**正文区中心**之后才发（`_Deps.scroll`），否则滚的是左侧会话列表。
- 锚点必须**唯一**：`_target_index()` 在库里命中多行就返回 `None`（同一句话说过两遍 → 不猜哪条）。
- 系统消息（`<sysmsg>` / 撤回提示）在 `recent_rows()` 里留空正文，不参与锚点匹配。

2 分钟这一层不写在撤回里，写在**调用侧**：`core/speech/correction.py::can_revoke(receipt, now)`
按回执时间先判，超了就直说「只能更正，不能撤回」——宁可只更正，也不要瞎点。

### 13.22 换手不换工具：backend 注册表（U-21）

判看到的是五个工具（`gui_snapshot` / `gui_state` / `gui_click` / `gui_input` / `gui_navigate`），
**换一只手不该换一套工具**。所以驱动层只做一件事：把「工具要做的动词」与「哪只手能做」对上。

| backend | 会哪几个动词 | 需要什么 | 今天 |
|---|---|---|---|
| `cdp` | `snapshot` `state` `click` `type_text` `navigate` | 本机调试端口 | 在用 |
| `uia` | `state` | 前台窗口 | 在用（只读） |
| `adb` / `vision` | — | — | 没登记（ADB 做过又撤了：手机当前不需要） |

三条纪律：

1. **不认识的 backend 名 = `unsupported`**，绝不回退到默认那只手——回退就是静默点错地方；
2. **`GUI_BACKENDS=off`（默认）只放行已经在跑的两只**（`cdp` / `uia`）：将来加 Vision / ADB 时，
   它们只能在 `on` 档被选中，否则一个参数名就能绕过整片能力自检；
3. **动词不在说明书里 = `unsupported`**，不是「试试看」：`uia` 今天不做点击，
   `gui_click(backend="uia")` 必须当场失败，而不是退化成坐标点击。

落点：`core/execution/gui/backends.py`——`BackendInfo(name, verbs, needs, note)`、
`BACKENDS`、`register(info, factory)` / `unregister(name)`、`resolve(requested, *, verb, default)`、
`reader(requested, *, verb, default)`（**只构造不连接**，`CdpReader()` 构造时不发请求）。

工具侧只多一行：`backends.reader(params["backend"], verb="click", default="cdp")`。
`backend` 参数**暂时不进工具清单**（prompt 那 700 字很贵）：等第二只手真会写动词，
再决定怎么告诉判「你现在能点哪个软件」。


### 13.23 自检报告：现在能不能开工（U-22）

「跑不起来」和「跑起来会发错人」是两件事，自检要把它们分开说。入口：

```text
.venv_it\Scripts\python.exe -X utf8 -m scripts.selfcheck          # 人看
.venv_it\Scripts\python.exe -X utf8 -m scripts.selfcheck --json   # 机器看
.venv_it\Scripts\python.exe -X utf8 -m scripts.selfcheck --network  # 顺手探一下 CDP 端口
```

六节，一节一句话：

| 节 | 回答什么 | 失败时会怎样 |
|---|---|---|
| `capability` | 六项能力（完整性 / 会话 / DPI / 身份可读 / 可写 / 菜单） | 动手前就被 `require()` 挡住 |
| `backends` | 登记了哪几只手、各自会哪些动词 | 选了不存在的 backend = `unsupported` |
| `lease` | `input` 现在归谁、心跳几秒前 | 心跳过 2×TTL 会标「可能僵死」 |
| `wechat_db` | 解密库能不能读、最新一行多久前 | 读侧会 `not_connected` |
| `flags` | 开关组合自相矛盾的地方 | 比如 `wechat_send=on` 但 `wechat_ui=off` |
| `receipts` | 回执按状态计数 | 只用于看量具，不阻断 |

三条纪律：

1. **只读**：默认不连 CDP、不模拟按键、不写账本。`--network` 是显式开关；
2. **`➖` 是「没测」，不是通过**——`ok is None` 单独一个状态，不许并进 `True`；
3. **一节炸了不影响其它节**：每节独立 try，炸了记 ❌ 并写清原因。
   `capability` 失败时会补一句人话（「微信窗口可能最小化到托盘，先点开再看」）——
   报告是给人看的，不是给人猜的。

它**没有开关**：自检不改变行为，只描述状态；加开关反而会让「为什么没自检」变成一个新问题。

### 顺带修正：租约那一节的语义

`lease` 节原来只看 `data/.locks/input.json` 的心跳，于是**一次非正常退出留下状态文件**就会
永远报"可能僵死"。真话是锁早就被 OS 回收了（真机实测 0.05s）。新增
`core/execution/gui/lease.py::lock_is_free(resource, *, lock_dir=None)`：探一下区间锁、立刻放，
不写状态。三种结论：

| 现场 | 判 |
|---|---|
| 没状态、锁空闲 | ✅ 空着 |
| 有状态、锁**空闲** | ✅ **残留**（可以开工，`data/.locks/*.json` 可删） |
| 锁真被持有 | ❌ 现在不能开工（要不要 `taskkill` 由人定） |
