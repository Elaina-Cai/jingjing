## #1（2026-10-28，P0）一个提前删掉的 `all.stop` 让重启静默失败

**现象**
- 写入 `logs/all.stop` 后等 150 秒，端口 39871 一直不开，pid 没变，也没有任何报错。

**根因**
- `all.stop` 是**全关总闸**，只有 `scripts/supervisor.py:39` 读到它才会停整条链（引擎 + 调度器）。
- 我写完 9 秒就自己把文件删了，监管器还没轮到读 → 认为没有停止请求 → 继续守着老进程。
- 真正的「只重启引擎」开关是 `logs/loop.stop`：引擎每圈轮询到就自己退出**并删掉该文件**。

**处置（已完成）**
1. 改发 `logs/loop.stop`：11 秒后端口关闭，监管器 9 秒后拉起新进程（pid 28936 → 34924）。
2. 停止信号分两档写进 `docs/运行手册.md`：`loop.stop` = 只重启引擎，`all.stop` = 全链停。

**怎么验证**
- `logs/loop_engine.lock` 里的 pid 与 `logs/loop_engine.json` 的 `started_at` / `dry_run` 对得上，才算真的换了进程。

**怎么预防**
- STOP 文件**只允许目标进程删**；任何脚本/人不许在发出停止后自行清理。
- 重启流程禁止「写 → 立刻删 → 再等」，等待期间必须看到 pid 变化或端口变化才有下一步。

## #4（2026-10-28，P0）1~2 个字被贴进输入框又立刻删掉：OCR 假阴性触发了破坏性重贴

**现象**
- 用户看到极短文本（1~3 个字）被粘进输入框，随即被删除，反复如此；
  日志里同一秒级窗口内出现 `wx_send_text_unverified` → `wx_send_text_missing_retry` → `wx_send_text_missing`。

**根因**
- `core/execution/wx_sender.py:424`：`landed = wx_chat.message_box_has_text()` 用 OCR 回读输入框。
- `core/execution/wx_chat.py:976-977` 原文 `if not items: return False` —— 把「OCR 测不准」当成「确定为空」。
  OCR 对 1~3 个字经常返回空列表，于是「字明明贴进去了」被判成没进去。
- 上游拿到 False 就执行破坏性补救：`:439` 之后 `focus_message_box()` + `_clear_focused_field()`（Ctrl+A + Delete）清空重贴，仍是假阴性 → 再清空。用户看到的就是「贴了又删」。

**处置（已完成）**
1. `message_box_has_text()` 空结果返回 `None`（三态：有 / 没有 / 测不准），不再把测不准当空。
2. 新增 `wx_chat.message_box_snapshot()` + `message_box_changed(before, after, min_px=_BOX_CHANGED_PX=150)`：像素差分，静止噪点不误报（实测空框 ink 约 0.85%，绝对阈值分不出 1~2 字，所以必须两帧比）。
3. `wx_sender._landed_in_box()`：OCR 说空时用差分兜底；判「有字」就不清空、不重贴，并记 `wx_send_text_diff_confirmed`。

**怎么验证**
- 合成阵列：空↔空 → False；加 20×20 方块 → True；尺寸不同 → None。
- 实拍：空输入框连拍两张，`message_box_changed` 为 False（噪点不误报）。
- 线上：日志出现 `wx_send_text_diff_confirmed`，且不再紧跟 `wx_send_text_missing_retry`。

**怎么预防**
- 「测不准」与「空」必须分开建模。任何**破坏性动作**（清空、重发、覆盖写）只允许由「确定为空/确定失败」触发，绝不由「没读到」触发。

## #12（2026-10-28，P0）改函数签名只改一半：监管器启动即 TypeError，她下线约 40 分钟

- `scheduler/main.py::_ensure_loop_engine` 的引擎输出改为追加 `logs/loop_engine.out`
  （`stderr=_sp.STDOUT`），不再扔 DEVNULL。
- 新增 `tests/test_supervisor_boot.py`：本文件里定义的无参函数，任何调用点不许传参；

**怎么验证**

**怎么预防**

## #13（2026-10-28，P1）「每个角色两个 pid」不是重复进程，是 venv 启动器

## #16（2026-10-29，P2）「写了名字没给值」是第三种状态，不是「没配」

**现象**：`PIT-092` 说「裸旗标一律按 true」，但收口后的 `core/infra/envflags.py::flag()` 只分两种情形：
变量不存在 → `default`；有值 → 查真词/假词表。中间那一档 —— `YINYUE_X=`（`.env` 里写了名字、没写值，
或 shell 里 `export YINYUE_X` —— 被 `raw.strip()` 抹成空串，落进「没配」那一支，于是 `default=False`

**根因**：把「变量的存在」与「变量有值」当成同一件事。`os.environ.get()` 返回 `""` 和返回 `None`

**怎么预防**：给任何「收口成一处」的解析函数写规格时，把三档写全 —— 不存在 / 存在但空 / 存在且有值。
只有两档的设计，第三档必然被某个分支悄悄吸收。同理，`tests/test_envflags_semantics.py` 里专门有
`test_bare_flag_means_on` 与 `test_text_keeps_empty_as_default` 两条，一条锁开关、一条锁「别顺手统一」。

**顺带记一笔（锁咬到自己）**：新增的 `test_no_bare_boolean_env_reads_left` 第一版把旧写法字面量
写在 `parametrize` 里，扫全库时把自己也算成了违规，4 条全红。修法不是加白名单，而是把模式用片段拼出来
（`"os.environ.get(" + chr(34) + name + chr(34)`）—— 检查器一旦需要豁免自己，它就不再是「零白名单」的锁。

## #17（2026-10-29，P2）「坏数据」和「本来就没有」长得一样，于是坏账被当成不限

**现象**：`data/.quota_warn.json`、`data/.voice_trigger.json`、`notes.jsonl` 的读口都是

于是该拦的没拦、该只响一次的响两次，而且**一切正常，没有任何一个环节报错**。

`missing`——**不知道不等于没有**。坏数据额外留一份 `<name>.bad-<ts>` 备份并记
`event=json_read_corrupt`。`read_json` 保留为兼容口，行为与改动前一致，只是内部改成调 checked。
需要「坏就不能当空」的调用点（额度、语音触发、notes 坏行计数、self_look 画像）逐个换成 checked，
判据写在各自模块里：`corrupt` 一律按**最保守**处理（额度当已用满、语音当已换过、坏行计入）。

**锁**：`tests/test_json_corruption.py` 11 条，其中结构锁扫全库——`core/rules/quota_gate.py`、
`core/rules/voice_gate.py` 必须出现 `read_json_checked(`，`core/identity/self_look.py` 不得再出现
`json.loads`。**判据只有一个出口，测试只锁出口，不去数「有几个地方判断过状态」**。

**顺带记一笔（机械替换的漏网）**：改签名时用脚本按 `read_json(X, {})` 的字面形状替换，四处
`read_json(path)` 的实参被换成了空串，语法完全合法、import 也不报错，只有跑到那条路径才炸
（`flag("")` / `read_json_checked("")`）。教训：**批量替换后必须把每个改动点按 AST 列一遍调用实参**，
不能只看 `py_compile` 过了、`grep -c` 数对了。

## #20（2026-10-29，P1）同步钩子喂给 `AsyncClient`：报错说 `NoneType can't be awaited`，不报「你传错了」

**现象**：修好 `egress` 的明文 http 门禁后，`tests/test_qq_provider.py::test_media_download_and_send_image` 报
`error="('127.0.0.1', 'http://127.0.0.1:54271/img.png')"`——看着像「地址被拒」，实际是 `Blocked(why, url)` 的 `args` 元组被打印出来，
而 `why` 是**通过时**的主机名。根因是旧契约：`check()` 原来「返回原因、无原因返回空」，现在「失败抛 `Blocked`、成功返回主机名」，
`_guard` 里那句 `why = check(...)` + `if why: raise Blocked(why, url)` 于是把每个通过的请求都拒了。

**修法**（`core/infra/egress.py`）：抽一个共用实体，钩子只调它。

```python
def _check_request(request, lane: str) -> None:
    check(str(request.url), allow_private=(lane == 'local'))
```

**第二个坑（更值得记）**：`httpx` 的 `AsyncClient` 是 `await hook(request)`。
把同步函数喂给它，报的是 `TypeError: 'NoneType' object can't be awaited`（因为 `hook(request)` 返回 `None`），
外加几条 `coroutine ... was never awaited` 警告；而把 async 函数喂给同步 `Client`，钩子**根本不执行**（协程没人 await），
于是公网车道的拦截**静默失效**——测试里表现为「本该抛 `Blocked` 却正常返回 200」。

所以两个钩子必须分开：`_guard(lane)` 同步给 `client()`，`_aguard(lane)` 异步给 `async_client()`。

**我自己犯的错**：第一版按「第二处 `event_hooks` 行」定位同步 client——但 `async_client` 定义在 `client` **之前**，
两行正好写反。**教训：给两处结构相同的代码分配不同待遇时，按「它在哪个 def 里」归属，不要按「第几次出现」归属。**
这个错误本身没有行为提示（同步车道只是"不拦"，日志干净），只有测试同时覆盖「该拦」与「该放」才会暴露——
所以锁要成对写：`tests/test_egress_guard.py` 三条（local 同步能过、public 同步被拒、local 异步能过）。



## #21（2026-10-29，P2）「随机」有四种，只有一种该被结构锁抓

**现象**：PIT-044 落地时，结构锁写的是「runtime 目录里出现 `random` 这个词就红」。
第一次跑就报 `loop/voice_out.py` 违规——而那一行正是刚写对的
`draw = det.rng("voice", inbound, reply).random()`。锁抓的是「词」，不是「用法」。

**四种随机，别混成一锅**：

1. **判定抽签**（要不要开口、要不要变语音）——必须键控可复现 → `core.infra.det`；
2. **人类手感**（`core/execution/wx_human.py` 的打字速度、错字间隔）——不可复现才是对的；
3. **抖动/错峰**（`loop/ports.py` 的分段发送停顿、批量脚本的礼貌延迟）——同上；

白名单每条都要写理由（`wx_human.py` = 手感、`ports.py` = 抖动、`det.py` = 随机源本体）。

**顺带挖出一个真 bug**：`scripts/bench_replay.py:593` 原本是
`random.Random(args.noise_seed + abs(hash(item["item_id"])) % 100000)`——
`hash()` 对 str 受 `PYTHONHASHSEED` 影响，同一份数据两次跑出两套结果，
「带种子复现」是假的。键控种子必须走 sha256（`det.seed_of`）。

## #22（2026-10-29，P2）「exit 0」不等于「验过了」：跳过必须有自己的状态

## #24（2026-10-29，P1）「跑了」有三种：真验过、一条没验、压根没入口

**现象**：全量首跑 `279/413 passed`，其中 20 条 NEW-RED —— 5 条是我自己刚写的 pytest 风格文件

- 17 个文件整体搬到 `tests/pytest_style/`（由 `scripts/run_pytest_suite.py` 用真 pytest 跑），
  路径常量统一升一级：`dirname×2 → ×3`、`parents[1] → parents[2]`、`.parent.parent → .parent.parent.parent`、
  `sys.path.insert(0, os.getcwd())` → 显式三级（cwd 依赖本来就脆）。
  搬完 pytest 侧从 **89 passed → 227 passed**：多出来的 138 条是这些文件**第一次真的执行**。
- 结构锁 `tests/pytest_style/test_gate_entry_point.py` 三条：判据真值表（`__main__` / `run_all(` / 裸 pytest
  文件三种输入）；`tests/` 根下不许再有 stray（有 `def test_` 却没入口）；`runner.SKIP_MARK == tests/_skip.py::MARK`

**教训**：「文件放在哪个目录」也是判据的一部分。位置错的用例比没写的更危险 —— 它占着报表的绿格，
还让人以为那条路径有保护。**能记 PASS 的东西，必须先能证明它跑过。**

## #26（2026-10-29，P2）前端请求路径只能有一种写法：`API + "/x"`

**现象**：`console/panel.html` 里同一个接口有 5 种拼法，其中两处是这样：

1. 请求路径必须是 `/x` 字面量：`API + "/x"` 或 `lawFetch("/x")`。**不要写相对路径**。

## #27（2026-10-29，P1）「拿不到结论」不能写成「结论是零」

**现象**：`python scripts/run_pytest_suite.py` 跑 `tests/pytest_style/` 全部 29 个文件，进度是 235 个点全绿，结尾却打出

```

```

退出码 1。也就是说：**用例全过了，车道报红**，而且报的理由完全不对。

3. 豁免要自证：`MUTATION_HARNESS` 里的文件必须真的用 `subprocess` 跑点东西（`tests/test_two_path_wiring.py` 就是变异测试：删锚点→跑目标用例→靠退出码判红）。

## #29（2026-10-29，P1）门禁第三次坏在自己身上：解码按本机 locale

**现象**：`python scripts/run_pytest_suite.py` 打出

```
RESULT 0/0 passed（一个用例都没收到）
```

rc=1，但那条命令之前明明跑出 `246 passed`（25 秒）。stderr 里藏着真话：

```
UnicodeDecodeError: 'gbk' codec can't decode byte 0xaf in position 691: illegal multibyte sequence
```

**根因**：`scripts/run_pytest_suite.py:108`

```python
proc = subprocess.run(cmd, cwd=str(ROOT), env=env, capture_output=True, text=True, timeout=1800)
```

`text=True` 没配 `encoding`，父进程按本机 locale（这台机器是 `gbk`）解码子进程的 UTF-8 输出。子进程加了 `PYTHONIOENCODING=utf-8` 和 `-X utf8` —— **那只管子进程，管不了父进程怎么读管道**。于是 pytest 输出里一旦出现中文（比如断言消息），读线程就炸，`proc.stdout` 拿不到 summary 行，判定逻辑把它当成"一个用例都没收到"。

**修法**：

```python
proc = subprocess.run(cmd, cwd=str(ROOT), env=env, capture_output=True, text=True,
                      encoding="utf-8", errors="replace", timeout=1800)
```

`probe` 那处同步改。修完全量 246/246，rc=0。

**规律**：这已经是同一类事故的第三次（#23 入口不存在 / #27 拿不到结论写成零 / 本次解码炸掉）。三个都不是业务 bug，都是**门禁自己坏了，而平时没人跑门禁**。所以凡是 `subprocess.run(..., text=True)` 都必须显式 `encoding="utf-8", errors="replace"`；凡是"没收到结果"都必须与"结果为零"分开报。

## #30（2026-10-29，P2）清单抄过来会多出一扇门：先问「这个健康指哪一层」

清单（`docs/该抄的清单.md:108`）写的是「能力按边界拆：只读探活单独一个 server，不挂在有写能力的 server 上」。照字面做就是：新起一个只读 HTTP 服务、新端口、新锁、启动与看护都要改。

摸完现状发现照抄会**多造一扇门**：

- 本仓真正的 readiness 早就有，而且是更小的实现：`console/open_window.py:_api_up()` 就是对 `127.0.0.1:39872` 做一次 TCP connect（`core/infra/egress.py::connect`），只问「端口有人接」。
- 相比之下 `/health` 是更差的实现：它挂在 `console/collector.py` 那个有 `executor` 写能力的 server 上，还回 `os.getpid()`——本机谁能连谁就能读，这个数字没有用处，只有信息面。
- 更要命的是：全仓没有任何东西消费 `/health`（只在 `console/collector.py:1001` 与契约测试里出现）。也就是说「挂错边的探活」其实是个死接口。

于是先定语义再定形状。健康分三层：第 1 层进程在、第 2 层 accept 循环在转、第 3 层业务还能正确回答。用户裁定只承诺 **1+2**（m01795），第 3 层是 `/state` 的事（看它的 age）。据此最小形状是**收窄 `/health`**，不是新起 server：

- `console/collector.py` 里把载荷收到 `_health_payload()` 一处，只回 `{"ok", "at"}`；
- 三把锁（`tests/pytest_style/test_console_api_contract.py`）：载荷键集合、该函数只许调 `_now()`（不许碰 `executor`/`os`/`open`/`db`/`getpid`）、`do_POST` 面只许是 `{"/rehearse", "/cmd"}`。

伪证：把 `_health_payload` 改回带 pid 且顺手 `open(os.devnull,"a")`，锁立刻红两条（`{'at','ok','pid'} == {'at','ok'}`、`{'_now','close','getpid','open'} == {'_now'}`）。

教训：清单是别人仓库的形状，抄之前先问「它要解决的那件事，在本仓是不是已经有更小的实现」。以及——**「拆 server」不等于「拆进程」**：同一个进程里再开一个端口，故障面还是共享的；真要隔离得独立进程，成本高一个数量级，不该为了对齐一张表去做。
## #31（2026-10-29，P2）一个事件名把六种失败糊在一起，等于没报错

改法不是加日志，是加一层：`core/infra/trouble.py` 一个写口（`note`/`clear`）+ 一张分类表（`REASONS`，8 个键）+ 一句第一人称（`render()` 输出「我这会儿发不出声音：连不上服务，引擎大概没起（04:56 起，12 分钟了，已经试过 3 次）」）。`tts_cosyvoice.py` 的六处失败全部收口到 `_fail(reason, detail)`，成功一次调 `_recovered()` 清账。`loop/brain.py` 每拍把 `render()` 的结果并进上下文，标题写「我身上的状况（系统告诉我的事实）」，明确标注这不是她自己的想法。

为什么**不**往 `self_state.json` 里加一个 `trouble` 键：那张表开头写着「这张表是我自己写的，不是别人塞给我的」。系统代笔会破坏这个承诺——她分不清哪句是自己的判断、哪句是别人塞的。所以与它**并列**放一小块，署名写清。

教训：
- **分类要收口成一张表**，散在调用点就会退回「一个名字盖六种问题」。
- **「谁看得见」决定要不要做**。这条清单看着像文案活，其实是「她有没有可能知道自己坏了」。
- 顺带一条工具教训：改代码前打印锚点行**必须打整行**，我按 88–106 字符截断打印，锚点尾部差一个 `if reply else 'no_reply'`，补丁全打在空气上（`AssertionError: ... count 0`）。要么打完整行，要么直接用 `lines[i]` 原样当锚点。

## #32（2026-10-29，P2）`except: pass` 不是「不处理异常」，是把「不知道」写成「没事」

**现象**
全库 AST 扫出来 **346 处** handler 的 body 只有 `pass` / `continue`（279 个 `文件::函数` 键，散在 120 个文件；裸 `except:` 0 处）。
它们里真正该骂的很少：关文件、停子进程、`__exit__` 里清理失败，静默本来就是对的。出事的是另一类——
判定路径上的那一小撮：读端口配置失败 → 静默回默认；别名表读坏 → 静默认不出人；素材查询失败 → 静默当她没发过图。
共同形状是「坏的方向是空 / 坏的方向是没有限制」，而且日志里 0 条，事故没有起点。

**为什么不能逐个改**
346 处要一百多次判断，判断成本高到没人做，做一半比不做更糟（后人不知道哪些是审过的）。
而且「该不该吞」在调用点往往看不见，得看着上层怎么用返回值才能判。

**改成什么**：给「这一次不做」一个唯一出口 `core/infra/skips.py`，跳过的定义是三件事，缺一条就还是吞：
1. **哪一类** —— `KINDS` 枚举，不许自由文本：`absent`（东西不在）/ `unsupported`（平台不支持）/
   `degraded`（能做但不完整）/ `flutter`（瞬时，可重试）/ `malformed`（写得不对，不是「没写」）；
2. **在哪** —— `where` 形如 `文件.函数:对象`，日志能直接 grep；
3. **看得见** —— 一条 `skipped_step` 事件 + 进程内计数。
`skip()` 不改变控制流也不改变返回值，退不退默认值仍由调用点决定——它只负责留痕，不负责决定怎么办。

第五类 `malformed` 是这场差点漏掉的：`PIT-092` 的教训是「写了值但解析不了」塞进 `absent` 会把「写错了」说成「没写」，
于是用户以为改了配置没生效，而系统认为「本来就没配」。分错类等于没分类。

**怎么防回退**
存量不逐个改，进台账 `tests/silent_except_ledger.txt`（`路径::函数<TAB>次数`，279 行），结构锁
`tests/pytest_style/test_silent_except_discipline.py` 只认三种变化：新键 → 红；次数变多 → 红；
次数变少但台账没跟着删 → 也红（只准减，改好就划掉）。判定路径上那 4 个函数额外钉在 0，且必须真的调 `skips.skip(`。
伪证验过：加一个空文件写 `except Exception: pass` → 报「新代码不许静默吞：core/_zz_silent_smoke.py::probe 有 1 处」；
把 `media_ref` 那处跳过删回去 → 同时红两条（台账 + 判定路径归零）。

**教训**
「跳过」和「通过」必须是两个状态。这跟 #22（skip 需要独立状态）、#27（拿不到结论别写成零）、
#29（解码失败被记成 0 个用例）是同一族，只是这次在异常处理这一层。

## #33（2026-10-29，P2）「沉默多久算故障」是个假问题：沉默的信息量本来就低

**现象**：《该抄的清单》BR-009 写「定义多久没有任何事件包 = 另一个故障面」。我第一版直接给秒数（沉默 30 分钟 / 60 分钟算报警），被连问两次：

- 「没有事件包就算报警吗？」
- 「事件包就只是你说的这些算作是事件吗，你再想想」

**为什么第一版是错的**：夜里没人说话是正常的；沉默的成因常常在上一环（OneBot 掉线，收不到消息自然也没东西可写）；把「没数据」升级成告警，只会训练人去关告警。**沉默是信息量不足，不是故障。**

第二版我扩到「她世界三圈（对话世界 / 她的器官 / 整台机器）」，被一句「你想的太大了，不需要关心软件进程」判死 —— 因为那不是本仓能观测、也没人需要看的东西。

**收窄后的结论（用户定的两条轴）**：

1. **能感知（perceive）** / **能操作（act）**。说话只是「操作」里的一种。
2. 两条轴的**坏法不同，所以观测方式不同**：
   - 操作坏了是**响亮**的 —— 抛错、被拒、没有回执 → 看回执，**不需要阈值**；
   - 感知坏了是**静默**的 —— 和「没人说话」一模一样 → 只能由**这条通道自己的心跳**证明。全系统唯一需要「多久」的地方在这里，而且量的不是「多久没消息」，是「证据多久没更新」。
3. **读不出来就是 unknown，不许显示成正常**（#27 的老教训，第三次用上）。
4. **声明是数据，活没活着是运行时**：`PlatformDef.senses` 说「应该有什么」（`core/execution/platform_registry.py`），`core/infra/senses.py` 说「现在有没有」。
5. **判据按 `proof` 走，不许按平台名分支**。一旦写 `if platform == "wechat": alive = mtime(...)`，加平台就得改判据 —— 那正是 BR-009 要治的病。

**留下的形状**：`tests/pytest_style/test_platform_senses.py` 12 条锁住上面五条（含「未接平台不许提前许诺能力」「判据里不许出现平台名比较」）。

## #34（2026-10-29，P2）「硬等超时就继续」把失败的等待写成了成功

**现象**：`console/executor.py::svc_restart` 的链路是「停 → 等端口 39871 释放 → 起」。等待那一段是：

```python
end = time.time() + wait_s
while time.time() < end:
    if not _port_open(ENGINE_PORT) and not _pid_alive(...):
        break
    time.sleep(0.5)
time.sleep(0.5)          # 超时也走到这里
for path in (ALL_STOP, SCHED_STOP, LOOP_STOP):
    os.remove(path)      # 照样删 stop、照样拉监管器
```

于是「等到了」和「没等到」走的是同一条路：没人知道这次是哪种，失败也没人负责。同一个链路另一头，`svc_stop` 写三个 stop 文件写一半抛 `OSError` 就 `return {"ok": False}`——已经写下的不回滚，系统停在「半个停止」：监管器以为该停，引擎还在跑。

**改法**：把「等」变成一个能回答两种结果的函数，把回滚点放在动手之前的快照上。

- `_wait_released(wait_s) -> tuple[bool, float]`：返回 `(是否等到, 等了多久秒)`。超时也照常返回——**超时算不算失败由调用方决定**，不许在等待函数里悄悄变成「继续往下走」。
- `_stop_snapshot() -> list` / `_stop_rollback(existed) -> list`：快照只记「动手前哪几个 stop 文件本来就有」；回滚只删**这次新写出来的**。
- `svc_stop` 把 `existed` 放进回执；写失败时先回滚再返回 `{"ok": False, "rolled_back": True, "undone": [...]}`。
- `svc_restart` 等不到就撤回新写的 stop、`warn("svc_restart_wait_timeout", waited_s=…, undone=…)`、**不拉监管器**，回到「什么都没改」。

**教训**：
1. 失败的动作必须有一个「什么都没改」的终点。把失败和成功汇进同一段收尾代码，等于把失败写成了成功——它不会报错，只会让下一次排查从错误的前提开始。
2. 回滚的语义是「撤销我做的」，不是「把系统恢复成我认为对的样子」。本来就存在的 stop 文件是别人早先要求的停，撤销它等于替别人开机。
3. 顺带一条本仓的 API 事实：日志入口是 `safelog.warn(event, **fields)`。我第一版写成 `from safelog import LOG as log` + `log.warning(...)`，抛了 `AttributeError: 'str' object has no attribute 'warning'` —— 因为 `safelog.LOG` 是个字符串。更值得记的是它**怎么没被发现**：那句在守护线程里执行，pytest 只给一条 `PytestUnhandledThreadExceptionWarning`，五条测试照样全绿。所以「线程里的日志」必须有一条测试真的走到它，否则等于没有这行日志。

## #37（2026-10-29，P2）「一次提交」的判据是「崩了以后已经落库的部分算不算完成品」

**现象**：`PIT-051` 的前半段（改文件）早就有交货——`core/infra/migrate.py` 预检全部锚点、备份、失败整批还原；后半段（DB 脚本）没人管：`scripts/backfill_actor_person_ids.py:332` 每 500 行提交一次，崩在第 7 批就是「前 6 批已落库、后 3 批没落、没有任何人知道改到哪」。而 `db/world_db.py:699` 是 `isolation_level=None`（autocommit），commit 就是唯一的事务边界。

**判据**（这次定下来的，能一句话回答该不该分批提交）：
> 这个东西崩掉以后，**已经落库的那部分**算不算完成品？

- 算 → 允许批提交（长期运行的增量处理）。本仓四处，每条都要能说出「为什么每一批都是完成品」：`db/decrypt.py`（按表解密，重跑跳过已解密的表）、`db/sync_service.py`（按会话/消息增量入库）、`loop/desk.py`（发件箱逐条确认）、`agents/late_vision_followup.py`（补发前先落标记再发）。
- 不算 → 一次性迁移，只能「算完 → 一次提交」。中途退出等于什么都没改，这就是回滚——不需要额外写 rollback。

**改了什么**：`scripts/backfill_actor_person_ids.py` 的分批提交删掉，`executemany` 仍在循环里（那是为了限制单条 SQL 的参数个数），但 `commit()` 挪到循环之后一次；`except sqlite3.Error: conn.rollback(); raise`。锁 `tests/pytest_style/test_batch_commit_discipline.py`（5 条）：循环里提交必须与白名单逐键相等、白名单每条要有理由、迁移脚本不许循环里提交、迁移脚本 `commit ≤ close`（一次连接一个事务单元）、扫描不许扫了个寂寞。

**两个顺手踩到的坑**：
1. **我第一轮的扫描漏了目录**：只扫 `scripts/ db/ core/ loop/ console/ scheduler/`，锁一跑就多出 `agents/late_vision_followup.py:244`。教训：结构锁的扫描范围要写「全仓应该遵守这件事的地方」，而不是「我上次找过的目录」；漏了目录的锁会给人已经收口的错觉。
2. **`ast.parse` 遇 BOM 会炸**：本仓 `agents/base.py`、`scripts/check_invariants.py`、`scripts/check_turn_entry.py`、`scripts/audit_extra_contract.py` 带 `\ufeff` 开头。Python 自己编译没问题，`ast.parse(text)` 抛 `SyntaxError: invalid non-printable character U+FEFF`。读源码做 AST 检查一律 `encoding="utf-8-sig"`。

## #38（2026-10-29，P2）收口要先问「谁定义这份数据的形状」，不是「谁最近改过它」

**现象**：`PIT-111` 早在 2026-10-28 就把「离上次开口多久」收进了 `loop/ledger.py::quiet_ms`，测试也锁住了「只有 ledger 算间隔」。但这次一查，同一份 `data/loop/ledger-<日期>.jsonl` 的文件名还有 **6 处在各拼一遍**：`loop/ledger.py`、`loop/ports.py`、`loop/followup.py`、`db/world_db.py`、`console/checkup.py`、`console/collector.py`。名字是对的、读出来的东西也对——**所以没有一条测试红**。真正的洞在另一边：`core/speech/outbound.py` 这条语音出口发完话不写流水，只往 DB 记「主动触达配额」；而 `core/terminal/proactive_service.py` 的冷却读的是那个 DB。于是「她刚回完一句」在冷却那侧不存在 → 「刚回完又搭一句」。

**判据**（用户定的口径）：
> 「她做过什么」只允许一本流水；「配额/配置」只允许 DB 一份；任何「多久没动作」的问题一律问流水。

**为什么改法必须是下移而不是合并**：`core/` 不能 import `loop/`，所以不能让 `proactive_service` 去调 `loop.ledger.quiet_ms`。于是把「流水的形状」下移到 `core/infra/actions.py`（`path` / `append_row` / `merge_last` / `append_receipt` / `read_receipts` / `rows_for_days` / `last_say_at` / `quiet_ms`），`loop/ledger.py` 只留别名当薄壳（439 → 325 行）。反过来让 ledger 去问 DB 最糟：jsonl 会变成投影，人眼回放那一天的账就没了。

**三条教训**：
1. **收口找「定义形状的人」**：文件名、字段名、append 方式都是形状；谁定义谁就是唯一的一份，其他人只能问它要。先前的锁只锁住「谁算间隔」，没锁住「谁拼文件名」和「谁写这一行」，所以看着绿其实是半个收口。
2. **锁要区分「构造」与「读取」**：`glob("ledger-*.jsonl")` 这种只读是合法的，必须允许；把「出现 `ledger-`」一律判红会逼人写更绕的代码。所以锁的规则写成「`ledger-%s` / `ledger_%s` / `ledger-{` 这种**格式化构造**只许出现在 `core/infra/actions.py`」。
3. **写口和问口要成对出现**：出口写一行回执 + 冷却问同一份流水，两件事必须同一次改完；只改问口，冷却就永远看不到语音这条出口发出的消息。

**顺带记的**：`core/speech/outbound.py` 里 `warn("核心/文件.py:行 Exception", ...)` 这类事件名会被 `scripts/check.py` 的 events 闸门判红（`EVENT_RE` 要求 `^[a-z][a-z0-9_]{2,}$`），新加日志要用 `outbound_action_receipt_failed` 这种名字。

## #39（2026-10-29，P2）「有锁」和「锁装在门上」是两件事

2. **有生产者**（系统里某个固定位置真的会在正常流程里调它）；

## #41（2026-10-29，P3）断言「现在不存在」会随环境变成假红，断言「与开始前一致」才是这条用例的本意

**现象**：`tests/pytest_style/test_restart_rollback.py::test_wait_timeout_rolls_back_only_what_this_run_wrote` 在全量里红了三次，单跑又是绿的。红的是这句：`assert not paths["LOOP_STOP"].exists()`。

**原因**：它断言的是「这个文件此刻不存在」这种**绝对状态**。可只要工作区里恰好存在 `logs/loop.stop`（别的脚本或别的用例留下），或在 `tmp_path` 复用/顺序变化时留了一个空文件，这句话就与「本次有没有撤干净」无关了。它在测的东西是「这次新写出来的东西有没有被撤掉」，却写成了「这世界上没有这个文件」。

**改法**：`_sandbox` 里先清干净起点（`elif path.exists(): path.unlink()`），用例开头记 `before = {name: path.exists()}`，断言改成 `assert paths["LOOP_STOP"].exists() == before["LOOP_STOP"]`。这样它测的是**本次变化**，环境怎么脏都不影响。

**一般化**：测试里出现 `assert not X.exists()` / `assert X == 0` 这类绝对量时，问一句「它想钉的是『本来就没有』还是『这次没造成』」；后者要拍快照再比。附带好处：偶发红会消失——偶发红最坏的地方不是烦，是它训练人忽略红。

## #42（2026-10-29，P2）「缺这个字段」和「字段值是 0」是两件事：宁可回 411，也不猜 0

**现象**：`console/collector.py::do_POST` 原本这么读长度：`n = int(self.headers.get("Content-Length") or 0)`，然后 `raw = self.rfile.read(n)`。请求**没带** `Content-Length` 时 `read(0)` 立刻回空串，`json.loads("")` 抛异常被兜住，落到 `body = {}` —— 于是「一个没有正文的畸形请求」被当成「一个空参数字典」，继续往下走业务逻辑。症状不是报错，是**有人往空 body 发 POST，接口照常执行**。

**原因**：`or 0` 是个静默的默认值——它把「没有」（absent）折叠成了「零」（0），而这两件事在这里语义完全不同：值是 0 表示「我知道正文长度是 0」，缺失表示「我不知道，你也别猜」。

**改法**：抽出 `_read_body(req) -> tuple[bytes | None, tuple[int, dict] | None]`，第一段就是
```python
raw_cl = req.headers.get("Content-Length")
if raw_cl is None:
    return None, (411, {"ok": False, "error": "缺 Content-Length（不支持分块传输）"})
```
只有拿到确切长度才继续读；`Transfer-Encoding` 里带 `chunked` 也走 411（我们不做分块），因为分块的长度协议我们没实现，装作支持就是下一个静默。

**一般化**：解析外部输入时，`x or <默认值>` 出现在**长度、计数、开关、状态码**这四类字段上要停一下——默认值把「不知道」写成了「知道，且是零」。这类位置要么显式区分 `None`（回 4xx），要么就把默认值写进契约里（`default` 是契约的一部分，注释说明为什么零是对的）。

## #43（2026-10-29，P2）纪律锁要跑一遍「它看不见的写法」——否则它锁的是自己的正则

**现象**：`tests/pytest_style/test_source_assert_discipline.py` 的初衷是「测试里不许只说『源码里有这行字』，要有行为断言」。它上线那天全绿。这次做 `BR-103`，把 9 条源码字符串断言换成真 handler 驱动的行为断言之后，顺手发现它有两个洞：
1. **读源码的姿势没认全**：`_SRC_READER = re.compile(r"""(?:Path\s*\([^)]*\)|\w+)\.read_text\s*\(|inspect\.getsource\s*\(|getsource\s*\(|_source\s*\(|_src\s*\(|_read\s*\(|read\.read_text\s*\(|__file__""")` 之外还有各种「本地 helper 帮你读」的写法——`tests/test_http_body_limit.py` 里是 `def _src() -> str: return ...read_text()`，然后在用例里 `assert "..." in _src()`。原正则**根本没匹配到**这些断言，于是这个文件在锁眼里是「零源码断言」，永远绿。

- 判据本身：新增 `source_vars(text)` 收集「本地 helper 读出来的源码」变量名（`_src`/`_source`/`_read`/`read` 这类），`source_asserts()` 把 `assert <src_var> in ...` 也算源码断言；`behavior_asserts()` 则**排除**所有「断言里出现源码变量」的行。
- 存量处理：直接把 4 个真违规文件（`tests/test_dry_run_send.py` 3/2、`tests/test_social_cost_gate.py` 12/7、`tests/test_trace_canonical_v2.py` 37/12、`tests/pytest_style/test_send_interval_source.py` 11/9，`src/beh` 计数）写进台账 `tests/source_assert_ledger.txt`，记作「上限/下限」，锁变成「**新文件不许**，存量只准朝好的方向改」，改好了必须删行（台账过期也是红）。

**一般化**：写「禁止某种写法」的锁时，必须再问一句「还有哪些姿势能达到同样效果」。正则锁最典型的失败不是写错，是**只覆盖了作者自己习惯的那一种写法**——于是它长期绿，绿得毫无信息量。验证办法是伪证：故意写一个「绕过姿势」的新用例，锁必须红；不红就说明洞还在。

## #51 变异测试的「恢复」必须在 finally 里，否则一次异常就把仓库留成变异态（2026-10-29，P1）

**现象**：给 `tests/pytest_style/test_unverified_index.py` 做反证时，一个探针脚本在 `violations()` 上抛 `TypeError`（我把它的签名记错了：它是 `violations(rows, body)`，不是 `violations(text)`）。恢复语句写在脚本末尾 → `docs/交接.md` 的索引表永久少了第 24 行；直到下一次全量 pytest 报 `编号不连续或有重复：[… 23, 25 …]` 才发现。

**连带三课**：
1. 此前那次「8 passed」是**历史事实**，不是现状。报告里引用绿数，必须和引用它的时点对齐（这一条与 `#39` 同源）。
2. 读 pytest 失败要看 `E ` 开头的**断言差异行**。我第一次调用的过滤器把 traceback 里的源码上下文行（`assert rows, "…找不到未验证索引表"`）当成了失败原因，白查半小时。
3. `#N` **不是全局唯一编号**：踩坑档案用它、未验证索引也用它。锁里因此只认「出现『未验证』的那一行上的 `#N`」，其余 `#N` 一律当普通正文引用。

**规矩**：任何「改文件 → 验证 → 恢复」的探针，恢复写成 `try/finally`（或改副本、不碰真文件）；反证跑完立刻再跑一遍原测试，确认已复位。

## #52 「偶发红」先问对端有没有读完你的请求（2026-10-29，P1）

**症状**：`tests/test_qq_setup.py::test_probe_login_ok_and_token_error` 偶发红，`AssertionError()` 没有消息（全量里报一次，单独循环 60 轮报 3 次）。

1. 用循环把偶发变成概率（60 轮 3 次 ≈ 5%），别指望再撞一次。
2. 不猜日志，直接把被测函数的返回值打出来：`bad` 是 `None`，不是超时、不是端口占用。

**一般化**：**本地写的最小服务替身必须把请求读完**，否则「服务端立刻挂电话」和「网络掉线」在客户端看来完全一样。偶发红先怀疑对端行为，不要先怀疑调度。

## #53 「没连上」和「连上了被打断」不能共用同一个返回值（2026-10-29，P1）

**现象**：`scripts/qq_setup.py` 里 `http_api_call` 传输失败 → `(0, str(exc))`；`probe_login` 收到 `status == 0` → `None`；`probe_http_ports` 把 `None` 读成「这个端口上没有 OneBot」，继续扫下一个端口。

**两种不同的事实**：A 端口上确实没有 OneBot（该继续找）；B 有东西，但它把连接打断了（该停下并说出来）。折叠成一个 `None` 之后，上层只能选一种解释，而它选了错的那种。

**修法**
- `_UNREACHABLE` 白名单（ECONNREFUSED / ENETUNREACH / EHOSTUNREACH / ETIMEDOUT / timeout / refused / unreachable）→ 仍返回 `(0, …)`。
- `_transport(text)` 认 WinError 10053 / 10054 / 10058 / 10060 / 10061 与 `RemoteDisconnected` / `ConnectionResetError` / `An operation was attempted on something that is not a socket` → 返回 `(0, {"transport": …})`。
- `probe_login`：不可达 → `None`；transport → `{"error": "连上了但对话被打断：…"}`。
- `probe_http_ports`：遇到 transport 立刻停下并把这个 error 交出去。

**钉法**：两条确定性用例（替身先回 200 再 reset；替身 `settimeout(0.05)` 报错）。原 `test_probe_http_ports_miss` 断言 `is None`，改成 `assert result is None or "打断" in str(result)` —— 判据是「有没有如实说出来」，不是「必须失败」。

**一般化**：一个返回值同时表示「不存在」和「坏了」，上层就只能选一种解释。HTTP 用 404 / 500 分开，本地函数也必须分开。

### #82 监管器看错了东西：它看主程序心跳，就永远不知道引擎死了

2026-10-30，`scripts/supervisor.py` 的退场判据是：

```python
if _scheduler_alive():
    _log("主程序心跳还在，说明已有实例在跑，监管器退出")
    return 0
```

`scheduler` 是调度器，真正干活的 `loop.run` 是它拉起的**另一个进程**。于是出现最坏的一种状态：
调度器还活着（心跳新鲜）→ 监管器以为"有人在跑"→ 退出 → 引擎死了没人管 → 她永远不说话。
现场证据（`logs/supervisor.out`）：`21:16:08 主程序心跳还在，说明已有实例在跑，监管器退出`。

修法是让判据看对对象：`_take_over(sched_alive, engine_state)` —— 两者都新鲜才退出，任一不新鲜就接管。

三条一般化：
1. **"X 还在吗"先问 X 是哪一个**。调度器 ≠ 执行者；用户侧说"她不回话"，要查的是引擎心跳，不是调度器心跳。
2. **"已有实例在跑"这句话必须由"我管的那个实例"证明**，不能由别的实例证明——否则监管器会把别人的存活当成自己的免责。
3. 监管器退场前应写下证据（谁的哪个心跳、多旧），否则事后只能靠猜。

## #94 「一小时 71 条静默告警」其实是两个"正常情况"当异常报了

**现象**：体检 `warnlog warn | 最近 1 小时 71 条静默告警`，但看不出业务上出了什么事。
