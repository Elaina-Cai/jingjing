# 开发规矩（改代码前必读）

> 形式取自 qq-bridge/surfcore 的 `AGENTS.md`（MIT License，Copyright (c) 2026 Derpyu520 and qq-bridge / QSH contributors）；
> **工程规矩内容为本仓自订** —— 它那边的命令（`npm run test:audit`、`node --check`、`.mjs`）与本仓无关，未沿用。
> 这份文件是「怎么改这个仓库」的硬规矩，不是设计文档。`AGENTS.md` 只保留一个指针指到这里。

## 0. 每次开工的固定动作（顺序别改）

1. 读 `docs/目标与蓝图.md` 的「不做什么」——它决定你**该不该**动手。
2. 读 `docs/交接.md`——上一个我做到哪、什么还没验证。
3. 带着具体问题查 `docs/踩坑档案.md`——每条都带「怎么验证」，能直接当判据。
4. **最后**再读代码。**别相信会话记忆，相信文件**：半天前的「我记得改过」通常是错的。

## 1. 十条铁律（违反任何一条都算事故）

1. **先分析，再动手**：写清「现象 → 根因 → 影响面 → 修法 → 怎么验证」。分析没到能预判失败点，就只做只读排查。
2. **先算收益再选路线**：至少比较 2 条（收益/成本/风险/回滚难度）。收益不佳就回退换路线，别因为「已经写了这么多」硬撑。
3. **不补屎山**：宁可回退重写 30 行，也不在错地基上叠 300 行补丁。判断标准——新代码让「下一次改动」更容易了吗？
4. **不盲目跑探针**：任何会起服务、发微信、写 `data/`、写 `logs/` 的脚本，先说明目的、预期输出、失败后果；跑完先看日志再下结论。通道限制见 §2.9。
5. **改完必测**：`.py` 必 `py_compile`；碰发送/执行链要跑一次 dry 拍；碰提示词要能说出「哪个块变了、为什么」。
6. **一次只改一件事**：同一次改动混进两件事，出问题就分不清是哪件。
7. **失败要留能定位到哪一跳的日志**：只打一个布尔事件等于没日志（踩坑档案 #4）。
8. **上限必配告警**：只有截断、没有声音的上限等于数据损坏（踩坑档案 #5）。
9. **破坏性动作只由「确定」触发**：清空、重发、覆盖写，绝不允许由「没读到」触发（踩坑档案 #4）。
10. **别让人猜**：改动影响用户可见行为时，说清改了哪、怎么回滚。

## 2. 本地硬规矩（2026-10-26 一天改坏 4 个文件的教训，原文保留）

背景：一天之内把 4 个文件改坏（两个 `.bat`、`loop/ledger.py`、`core/memory/recall_chain.py`），每次都回滚重来。原因只有一个——**没看原文，就按「应该长这样」去改**。

1. **先打印原文再改。** 读文件打出签名、缩进、行尾风格，而不是凭记忆拼锚点。
2. **锚点只用短子串，且不含换行、不含缩进。**
   - 行尾：Windows 侧文件多是 CRLF，用 `"\n"` 拼的锚点会 `COUNT 0`。正确做法：`eol = "\r\n" if "\r\n" in raw else "\n"`，或者干脆用不含换行的子串匹配。
   - 缩进：数空格容易错，改成按「该行唯一子串」定位，整行替换。
3. **能改一行就绝不插几行。** 插行会带来缩进匹配问题（`IndentationError: expected an indented block after 'except' statement` 就是这么来的）。
4. **改完立刻验证**：`.py` 跑 `py_compile`，`.js` 跑 `node --check`，`.json` 用 `json.loads`。不要只看「文件写了没」。
5. **替换前先数命中次数**：`assert src.count(OLD) == 1`，命中 0 或 >1 就停手重新看原文。多处同名模板（例如 `append_receipt(act="say", ...)` 有 5 处）必须先按上下文筛出唯一那处。
6. **改的是「运行时真正走的那条路」吗？** 同一个功能常有多个入口（`/api/loop/ledger` 走 `web/routes_loop.py`，不是 `web/routes_harness.py`；`resolve_nickname` 在 `wx_chat.py`，不在 `wx_sender.py`）。先 grep 调用链再动手。
7. **先备份再改**：`shutil.copyfile(p, p + ".bak_<主题>")`，坏了能一键还原。
8. **改 .bat 只用最小手法**：bat 里不要解析 JSON、不要拼 `python -c`（引号和 `%` 会被吃掉）。让 python 写 `logs/current_port.txt`，bat 用 `set /p PORT=<logs\current_port.txt` 读文件。
9. **执行通道**：本机 `pwsh` 工具不可用（`Error: PTY shell exited during startup`），唯一通道是 `blender_rt_headless(engine="none")` 跑 `.venv\Scripts\python.exe`；`py_compile` 必须用 `.venv` 的 python（blender 自带的没有项目依赖）。
10. **一个脚本写多个文件时**：备份与断言必须在**所有**写盘之前；要么全成功，要么一个字节都不动（踩坑档案 #3）。
   > 现在有壳子了：`core/infra/migrate.py` 的 `Migration`（预检 → 备份到 `.test_tmp/migrate_bak/<时间戳>` → 写入 → 任一步失败整体回滚）。改文件用它，别再手写备份与断言。

## 3. 事故即证据

反例（都真实发生过）：
- 用 `\n` 拼锚点改 CRLF 文件 → `COUNT 0`，误以为「没这行」，转头去改别的文件。
- 往 dict 字面量行尾追加 `"ack": ack,` → 插到右括号后面 → `SyntaxError`。
- 想插两行注释却把缩进算错 → `except` 后空块 → `IndentationError`。
- 按名字猜接口位置，改完发现「接口根本不走这条函数」，白改两轮。
- 按行号改代码，插入一次后行号全部漂移 → 第二处补丁落到错行（踩坑档案 #2）。

完整档案（现象 / 根因 / 处置 / 怎么验证 / 怎么预防）：`docs/踩坑档案.md`。

## 改完必跑

```
.venv\Scripts\python.exe scripts\check.py all
```

四检：语法、日志事件名（不许 `xxx.py:NN Exception`）、开关写法（不许裸 `os.environ ... == "1"`）、JSON 落盘是否原子。新增违规会红；历史欠账在 `scripts/check_baseline.json`，只许变小。

11. **禁止机械枚举式方案**：不许用“把所有调用点都列出来挨个加校验”“把所有异常都列出来挨个 if”“名单越写越长”来充当设计。
    合格的形状只有三种：① 把能力删掉（结构上做不到）；② 把判定收到**唯一入口/唯一真源**；③ 让反例在类型或接口层面表达不出来。
    每条改动交付时必须能回答一句：**“这套错还能从别的路进来吗？”** 答“能”＝还没改完；只能靠枚举拦住＝不算改完。

## 规则与诉求冲突时，改规则本身（2026-10-29，由 `HO-045` 并入）

「她不像人」如果逐句追得到某一条**写死的规则**（不是模型能力、不是数据、不是速度），要改的是那条规则自己，不是靠加提示词技巧去绕开它。

三条判据同时成立才动：

1. **规则在磁盘上找得到**：卡片、提示词装配、守卫代码里能 grep 到那句约束。找不到就不是规则问题，别改（先怀疑自己记错了）。
2. **冲突能举出具体反例**：某句话因为这条规则变成了不对的反应（如「回复后先等 30 秒~10 分钟」导致冷场），不是「感觉不自然」。
3. **改完只动这一条**：人格文件属资产，逐句改、留 diff、不顺手重写；要用户在场时逐句确认。

为什么写在这里而不是 `docs/该抄的清单.md`：清单记的是「还欠一件事」；这条抽出来是**原则**，而它的原始对象（当初那条旧规则）已不在磁盘上（复核过程见 `docs/踩坑档案.md` `#55`）。
