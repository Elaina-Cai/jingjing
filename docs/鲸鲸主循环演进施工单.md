## 1. 主链和职责

```text
平台观察 → loop/run.py::one_tick → 当前会话、触发消息及可见证据
   → loop/brain.py::run_loop
       当前对话 + 允许使用的相关记忆 + 当前任务及相关经验 + 稳定表达原则
   → 模型选择继续了解、回应、执行或等待
   → loop/ports.py / 既有任务、队列和出口 → 操作事实及回执
   → 现有反馈、信念和目标写入口 → 供以后回合读取
```

- 代码提供来源、权限、时间、操作结果及已知状态。LLM 结合这些材料判断现在该怎样回应或行动。模型提出的解释、计划和承诺按既有接口提交，由代码检验并持久化。
- 原话、可纠正信念、方法经验、目标和实际回执各用对应的现有记录。谁说过什么、是否可信、是否当前有效以及能否对当前对象使用是不同字段和条件。
- 信息按需要提供。当前消息和直接前文优先。检索到的材料要可展开并指回来源。候选条数和字符预算沿用现有上限为起点，以回放衡量排序和信息密度。
- 继续使用现役决策循环及工具协议。表达规则只指导生成。工具调用、权限、回执与状态推进仍经现有边界。方案沿用蓝图对每轮额外模型调用、出口润色、图谱和全量注入的取舍。

## 2. A · 对话与表达

**交付行为。** 她能根据对方这句话在当前对话里的作用选择不同的回应。她可以简短接话、完整解释或询问必要信息，并准确表达已知、未知、失败和能力限制。

**入口。** `loop/run.py::one_tick`、`loop/snapshot.py::{render_text,render_turns}`、`loop/brain.py::{run_loop,_system_head,_reshape,SPEAK_GATE,WALLS}`、`loop/expression.py`、当前 active 人设卡、`core/policy/channel.py`、`core/contracts/limits.py`。评测使用 `evals/expression/{harness,review}.py`，与 `evals/rubric.md` 对照。

### A1 先修评测，再看表达效果

1. **隔离在前。** `harness.py::cmd_run` 现在先构造 `RealLLM`，而其构造路径会经 `ports.get_llm` 调用带生产权限的 bootstrap。先将库、账号目录、日志、提示词记录及模块级存储路径设到独立临时目录，再导入会缓存路径的模块。真实模型调用使用能独立构造的现有模型客户端，避开生产 bootstrap。测试先装能拒绝外发和业务写入的工具边界，再让带工具调用的脚本模型跑。`rehearse=True` 仍需这层隔离。
2. **固定真实对照。** `harness.py::_persona` 的 baseline 分支不能依赖当前 active 卡。将已知旧卡和候选卡固定为可复验输入，记录文件散列和对应提示词版本。有条件随仓库提交的合成夹具单独存放。未授权分发的人格原文使用显式路径和预期散列。旧卡缺失时报错。接线测试不依赖被忽略的工作区临时目录或线上人设。
3. **每次请求保留证据。** 记录实际 messages、tools、模型和供应商、采样参数、场景 ID、repeat、请求次序、输出/失败状态和用量。模型回落、超时、缺失、错误回包需要留状态，无法按固定模型完成的样本不进入有效对照。区分有意沉默和运行失败。重跑写新 run ID，保留原始配对。
4. **禁止盲评计数被缺样或重复票抬高。** 按冻结输入、模型/供应商、参数和 repeat 配对。先验输入覆盖，拒绝重复结果。评分按评审人与案例组合去重，显式区分平票和无效票。逐例记关键事实、隐私与权限错误，维度总分不能抵消这些错误。多轮包按原顺序保留每条消息的说话人及沉默。
5. **让场景前提真的到达模型。** 无人点名的群聊夹具要实际标成未受话；保存失败夹具要提供已经失败的原关联回执，不能靠模型这轮再次保存来制造失败。逐案检查实际首轮输入，避免评测标签和模型看见的内容相反。

### A2 验证和修正当前改造

- 固定前文，只换表达版本。优先对照旧卡与已上线完整候选，使用现有保留集与独立新增案例。看自然程度、对话贴合、人格一致、内容完整。建议继承原表达方案的偏好率及样本要求。混合模型、覆盖不足或关键回归时标效果未验收。
- 固定表达规则，只改变前文或引用对象。覆盖同一句「终于好了」分别接修报错和饭做好；同一句「你又开始了」分别接玩笑和认真不满；群里相同原句分别引用鲸鲸和其他人。只改变该因素，保留其他输入。
- 有失败先读实际请求。排查次序为触发和引用有没有送进来、模型是否读对、说出来是否自然。缺输入就修对应视图，输入充分才改表达或对比模型。
- 当前卡样本逐句核对三处：无依据的开会截止理由、未给能力前提就说群消息发不了、收尾示范加嘱咐与现行提示冲突。优先补足前提或换场景。样本清楚标为虚构，验收题另存。
- 行为底线用对照确认。正常短答、需要长解释、必要澄清、未被问时安静、保存失败与保存未知、能力暂缺与不具备能力。观察截止条件和事实保真，同时给两个提示词布局跑装配检查。

**退出证据。** 同一批合成输入下可重放两版模型请求，出站和业务写口隔离通过，计分能拒绝重复票和错误配对。实际模型候选的偏好、失败和信息完整度逐项报告。此阶段的产物成为 B–D 的测量入口。

## 3. B · 跨天记忆

**交付行为。** 她在需要时想起合适的前情，遇到明确更正会使用有效信息，面对不相关情境时不过度套用以往偏好。

**已核对的缺口。** `brain._canonical_memory_block()` 调 `MemoryService.search(context, kinds=[…])` 时没传 query。`one_tick` 当前传了视界、发送人和证据 ID，没传 `user_message`。后者也被其他检查使用，因此不能只在生产入口补参数就当作完成。`BeliefMemoryProvider` 当前对非空 query 有整串包含匹配，中文整句直接塞进去可能减少有效命中。

### B1 先把当前问题接上

1. 在真实窗口构建处确认触发消息来源。优先复用 `loop/run.py` 的当前窗口、`_fresh` 和引用/消息 ID，以同一范围的真实文本与直接引用作相关性输入。多条消息时保留对应人和证据 ID。无新消息的复核回合可用该目标标题或下一步做线索。
2. 查询上下文从当前回合身份派生，权限仍由 `ports.scoped_turn` 和现有 memory authority 确认。模型参数、群名、显示昵称和其他窗口正文不能替代身份。若决定复用 `user_message`，先回归它现有的红线、空回复检测和工具上下文行为。若这些语义不同，用专供召回的当前文本参数并明确来源。
3. 复用 `core/memory/service.py::MemoryService.search`、`recall_router`、`hub` 和现有 provider。保留固定、确有必要的常驻事实与按问题取回的记忆的明确区别。查询为空且无其他线索时提供必要常驻项即可。缺范围时退出。

### B2 排序和更正

1. 顺序为可见范围 → 有效版本与冲突 → 相关性排序 → 去重 → 截断。优先最小改动，比较旧空查询方案和现有中文分词或字串候选方案。初版把实体名、短关键词或分词命中用来取候选，避免在每个 provider 独立加一套同义规则。
2. 检查 `core/memory/beliefs.py::resolve_versions` 与 `core/memory/hub.py::recall` 的早截断。低相关但重要的条目不能在正确条目参与排序前把它挤掉。用固定候选数和现有 prompt 预算控制读数，先看真实用例再调整。
3. 条目保留 memory ID、事件来源、有效性和冲突标记。来源冲突可并列；更正后的旧版本不能在现状问题中复活。保留既有历史查询语义和显式查看能力。任一查询出错在现有 trace 可定位，不能解释成对方从没说过。
4. 验证显式读取与自动注入都经过同一权限和版本约束。记录实际命中、被截断和入 prompt 的 ID，方便排查漏召回。用现有 trace 和关联字段，不另外维护一份历史真源。

**验收。** 私聊明确表达偏好 → 模拟新回合与隔天 → 改写问法仍命中 → 同一句在不适用场景不触发 → 用户后来改口后使用新版 → 问当时的状态仍可依契约回查 → 同名不同账号、群、撤链范围不会带出旧事实。补一例相关结果被无关高重要记忆挤掉的反例。实际入口测试应检查进入 prompt 的有效证据与最后的回复。替身只负责证明接线，模型实际采用另测。

**复用测试。** `test_belief_reads.py`、`test_belief_history_tool.py`、`test_belief_commit.py`、`test_native_cognitive_eval_suite.py`。新增一条从窗口触发到实际首轮 prompt 的检索集成用例，避免只 mock 最终命中。

## 4. C · 经验复用

**交付行为。** 在明确反馈与相同条件下，她能改变下一次做法。条件变化时仍能自行判断。

**最小场景。** 用户先让她找同一项目的一条资料。当前任务明确要查本地项目文档，既有方法连续找不到，用户随后明确指出文档索引里有路径。下一次同类问题优先由索引定位。另用公共资料查询作条件变化反例。实验中使用已注册的、适用于回合的只读工具。输入和工具回包都可用合成数据。

1. 走读 `loop/brain.py::evaluate_experience` 工具处理、`core/context/experience_commit.py::{offers,submit}`、`core/context/reflection.py::{record_lesson,current_lessons_for_scope}` 和 `agents/planner.py::_reflection_state`。现役助手工具调用经 `loop/ports.py::act`，不能把 Planner 的读路径当成主循环已消费。
2. 先证明明确反馈能关联到对应任务和具体尝试。复用现有事件、工具结果与证据 ID。缺归属、不同会话、现有参考已撤销、只是用户没回话等情况保持未知。写入使用现有提交和版本守卫。
3. 经验应能表达所解决的问题、适用条件、方法、结果与证据。先验证现有 `Lesson` 和投影能否保留所需语义。如果按工具名单条覆盖会丢掉相反案例，最小扩展现有记录/索引并兼容旧条目。旧经验条件不完整时作为低确信度背景，不能作为强制选择。对确认范围内的保留和撤销沿用当前事件版本机制。
4. 在 `brain.run_loop` 现有请求装配里按当前任务及首轮可用能力选少量匹配经验。复用 reflection 的读取或渲染。优先把经验作为说明给模型，保持工具目录和执行侧授权。若同一匹配也供 Planner 使用，把共用读取和匹配维护在现有经验模块。
5. 试验只增减经验输入，固定其余前文与工具回包。记录哪些经验进入模型、模型选什么方法、结果如何。模型偏好不可用时不要悄悄将同一案例做成硬编码流程。

**验收。** 无经验时有合理选择 → 明确失败与反馈后同条件更换方法 → 条件变化仍可用旧办法 → 新证据能纠正旧经验 → 重复反馈不会累积同一经历 → 错范围或过期证据不会影响选择。对照有经验/去掉经验两组，对真正改善的类别给出原始选择和回执。复用 `test_experience_commit.py`、`test_appraisal_reflection.py`，加真实主循环读取及实际工具选择验收。

## 5. D · 连续任务

**交付行为。** 用户让鲸鲸整理两篇符合条件的资料。她接受后能说明还差什么，暂停、隔天或重启后能继续，收到取消会停止，拥有验收证据才说完成。第一批用隔离本地资料或工具替身，限定一个会话和一种任务。

**先复用的入口。** `loop/brain.py` 的 promise 路径，`core/context/promise_goal.py`，`core/context/goal_wake.py`，`loop/goal_review.py`，`core/context/goal_links.py`，`core/context/goal_receipts.py`，`core/context/goal_close.py`。任务执行按现有 Job/WorkItem 使用方核对，确认 `loop/job_bridge.py` 哪些动作有真实执行者。优先扩展已有端到端测试覆盖到本用例。

1. **建立。** 同一来源请求重放只挂一个目标。持久记录范围、期望产物、完成条件、下一步、等待条件和复核点。写目标失败就保留失败或部分回执，不能回「我已经记下」。审计流水、目标和 Job 的关联从现有目标链接读取。
2. **推进。** 有新材料或目标到复核点时，已有调度器把目标带入当前范围的回合。复核本身只说明重新检查过，目标进度由实际子步骤与可引用结果推进。记录找到的资源和去重依据，找到第一篇后明确剩余一篇。
3. **中断和恢复。** 在第一篇的结果持久化后终止测试进程。以同一隔离存储重新创建执行者，检查复核条件以及下一步从持久状态恢复。对步骤尝试使用已有幂等和关联约束。若发送或执行结果未知，保留未知并按现有对账规则处理。
4. **取消。** 从有权限的原会话发明确取消。先验证取消生成了持久状态及原因，再模拟已唤醒旧回合、迟到回执和重复取消。执行前复查目标状态，已取消目标不得继续提交动作。迟到的事实可审计，不能使目标重新活动。测试覆盖取消发生在外部动作之前与动作结果回来之后的区别。
5. **验收与报告。** 第二份独立结果确实符合约定，且产物已写入或可引用，才登记达到完成条件。将「资料找齐」「产物保存」「交付执行」「本机观察」「平台送达」按各自证据陈述。完成前的对话应能说明已完成部分和阻碍。最终交给用户的文字以届时实际状态生成。

**固定回放。** 开一个任务 → 第一篇成功 → 一条无关聊天 → 结束进程并从磁盘恢复 → 第二篇第一次失败 → 后续有效回包 → 查两篇证据 → 正确报告完成。另开一条分支在第二篇执行前取消并送迟到回执。补一个重复资源和一个无结果但工具返回正常的反例。

**复用测试。** `test_goal_review_loop.py`、`test_goal_wake_sources.py`、`test_goal_close.py`、`test_goal_reconcile.py`、`test_work_goal_link.py`、`test_wechat_goal_delivery_joint.py`。报告说明哪些路径走真实任务调度，哪些用工具替身。待 D 的恢复、取消和准确报告成立，再独立评估自主找机会和主动联系。

## 6. 共用回放、测试与交付

### 用三个故事贯穿四个切片

- **故事一 · 同一句话，前文改变。** 验 A 的情境理解与表达，后续每次改动都做回归。
- **故事二 · 说过、被纠正、隔天再聊。** 验 B 的相关召回和有效版本，再加一次明确的工具反馈验 C。合成一组跨账号反例，确认可用行为和权限同时成立。
- **故事三 · 承诺、中断、恢复。** 验 D 的任务推进、报告分寸和停手条件，串联 A 的表达、B 的事实和 C 的方法选择。

案例拆成开发集和冻结保留集。可在现有 `evals/expression` 与认知评测各自增加对应案例，用共享 ID 或对照关系串起来。留输入、唯一改动、预期行为、禁止结果及失败理由。验收比较可接受的行为，避免断言唯一台词。回复、沉默、工具选择与状态提交分开记。采用现有 `TurnTrace` 或录制器记录短理由、请求与证据引用，调试优先用合成输入。
